Key Takeaways

1. Meeting mode is the single largest feature gap. The meeting module files exist on disk in the Linux port directory, but the controller (mumble_linux.py) never imports them. This is a structural disconnect — not a missing-code problem — that could be resolved by porting the Windows meeting-wiring logic.

2. The island overlay has no mode selection UI. The companion bar / mode deck (Prompt, Email, Reply, Foreign chips) is entirely absent on Linux. Users can only toggle Prompt mode through the web Settings panel — there is no Email, Reply, or Foreign mode surface at all. Combined with the missing armed_color in the pill snapshot, the island UX is significantly degraded.

3. Three crash-grade bugs are present in the controller. bindings._session_type() doesn't exist (will crash copy_image()), stop_recording is not idempotent (will crash on double hotkey), and on_hotkey lacks a _processing guard (can double-start recording). All three have clear Windows reference implementations ready to port.

4. The Linux port has 59.7% code drift from Windows. Only 27 of 67 shared files are byte-identical. Six core modules (local_engine, meeting, meeting_diarise, tips, context_store, mumble_linux vs mumble) have >12% drift. Entire packages (eval/, models/, perf/, pipeline/, platform/) have no Linux counterpart. This is the primary long-term maintenance risk.

5. The installer is the strongest part of the port. install.sh is well-structured, covers four package manager families, correctly uses --system-site-packages for PyGObject, and handles errors gracefully. The main UX concern is repeated sudo prompts for optional packages.

C-001: Meeting Mode Entirely Absent

CRITICAL Area: Controller P0

Description: The entire meeting recording feature is absent from the Linux port. The controller does not import the meeting module, does not create a MeetingRecorder, and exposes no meeting commands. Meeting source files (meeting.py, meeting_diarise.py, meeting_store.py) exist in the Linux port directory but are never imported or wired.

Why it matters

Users cannot record, transcribe, or diarize meetings on Linux. This is a headline feature advertised on the Mumble website and present on Windows — its absence on Linux is immediately noticeable and disqualifying for many potential users.

Detail Evidence & Fix

Location: Internal/app/Ports/Linux/app/mumble_linux.py

Missing methods (present in mumble.py lines 207-417):

  • __init__ → self.meeting_recorder = None; self.meeting_recording = False
  • _meeting_island_cb — island timer + speaker count display
  • _meeting_start — begin recording with diarisation
  • _meeting_stop — stop and background-process
  • _meeting_import — import external audio
  • Meeting commands in cmd server: meeting_record_start, meeting_record_stop, meeting_record_pause, meeting_record_resume, meeting_import_audio

Evidence: Controller Audit §1.1, §2.1. The import meeting statement at Windows mumble.py line 97 has no equivalent in mumble_linux.py.

Additional concern: The shared meeting.py file in the Linux directory is 53.1% smaller than the Windows version (14,846 vs 31,652 bytes), and meeting_diarise.py is 60.6% smaller (9,451 vs 23,985 bytes). Even if wired, the Linux meeting modules are severely out of date.

Suggested fix:

  4. Add dictation veto during meetings (check self.meeting_recording in start_recording).
  5. Estimated complexity: L

C-003: stop_recording Not Idempotent — Double Hotkey Crash

CRITICAL Area: Controller P0

Description: Linux stop_recording (line 917) lacks the idempotent guard present in Windows (lines 996-1002). A double hotkey press can enter stop_recording twice before self.recording flips, causing np.concatenate(self.frames) on an already-cleared list, producing a "need at least one array to concatenate" error.

Why it matters

Double-tapping the hotkey is a common user behavior (nervousness, uncertainty about whether the first press registered). On Windows this is safely handled; on Linux it crashes the recording thread. This is a user-facing crash with a trivial fix.

Detail Evidence & Fix

Location: mumble_linux.py line 917 vs Windows mumble.py lines 996-1002

Windows guard (missing on Linux):

with self.lock:
    if not self.recording:
        return
    self.recording = False

Evidence: Controller Audit §3.6. Code diff confirms missing guard.

Suggested fix: Copy the Windows idempotent guard into Linux stop_recording. One-to-one port with no adaptation needed.

Estimated complexity: S

C-004: on_hotkey Missing _processing Guard — Double-Start Recording

CRITICAL Area: Controller P0

Description: Linux on_hotkey (line 1497) doesn't check self._processing. If the hotkey is pressed while a previous dictation is still in its transcribe→AI→paste pipeline, a new recording starts on top of the in-flight one, corrupting shared stream state and potentially opening a second microphone stream.

Why it matters

This can cause garbled transcription output, microphone resource conflicts, and in the worst case, corrupted audio buffers that produce nonsensical text. Windows has the guard; Linux needs it too.

Detail Evidence & Fix

Location: mumble_linux.py line 1497

Windows guard (missing on Linux, mumble.py lines 1711-1718):

if self._processing:
    return None

Evidence: Controller Audit §3.7.

Suggested fix: Add the _processing guard at the top of on_hotkey, matching Windows. Also add the missing _safe_start cleanup-on-error pattern (see issue C-005).

Estimated complexity: S

C-005: linux_fallback.py Missing — Vulkan Acceleration Dead

CRITICAL Area: Platform Integration P0

Description: platform/__init__.py line 233 imports from .linux_fallback import WhisperCppTranscriber, but linux_fallback.py does not exist anywhere in the project. On Linux ARM with Vulkan, the import raises ImportError (silently caught), and the system falls back to CPU-only faster-whisper with no user-visible warning.

Why it matters

Linux ARM users (Raspberry Pi 5, Jetson, Snapdragon X Elite laptops) get no GPU acceleration. Transcription runs on CPU, which is significantly slower and more power-hungry. The silent fallback means users never know acceleration was attempted and failed — they just experience poor performance with no explanation.

Detail Evidence & Fix

Location: Internal/app/platform/__init__.py line 233

Evidence: Platform Integration Audit §6. The app/platform/ directory contains only __init__.py, macos_audio.py, and windows_dml.py. No linux_fallback.py exists in the entire repo.

Suggested fix:

  1. Implement linux_fallback.py with a WhisperCppTranscriber class wrapping whisper.cpp with Vulkan compute shader support.
  2. At minimum, add a proper log warning (not silent ImportError pass) when the acceleration path is unavailable, so users understand why performance is degraded.
  3. Consider bundling pre-compiled whisper.cpp ARM binaries during install.

C-010: Pure Wayland (No XWayland) — No Island at All

Pure Wayland sessions are increasingly common (Fedora Workstation defaults to Wayland, GNOME on Wayland is standard on most distros). Detail Evidence & Fix

9Performance & Memory

In plain terms

Several performance optimizations present on Windows are absent from Linux. The Linux port may use more idle memory, lack STT performance diagnostics, and miss hardware-aware optimizations that Windows users benefit from. No live benchmarking was performed — these assessments are based on code analysis.

9.1 Memory Management

  • Missing GC calls: Linux doesn't call gc.collect() after dictation, model swaps, or boot. Windows does all three. Linux may hold more idle memory, particularly after long sessions or model changes. Risk to VAL-PERF-003 (<1GB idle target). MEDIUM
  • Missing STT performance diagnostics: ITEM 20 realtime-factor tracking (_stt_device, _stt_compute, _stt_model) is absent from Linux. No way to diagnose slow transcription on underpowered hardware. LOW
  • PIL Image reference management: _cur_img overwritten each frame — old PIL Image is GC'd promptly. OK. OK
  • Pixbuf memory: GdkPixbuf objects are GLib ref-counted, freed when Python wrapper goes out of scope. OK. OK
  • Background cache: island_render._BG_CACHE LRU-bounded at 8 entries. OK. OK

9.2 CPU Efficiency

  • Polling throttle: Text clipboard polls every ~2.1s (every 3rd cycle at 0.7s interval), image clipboard throttled to ~5.6s. Appropriate for Linux's fork-heavy pyperclip. OK
  • Wayland fallback: No Vulkan acceleration means CPU-only transcription on Linux ARM. Significantly slower and more power-hungry. CRITICAL
  • Process priority: _boost_priority() returns None (no-op) with documented reason (needs CAP_SYS_NICE). Correctly handled. OK

9.3 Rendering Performance

  • GLib tick scheduling: Uses GLib.timeout_add() with manual re-add (returns False). Correct pattern for variable-interval timers. OK
  • Cairo surface creation: Pixbuf path is preferred (avoids byte-order issues). Both paths are correct. OK
  • No GDI handle leaks: Linux doesn't use GDI. Windows has _LayeredDC.__del__ finalizer; Linux has no equivalent concern. OK

10Code Quality & Technical Debt

In plain terms

The Linux port shares the same structural problems as the overall Mumble project: large monolithic controller files (~4000 lines), copy-pasted logic across three platforms, and no automated testing. However, the Linux port introduces additional debt: a partially complete _NoopIsland fallback, duplicated rendering logic, an inconsistent package structure, and missing documentation markers for unimplemented features.

10.1 File Size

  • mumble_linux.py: 4,089 lines (~189KB). Large but structurally mirrors Windows (4,994 lines). The Linux version has ~82% the size of Windows with significantly fewer features — suggesting significant redundant code that could be factored out into shared modules.
  • overlay_linux.py: 962 lines (~42KB). Relatively modest compared to Windows overlay.py (2,194 lines), but only because the companion bar (~500 lines) is missing entirely.
  • ai.py (flattened): 111K monolith. Windows equivalent is 11 files in ai/ package. The monolith approach makes it harder to diff, sync, and maintain.

10.2 Duplicated Code

  • Controller methods: _ai_cfg, _prompt_ai_cfg, _pro_fallback_notice, _build_menu, _recent_items, _preview are near-identical copies between Windows and Linux controllers.
  • Overlay snapshot logic: _build_snapshot() is ~90% identical across overlay.py and overlay_linux.py. Any schema change requires edits in both files (plus macOS).
  • Utility functions: _hex(), _blend(), _mode_names(), _listen_timer() are duplicated across both overlay files AND island_render.py — three copies total.
  • Three parallel codebases: Controller (~4000 lines each), overlay modules, and shared libraries are duplicated across Windows, macOS, and Linux rather than abstracted behind interfaces. This is a structural debt that compounds with every feature addition.

10.3 Missing Error Handling

  • No try/except around clipboard resume in _paste_impl
  • No cleanup in _safe_start on stream error
  • No idempotent guard in stop_recording
  • No _processing guard in on_hotkey
  • Silent ImportError catch for missing linux_fallback.py — no warning logged

10.4 Missing Documentation Markers

Neither mumble_linux.py nor overlay_linux.py contain any TODO, FIXME, HACK, XXX, or WORKAROUND comments. This is unusual for a port of this size — it suggests comments that might flag incomplete work were never written. The suspended attribute comment ("unused on Linux, kept for parity / tick guard") is the closest thing to an implicit TODO. Several clearly incomplete areas (companion bar, suspended state, Wayland fallback) have no markers.

10.5 Inconsistent Patterns

  • _process structure: Windows manages _processing in stop_recording (sets it before calling _process, clears in finally). Linux manages _processing inside _process itself. Structural divergence could confuse future refactoring.
  • _collect_text: Linux relies on shared ai module's version. Windows defines its own with additional TRUNC_MARKER handling. Inconsistent behavior for truncated AI responses.
  • Package vs monolith: Linux flattens ai/ into ai.py but entirely omits other packages. No clear rationale for which packages get flattened and which get dropped.
