In plain terms

This is the builder's guide to Mumble — the dictation app that turns your speech into clean, formatted text. It explains how the program is wired together, the unbreakable promises it makes (the biggest: audio stays local unless the user explicitly selects Cloud transcription), and the step-by-step habits a developer follows when starting work, fixing a bug, shipping a feature, or copying changes over to the Mac and Linux versions.

1The session ritual

In plain terms

Every work session has a fixed start and a fixed end — like a pre-flight and post-flight checklist. You open by getting your bearings (read the docs, write down what you're going to do, read the exact code you'll touch). You close by proving the work is sound (run the tests), ticking off every item, updating the docs so they still tell the truth, committing, and shipping.

How a session begins

  1. Read the four core docs (this file, README, STATUS, LOGS) — at least skim STATUS in full; it's the state of the world.
  2. Restate the request as a □ checklist (see README §8) before touching code.
  3. Read the code you'll actually change — the module + its tests + its callers. Never edit blind.
  4. Confirm the operating mode (default 🟢 Autonomous) and note any owner-only blockers.

How a session ends

  1. Verify — offline test suite + lint + compile (see §4).
  2. Resolve the checklist — every line ✓ or □; every □ gets a reason and is written into STATUS (a known bug / TODO / roadmap item) so it survives.
  3. Update the docs to match reality — STATUS (open items moved/closed), HANDBOOK (any rule/architecture change), README (any user-facing capability change), and append a dated entry to LOGS for what shipped.
  4. Commit with a clear message; deploy/sync in the autonomous modes; confirm the deploy.
  5. Sign off with the completion report and the · docs updated marker if any core doc changed.

Planning and decisions across sessions

GitHub Issues are Mumble's long-term work tracker. Use the Planning map issue form for a multi-session outcome, the Engineering decision form when a choice would be expensive to reverse, and the Implementation work form for one bounded change. Each implementation issue must name the planning map, any decision that governs it, its blockers, and the evidence required to close it.

  • Planning map: the living route through a substantial outcome. Keep it as a GitHub task list so its linked work can be seen at a glance.
  • Decision ticket: the durable explanation of why Mumble chose a startup, packaging, deployment, local-model, or dictation-latency direction. Link source evidence and say when the choice should be reviewed.
  • Implementation ticket: one safe slice of work. Use GitHub's issue relationship control, plus the written Blocked by #number line, whenever another issue must finish first.
  • Core records: keep STATUS as the short current truth, this HANDBOOK as the procedure and architecture context, and LOGS as completed history. GitHub issues hold the work discussion; they do not replace these records.

The repository keeps the issue forms and label list in .github/. To restore the labels after a new GitHub repository is created, run the documented .github/scripts/sync-labels.ps1 helper from a machine already signed in to GitHub; it only creates or updates labels in the named repository.

2Architecture deep-dive

In plain terms

Mumble is built from a handful of cooperating parts. One file, mumble.py, is the "brain stem" — it listens for your hotkey, records audio, runs the transcription, and decides what to do with the words. Around it sit the window (the settings UI), the floating "island" pill that shows status, the engines that clean and shape your text, and the little databases ("stores") that remember your history, clipboard, favorites, and settings.

The most important idea below is the privacy invariant: raw audio is processed on your machine; only the finished text is ever sent to a cloud AI, and only if you turned that on and supplied your own key.

The runtime, top to bottom

  • mumble.py — the controller (entry point). Owns audio capture, the transcription pipeline, Smart-Mode dispatch, the system tray, global hotkeys, the single-instance command server, and the meeting recorder. Everything the user triggers flows through here.
  • webui_shell.py — the window. A pywebview shell hosting the webui/ SPA, plus the Api bridge that exposes Python methods to JavaScript. Imported by the controller; also launchable standalone for UI preview.
  • app_window.py — the Tkinter fallback window ("Lite"). Live, not dead: if _open_web_ui() fails (pywebview / Edge WebView2 runtime unavailable), mumble._open_window falls back to AppWindow. Also a test_ui.py dependency.
  • overlay.py + island_render.py — the island. An in-process, per-pixel-alpha, click-through, always-on-top layered window (Pillow → Win32 UpdateLayeredWindow). No separate process, no WebView2, never steals typing focus, follows the active monitor. The companion bar is visible only for actionable states. Correction candidates remain passive until a concrete target edit is detected; that event opens a bounded Review/Dismiss consent surface rather than keeping the island alive after every paste. Falls back to a plain tkinter-canvas pill if Pillow/numpy are missing, so the island can never go missing.
  • Core engines. formatting.py (offline text cleanup + mode inference), ai/ (cloud provider package — replaces the old top-level ai.py), transcription.py (opt-in cloud STT), prompt_constitution.py (prompt crafting), islamic_terms.py, presets.py, foreign_boost.py (offline Foreign-Mode phonetic token boosting).
  • Local AI / offline LLM (V1.0+). local_engine.py (cloud-vs-local router; LlamaCpp / LlamaServer backends), models/ (registry, downloader, cache, backend manager), pipeline/ (local post-processing stages: formatting, grammar, punctuation, cleanup), platform/ (platform runtime helpers: macos_audio.py, windows_dml.py, linux_fallback.py).
  • Meeting capture (V1.2 foundation). meeting.py (recorder controller), meeting_diarise.py (speaker diarization pipeline), meeting_store.py (meeting persistence).
  • Reader / Document. reader_parser.py (document parsing for Reader view) and reader_store.py (parsed document library).
  • Quality / observability. eval/ (harness, scenarios, metrics, reporter), perf/ (diagnostics, optimizer, profiler), stats.py (word/frequency stats), and dictation_trace.py (opt-in, local-only end-to-end timing evidence).
  • Stores. Each persists to the OS app-data dir: settings, history, clipboard, favorites, stats, prompt_history, context_store, reader_store, and cloud_sync (Supabase; schema in cloud_schema.sql).
  • Infra. bindings (the single funnel for all key/mouse input), branding (names, paths, VERSION, design tokens, DATA_DIR), ui (shared Tkinter toolkit), autostart, update (with optional Ed25519 manifest signing), brand_exe, assets_gen, tips.py.

Data flow — dictation

What happens, in order, from the moment you press the hotkey to the words landing at your cursor:

1
Start capture

Hotkey → controller starts audio capture.

2
Stop & transcribe

While the user speaks, the local worker commits bounded four-second ranges. Hotkey again → capture stops → an already-running range is harvested once → only the uncommitted tail is transcribed. Ordinary local decoding is a single greedy pass with no timestamp tokens; opt-in cloud STT still falls back to local on any error.

3
Clean & infer shape

formatting.py applies personal vocabulary and cleanup. With Instant plain dictation enabled (the default), ordinary Text is formatted locally and proceeds directly to paste; explicit Prompt/Email/other modes retain their richer processing.

4
Pro Mode lane (or offline builder)

For an explicit AI mode—or when Instant plain dictation is switched off— local_engine.route() decides cloud vs local. If Pro Mode is on, a key is set, and local-only mode is off, the ai/ package sends only the text to the chosen provider. Otherwise the local LLM/pipeline or deterministic builder produces the result.

5
Paste & record

The result is pasted at the cursor (confirmed clipboard save → paste → restore) and saved to history. The island shows the live state and the finish flash.

Dictation timing trace (benchmark and support use)

The production controller has an opt-in trace for measuring cold and warm dictation without changing the speech engine or normal user experience. Set MUMBLE_DICTATION_TRACE=1 before starting Mumble. Completed sessions are appended beneath the normal application-data directory at diagnostics/dictation-traces.jsonl. Tracing is off by default.

  • Coverage: activation, the first rendered Island state, microphone open/record/close, first audio, first stable partial when present, stream drain, transcription and paste lock waits, model load/warm-up when they occur during a session, inference, final-result readiness, formatting, persistence, clipboard readiness, paste dispatch, completion, and process CPU/RAM/thread samples.
  • Truthful partial-result boundary: the current local worker commits stable four-second chunks. It has no tentative-token surface, so traces declare partial_contract=stable_chunks_only and do not invent an unstable-partial timestamp.
  • Privacy: schema mumble.dictation-trace.v1 accepts a fixed metadata vocabulary only. It stores no audio, transcript or partial words, clipboard contents, prompts, file paths, provider payloads, keys, or exception messages.
  • Storage: the local JSONL file is capped at 5 MB with two rotated backups and private-file permissions where the operating system supports them. A completed record is flushed before the session is considered recorded; tracing failures never block dictation.
  • Export: call dictation_trace.export_traces(source, destination, limit) from the application environment to create one standalone JSON array. Review that export before sharing it even though the schema is content-free.

The AI payload invariant (privacy)

Local means local; cloud means disclosed. Local transcription never uploads audio. When the user explicitly selects Cloud transcription, the recorded audio clip is sent to the selected STT provider. Pro Mode and Reader voice send their disclosed text payloads. No telemetry or hidden payload is added. When you add or change a lane, document exactly what leaves the device.

Threading model (essentials)

  • The controller runs the tray + hotkey listeners; transcription and AI calls run off the UI thread so the app never blocks.
  • The island renders in-process; UI updates that touch tk/pystray must be marshalled to the right thread (off-thread pystray menu updates are a known hazard — see STATUS).
  • Generation lanes use a generation counter so a newer dictation/Reader action cancels a stale in-flight one. Preserve gen-checks when editing playback/prefetch paths.
  • Local STT is serialised by _tx_lock. Streaming ranges carry a recording-session id and an idle/in-flight event: key release may harvest work from the same session, but a superseded or sleep-invalidated worker cannot publish text, advance the seam, or signal a newer session idle.

Provider routing & fallback

  • One processing provider handles every optional AI text lane. Product settings expose only Cerebras (recommended low-latency route with a rate-limited free tier) and OpenRouter (one key with a curated fallback list plus live model discovery). There is no separate Prompting Provider. Keys are user-supplied, stored locally, and masked.
  • The Model field is a dropdown populated from the provider's live model list (curated fallback offline). On 429 the lane waits the server-requested delay (capped) and retries once, then falls back to the offline builder. Reasoning models that reject a custom temperature (400) must have temperature omitted.

Prompt templates and provenance

  • prompt_constitution.py contains original Mumble prompt-shaping instructions. prompt_template_registry.py records template id, version, modes, output contract, authorship, and licence posture.
  • External prompt projects may inform architecture only until their licence and exact reuse plan are recorded. Fabric and Microsoft promptflow are currently MIT research references; no prompt text or code from either project is copied into the runtime.
  • Prompt history is a visible Deck artefact store. It is not conversation memory and is never injected into a later generation. The retired continuity file is removed during migration.

Experimental Mumble Search boundary

  • experimental/system_search/engine.py owns a bounded local index of known application locations and standard/configured user folders. It skips hidden and dependency/cache trees and caps the index at 75,000 items by default.
  • The WebUI receives display metadata and opaque stable IDs, never executable command lines. Open, reveal, copy-path and favourite actions are accepted only for IDs present in the current index (or a short-lived web-fallback result).
  • User search text is never interpreted as a path or shell command. Windows opens Start Menu/App Paths entries with OS APIs; Linux launches trusted desktop entries or xdg-open using argument arrays and no shell.
  • Fuzzy matching combines exact/prefix/token/subsequence signals with local-only favourites, use count and recency. A configured web engine appears as a low-ranked fallback only for non-empty all-category queries.
  • Application icons are display metadata behind the same opaque-ID boundary. Windows asks Explorer for shortcut, executable and virtual Start-app icons, draws them into a top-down 32-bit DIB (so orientation and alpha remain correct), and keeps a 128-entry memory cache. Linux resolves each trusted desktop entry's local icon through installed theme directories. Search never downloads an icon or substitutes a generated application monogram.
  • The feature and hotkey route ship on Windows and Linux. The macOS port intentionally has no Search loader or API because the product decision is to rely on Spotlight/Finder there.

3Data model

In plain terms

Mumble keeps your data in plain files in a folder that belongs to the app. There's no cloud account required and no shared database — just files on your disk. One file, settings.py, is the official list of every setting; trust it over any list written in docs, because docs drift. Your keys and secrets live only in that settings file — never in the source code or in git.

Each platform now resolves its native per-user data location. The Mac port uses ~/Library/Application Support/Mumble; Linux uses the XDG data directory.

Each store reads/writes JSON (or its store-specific format) under an app-data dir resolved in branding.py (DATA_DIR):

  • Windows: %APPDATA%\Mumble — confirmed in code.
  • macOS: ~/Library/Application Support/Mumble.
  • Linux: $XDG_DATA_HOME/Mumble, falling back to ~/.local/share/Mumble.

settings.py is the single source of truth for setting keys — read it rather than trusting any enumerated list in docs (the old HANDBOOK's key list drifted; don't recreate that mistake). Keys/secrets live only here, never in source or git. History, clipboard, prompts, favourites, stats, context, and the Reader library are each their own store with its own file; cloud_sync.py mirrors the syncable ones to Supabase when the user opts in.

4Testing & verification

In plain terms

Before any code is committed, it has to pass three automatic checks: the test suite (does it still work?), the linter (is the style clean?), and a compile pass (does every file even parse?). Most tests run fully offline — no API key, no internet needed. A small "live" set actually talks to a real provider and needs a key plus a network connection.

The suite lives in Internal/app/test_*.py, co-located with the modules so sibling imports work. It is excluded from the production Mumble.zip. (Post-restructure the runtime + tests live under Internal/app/; older docs that said Internal/test_*.py predate the app/ move.)

Authoritative runner: run_tests.py forces UTF-8, isolates app data per test, scrubs credential-shaped environment variables, enables offline model guards, and applies a per-test timeout. Live provider scripts are excluded unless both --live and MUMBLE_RUN_LIVE_TESTS=1 are supplied. The runner can emit a JSON report for CI.

5The rules you must not break

In plain terms

These twelve rules are non-negotiable promises about how Mumble behaves. Breaking one counts as a bug even if every test still passes. They cover privacy (local stays local, cloud use is disclosed, no built-in key), reliability (only one copy runs at a time, the clipboard is always restored), and honesty (the UI never shows features that aren't real, the docs always match reality).

These are invariants. Breaking one is a regression even if tests pass.

  1. Local stays local; cloud use is explicit. Local transcription is the default and never uploads audio. Opt-in Cloud STT sends the recorded clip to the selected provider and falls back to local on error. Pro Mode and Reader disclose the text they send. privacy
  2. No built-in API key. Every key is the user's own, stored only in the local settings.json, masked in the UI, never logged, never committed. privacy
  3. Key/mouse input listening goes through bindings.py. Don't add new direct calls to a key/mouse listening library elsewhere. (Output key-synthesis — paste/copy via the keyboard library in mumble.py — is the established exception, not a violation.)
  4. Single instance. One controller at a time: _acquire_single_instance() binds 127.0.0.1:49517 (no SO_REUSEADDR) so a second bind fails; the second launch signals the running instance and exits via sys.exit(0). (os._exit(0) is the controller's own teardown path, not the second-launch handoff.)
  5. Authenticate the localhost command channels. The loopback IPC ports (49519 controller, 49520 webui, 49517 lock) are bound to 127.0.0.1 but that is NOT a trust boundary — any local process, including a malicious page hitting http://127.0.0.1:49519, can connect. Every privileged command must carry the per-session token (branding.write_session_token at controller startup → read_session_token on the client → token_ok constant-time compare). When you add a new command verb or a new IPC surface, gate it with the token; never add an unauthenticated paste/selection/job/window-control verb. security
  6. The constitution is sent on every Prompt-lane call. Don't cache it away.
  7. The Prompt lane gets the long budget + a capped adaptive 429 retry — it must not silently degrade to the offline draft when the server just asked us to wait.
  8. Confirmed clipboard restore. Paste = save clipboard → set → paste → restore, with the restore verified.
  9. Zero-CDN UI. No web fonts, no remote scripts; everything in webui/ ships locally.
  10. Resource-aware UI. Minimised / hidden / unfocused → all ambient animation + status polling stop.
  11. Platform-agnostic core stays portable. Shared engine/store/UI code must be reusable byte-for-byte by the ports; OS-specific code lives only in the port seam files.
  12. Don't reintroduce "depicted-but-not-real" UI (see STATUS §7).
  13. Docs match reality before "Prompt done" (see README §8).

6Implementing a feature

In plain terms

Build new things on Windows first (it's the reference version), change as little as possible, add a test in the same edit, and make sure the feature works all the way through before calling it done — a feature half-built across many places is worse than one clean slice. Update the docs, then copy it to Mac and Linux once it's solid.

  1. Land it on Windows first — it's the source of truth.
  2. Touch the smallest surface. Engine logic in the engine module; UI in webui/ + the Api bridge; persistence in the relevant store. Keep the seam between them clean.
  3. Add/adjust a test in the same change. Offline-testable logic gets an offline test.
  4. Wire it end-to-end before calling it done — a feature that's half-built across many surfaces is worse than one slice done fully. If a large/risky rewrite can't be fully verified here, pace it: one focused slice end-to-end, and say so.
  5. Update the docs (README if user-facing, HANDBOOK if architectural, STATUS for the to-do, LOGS for the record).
  6. Then port to macOS/Linux (see §8) once it's solid on Windows.

Experimental isolation boundary (5.6 sol xtra high). The Operator prototype under Development Files/Other/experiments/AIs - DO NOT TOUCH/Experimental Feature - 5.6 sol xtra high/ is development-only and deliberately sits outside this production feature procedure. Its optional Right Shift watcher and localhost action adapter are evaluation harnesses, not production seams: do not import them into Internal/app/ or copy their key polling into a controller. Any future product spike must register through bindings.py, use authenticated IPC, receive local transcripts through one explicit adapter, preserve the clipboard fully, and keep destructive actions behind visible previews and consent.

7Bug-fixing protocol & quality standards

In plain terms

To fix a bug: reproduce it exactly, check which promises (the rules in §5) the area touches, write the smallest failing test, then make the smallest change that turns it green. Re-run the related tests, update STATUS, and commit. And be honest — never claim "fixed" for something you couldn't actually verify.

  1. Capture the exact repro and the owning surface before editing.
  2. Check the invariants (§5) the area touches.
  3. Write the smallest regression test that fails, then make the smallest code change that turns it green.
  4. Run the offline suite + the neighbours of what you changed — a fix in formatting re-tests dictation; a fix in ai re-tests every lane; a fix in a store re-tests its round-trip.
  5. Update STATUS (move the bug from Known Bugs to a LOGS entry) and commit.
Honesty bar: never report "fixed" for a path you couldn't verify. If it's fixed-on-Windows-but-unverified-on-a-port, say exactly that and leave the port item open in STATUS.

8Port-sync procedure (macOS / Linux)

In plain terms

Mumble's Mac and Linux versions reuse almost all of the Windows code unchanged — the "brain" (text, AI, storage, the island, the lock channel) is identical everywhere. Only the small OS-specific "seam" files differ (how hotkeys, pasting, the window, and the tray talk to each operating system). To port, you copy the shared files over verbatim and hand-edit only the seam.

One sharp warning: pause OneDrive sync first. If sync is running while you edit the port folders, it can silently undo your changes within seconds — so after editing, check the file on disk to confirm the change actually stuck.

The ports live in Internal/app/Ports/macOS/app and Internal/app/Ports/Linux/app (post-restructure path; older docs said Internal/Ports/…). Each forks only the OS-seam files (mumble_mac.py/mumble_linux.py, overlay_mac.py/overlay_linux.py, the installer/launcher). The data/AI/text brain, the web UI, the island renderer, and the lock/command channel are platform-agnostic and reused verbatim — Internal/app/ (Windows) is the parity source.

Drift is real — verify, don't assume (updated 2026-07-15). The macOS snapshot now has the current ai/, eval/, models/, perf/, pipeline/ and platform/ packages. Its obsolete top-level ai.py, duplicate mumble.py, Prompt Memory/provider files and mode-key runtime were removed. The Linux snapshot was reconciled the same day: it now carries the current shared package/UI contracts, and its duplicate Windows controller, Tk window, overlay, top-level ai.py and Prompt Memory files were removed. Real macOS and Linux hardware behaviour remains a separate qualification gate. After a Windows shared-module change, compare both ports deliberately and preserve only documented OS-seam differences.

Procedure:

  1. Pause OneDrive sync first. Editing the port dirs while sync runs can revert your writes within seconds (STATUS → T-PORTREVERT). After editing, grep-verify the change actually stuck on disk.
  2. Sync the shared modules verbatim from Internal/ to each port's app/ — never hand-edit shared code in a port.
  3. Apply only the seam differences by hand (hotkeys via pynput/evdev, paste via AppleScript / xdotool·ydotool, overlay via WebKit/GTK, paths, tray).
  4. Run that port's offline suite. Keep the port runner's authoritative allow-list and release-closure tests current when shared modules or browser assets are added.
  5. Record verified drift in the four core docs. Do not rely on an untracked side file; unfinished port work belongs in STATUS and completed work in LOGS.

Platform seam summary:

macOS

Global hotkeys via pynput (no sudo); WebKit window via pywebview; paste/focus via osascript; data under ~/Library/Application Support/Mumble; launch-at-login via a LaunchAgent; a detached pystray menu-bar process so the main thread can run tk + pywebview.

Linux

Hotkeys via pynput (X11) / evdev (Wayland; needs the user in the input group); window via pywebview on GTK + WebKitGTK; island as a native GTK transparent click-through pill (Cairo per-pixel alpha); paste via xdotool/ydotool + xclip/wl-clipboard; tray via pystray/AppIndicator (degrades to notify-send); data under XDG; autostart via a ~/.config/autostart/*.desktop entry. X11 is the full-fidelity target.

9Commit expectations

In plain terms

Make one clean change per commit with a message that says what changed and why. Verify before you commit — never commit a failing test suite. Commit promptly, because this repo can be touched by another device through OneDrive, and long-lived uncommitted edits risk being swept away. Never commit secrets or heavy build junk.

  • One coherent change per commit; a clear, specific message (what + why, not "fixes").
  • Verify before you commit (§4). Don't commit a red suite.
  • Commit promptly. This repo can be touched by another device via OneDrive — long-lived uncommitted edits risk being swept into a foreign commit or reverted. Keep messages simple and land them.
  • Never commit secrets or the .venv, caches, or build zips that .gitignore excludes.

10Deploy

In plain terms

Shipping Mumble means packaging the runnable app (the Mumble.exe launcher plus the Internal/ code) into a zip — leaving out tests, the virtual environment, and dev scripts. Each operating system has its own install path. Always run a quick smoke test to confirm the deploy worked before declaring victory. Note: the auto-update feed isn't live yet, so don't switch it on.

The production build is Mumble.exe + Internal/. Development Files/ is excluded.

Rebuild the distributable when the runtime changes meaningfully — repackage Mumble.zip from Internal/ (the build-tools/ helper handles this; it mirrors source, refreshes every zip entry from disk, drops deleted files, and force-adds new modules). Exclude test_*.py, .venv, __pycache__, and dev scripts from the shipped zip.

Windows

Rebuild Mumble.zip → user extracts → runs Install Mumble.bat (one-time: installs Python + the speech model + builds the venv) → tray icon appears.

One installed target: the manual entry point is the repository-root Mumble.exe. Installed Desktop, Start-menu and Startup shortcuts point directly to Internal/app/.venv/Scripts/Mumble.exe, pass Internal/app/mumble.py, use Internal/app as their working directory, and load Internal/app/assets/mumble.ico. Windows login uses only the Startup-folder Mumble.lnk; there must be no competing Mumble Run-key entry or one-time FinalizeMumble.cmd helper.

Flow Launcher discovers Mumble through the Start-menu shortcut. After moving, reinstalling or replacing a Mumble checkout, recreate the shortcuts first and then press F5 inside Flow Launcher to reload plugin data. Never preserve a shortcut or icon path to a downloaded test folder.

Code Windows launch-path verification 
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "Development Files\Other\build-tools\verify_windows_launch.ps1"

Run this from the repository root after installation or a folder move. It fails if the manual launcher, runtime, entry script, icon, installed shortcuts or Flow Launcher index point to a missing location, or if another Mumble startup item competes with Mumble.lnk.

macOS

Use the port launcher for a normal install, or run from the app dir for development. Hotkeys need Accessibility permission and dictation needs Microphone permission on first run.

cd Internal/app/Ports/macOS/app && pip install -r requirements.txt && python mumble_mac.py

Mumble Custom Model — Licence Strategy

The planned Mumble-branded model will be based on Qwen3.5-4B (Apache 2.0). Apache 2.0 permits:

  • Fine-tuning, modification, and redistribution under any name
  • Commercial use without restriction
  • No obligation to open-source derivative weights (permissive, not copyleft)

Required: include the original Apache 2.0 LICENSE file, state what changes were made, preserve any NOTICE file from the original model. The model can be named "Mumble LM" or any distinct name without referencing Qwen in the product name (though attribution in documentation is required). See the full model strategy in the 2026-06-28 LOGS entry.
