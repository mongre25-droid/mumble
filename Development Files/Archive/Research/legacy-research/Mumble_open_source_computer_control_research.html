Open-source computer control for Mumble

A deep review of open-source desktop agents, browser agents, Windows automation libraries, and voice-command building blocks—with a recommendation tailored to Mumble’s existing Python, Windows-first, privacy-first architecture.

Research method: Firecrawl search/scrape across primary GitHub repositories, GitHub topics and discussions, Reddit discovery threads, and X posts; plus browser verification of the Microsoft UFO repository. Popularity/licence figures below are a point-in-time GitHub API snapshot, not a quality guarantee.

The short answer: do not embed one broad “autonomous desktop agent” as Mumble’s only control mechanism. Build a small, permissioned command router that uses pywinauto for Windows applications and Playwright for browser tasks. Add Browser Use for open-ended web tasks and make UI-TARS Desktop an explicit, visible fallback for unfamiliar UIs. This gives Mumble speed and reliability on routine commands, without pretending that visual AI control is infallible.

What “open anything and do anything” really requires

1. Intent and policy

Turn speech into a structured request, decide whether it is allowed, and ask before destructive or external actions. This belongs in Mumble—not in a third-party agent.

2. Direct actions first

Launching an app, opening a URL, searching Brave, changing a known setting, or filling a known form should use a deterministic API or automation library. It is faster, auditable, and far less brittle than screen clicking.

3. Visual fallback

A GUI agent that sees screenshots and clicks is valuable for unknown apps and dynamic interfaces. It is also inherently probabilistic, can misread screens, and needs an obvious stop control.

Recommended foundationBSD-3-Clause

pywinauto + a Mumble command router

Best native Windows foundation. Mumble is already Python and runs as a background Windows app, so pywinauto can launch known applications and target their UI Automation/Win32 controls without adding a Node or Electron runtime. Use it for reliable, approved workflows—not as a visual general-purpose agent.

Use for: app launch, focusing windows, menus, forms, desktop settings, and an explicit “open application” tool.

Recommended browser layerApache-2.0

Playwright, then Browser Use

Use Playwright for predictable browser commands; it gives structured browser control rather than coordinates. Browser Use is the Python/MIT agent layer for requests that are genuinely open-ended, such as “find the latest issue and summarise it.” Brave is Chromium-based, so it is practical to launch it with a chosen profile or remote-debugging connection.

Use for: “open Brave and search…”, website navigation, forms, extraction, and web-task fallback.

UI-TARS Desktop

Most directly aligned with the request: a local, multimodal desktop agent stack that observes a screen and executes mouse/keyboard actions. It is cross-platform and actively maintained. Treat it as a separately launched, opt-in “visual control” capability—not a silent background authority.

Use for: unfamiliar desktop UIs where no accessibility/API route exists.

Recommended Mumble architecture

spoken command
  → existing Mumble STT / LLM intent extraction
  → CommandPlan { action, target, arguments, risk, confirmation_required }
  → policy + allow-list + preview
  ├─ direct app/URL action       → Windows launcher / pywinauto
  ├─ structured web task         → Playwright
  ├─ open-ended browser request  → Browser Use (isolated browser profile)
  ├─ saved repeated routine      → OpenAdapt workflow
  └─ unfamiliar screen           → UI-TARS Desktop, visible + opt-in
  → activity log + result spoken/displayed by Mumble

For “Open Brave and search open-source GUI agents”, the normal route should not invoke an AI GUI agent at all: resolve the approved Brave executable, percent-encode the query, launch https://search.brave.com/search?q=…, then report success. The visual fallback is for a task such as “configure an obscure setting in this app,” after Mumble has shown the plan and received confirmation.

Permission model to ship before autonomy

  • Low risk: launch/focus approved apps; open a search URL.
  • Medium risk: type into a form; change a local setting; download a file—show a plan and allow one-task approval.
  • High risk: submit, purchase, delete, send messages, change credentials, use a password manager, or run shell commands—require a fresh confirmation at the final action.
  • Always: an emergency global stop hotkey, an on-screen “agent is controlling…” indicator, a per-step activity log, timeouts, and a separate non-admin agent process.

Why the router matters

  • Most useful commands need no model after the intent is known.
  • Direct tools can report exact success/failure; screenshot agents often cannot.
  • An allow-list prevents a webpage or prompt injection from becoming arbitrary desktop authority.
  • It keeps Mumble’s privacy promise: local commands and local logs by default, isolated browser profiles for web agents.

Useful additions for Mumble beyond computer control

Apache-2.0

openWakeWord

Local wake-word/phrase detection. This can make command mode hands-free without continuously sending audio away. Start with push-to-talk as the safer default; wake words should visibly indicate when Mumble is listening.

Apache-2.0MIT

Vosk and whisper.cpp

Offline speech options. Mumble already ships faster-whisper, so neither is required for general dictation. Vosk may be useful for a tiny, fixed command grammar; whisper.cpp is useful only if a native/C++ distribution route becomes desirable.

Saved voice routines

Combine Mumble intent extraction with OpenAdapt recordings: “run my expense-report routine.” This is a much better UX than repeatedly letting a visual agent re-plan a known workflow.

Automation history and replay

Create a new Deck source type for command plans and results: original words, parsed intent, tools invoked, screenshots/steps (when consented), result, and a one-click “run again.” This is the product feature I would prioritise after basic control.

Practical rollout

  1. Phase 1 — safe deterministic commands: add a local command mode with a small JSON schema. Ship only app launch, Brave search/open URL, window focus, and clipboard/search actions. Implement allow-lists and confirmation UI first.
  2. Phase 2 — browser tasks: run Playwright in an isolated profile. Add Browser Use behind an “AI web task” toggle, domain restrictions, visible progress, and final-step confirmation for submitting/sending.
  3. Phase 3 — Windows controls and routines: add pywinauto skills for the apps Mumble users actually ask for; add record-and-replay/saved routines using OpenAdapt concepts.
  4. Phase 4 — visual fallback: evaluate UI-TARS Desktop in a disposable Windows profile/VM. Only graduate it if it succeeds on a Mumble-owned evaluation set and can be stopped immediately.

Licensing conclusion: the recommended core—pywinauto (BSD-3-Clause), Playwright (Apache-2.0), Browser Use (MIT), UI-TARS Desktop (Apache-2.0), OpenAdapt (MIT), and openWakeWord (Apache-2.0)—is compatible in principle with Mumble’s MIT distribution, subject to retaining notices and verifying each dependency/model’s current terms at the version you ship. Do not treat a repository licence as automatically covering hosted models, checkpoints, or bundled weights.

Community signal and caveats

Community search surfaced substantial interest in local desktop agents, especially UI-TARS. An X walkthrough describes natural-language desktop actions and local processing, while a discussion reply cautions that a 7B local model may be insufficient for complex computer-control tasks. Treat both as anecdotal—not benchmark proof. Reddit searches surfaced multiple active “control my computer” and open-agent discussions, but Reddit’s current page/API access did not return stable thread text for reliable quotation; this report therefore does not rely on Reddit comments for technical claims.

The important product conclusion is unchanged: visual agents are compelling, but a Mumble user asking for an ordinary task should get a direct, reversible tool action whenever one exists.
