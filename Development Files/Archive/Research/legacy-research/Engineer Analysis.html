Workflow Engineering Analysis

Engineer Analysis

◆Question: would adopting the How I Engineer workflow meaningfully improve how Mumble is built?
◆Source studied: github.com/AnasInno/how-i-engineer (cloned & read in full)
◆Compared against: Mumble's own doctrine (the four core docs) + the live toolchain — Claude Code, Factory, Mission Control
◆Date: 2026-06-28 · Verdict: adopt selectively (see §8)
In plain terms

Someone published a public "kit" that shows how they ship AI-built software with discipline — turn a conversation into a tight brief, build the smallest useful slice, prove it with real evidence, and only then call it done. This document studies that kit, lines it up against how we already build Mumble and the tools we already use (Claude Code, Factory, and Factory's Mission Control), and answers a practical question: is any of it worth adopting, and if so, exactly which parts and how?

Short answer: yes — but only the parts we're actually missing. Mumble is already strong on discipline (the four core docs, the completion checklist, the honesty bar) and on mechanical testing. The two real gaps are (1) we never measure whether the AI output is actually good — only that the code runs — and (2) we have no separate "did we overbuild / did our claims match the evidence?" review. How I Engineer targets exactly those two gaps, cheaply. The orchestration it describes, Mission Control already does better. So we adopt the proof discipline, feed it to Mission Control, and skip the rest.

1How the workflow operates

In plain terms

How I Engineer isn't an app or a bot — it's a repository of operating procedures that any AI coding agent can load and follow. It encodes one belief: an AI demo that "said something plausible" is worthless; the work only counts when there's less human work left afterwards and the result is proven. Everything in it exists to push a change from a vague idea to a merge you can trust, without lying to yourself along the way.

The whole thing is one pipeline, and it is deliberately conversation-first:

conversation → tight brief → smallest slice → orchestrator (if needed)
            → build → eval → autoreview → proof → PR → CI/CD → merge

1.1 The shape of the loop

1
Problem conversation

Before any agent is launched, pin down the real job: who is stuck, what they do by hand today, what input they already have, what output changes their next action, what the system must never do automatically, and what proof would make the result trustworthy. The useful slice appears here, not in the code.

2
Tight brief

The conversation is written into a one-page brief (templates/automation-brief.md): mission, user, input, output, deterministic core, optional AI layer, safety boundaries, smoke test, worker plan, proof ladder, limits. A brief that's still vague is rejected before code exists.

3
Smallest slice, deterministic first

Build the smallest coherent thing that produces useful output and can be proved — one persona, one input shape, one output format, one smoke command, one proof standard. Plain code does the parsing/scoring/transforming; AI is added only where judgement, extraction, ranking, rewriting, or critique genuinely improves the result.

4
Eval — only where quality matters

If the change touches output quality, model routing, confidence, or fallback, run a scenario-pack eval with a weighted rubric and fatal safety gates. This is where "the output exists" becomes "useful enough / needs repair / needs human judgement." A green smoke test is explicitly not quality proof.

5
Autoreview — a separate skeptic

A distinct review pass challenges the artifact against the brief: scope creep, unused abstractions, broad integrations, AI where deterministic logic was enough, and proof claims that outrun the evidence. The reviewer is allowed to recommend deleting work. Smaller-that-fits beats larger-that-impresses.

6
Proof, then PR / CI/CD / merge

Each claim names the surface it was proved on (the evidence ladder, below). Work can be messy locally; the PR cannot. Merge only when claims match recorded evidence.

1.2 The doctrine that drives it (the kernel)

One always-loaded file, codex/how-i-engineer/KERNEL.md, is the compact operating doctrine every agent reads. Five ideas do the work:

  • The promise. "The work only counts if less useful human work exists afterwards." Process narration, agent theatre, and one nice output don't qualify.
  • Truth model. Current files beat old docs. History/routing docs are for navigation; the live checkout, git status, tests, generated outputs, and recorded proof are what's true now. Don't write stale "current state" docs — inspect the repo directly.
  • Autonomy boundary. Local autonomy is high (code, docs, tests, fixtures, local proof); external autonomy is low (sending email, writing CRMs, posting publicly, mutating live systems, touching real customer data, publishing secrets all stop for approval).
  • Slice rule + autoreview rule. Build the smallest provable thing; review non-trivial work separately before calling it ready.
  • Evidence ladder + closeout labels. Never let one layer of proof stand in for another, and end every job with an honest verdict.
Detail The evidence ladder (11 rungs) and the four closeout labels

Proof is ranked so a weak layer can't masquerade as a strong one:

 1  Code shape ......... files exist, commands documented
 2  CLI smoke .......... sample input → sample output
 3  Tests .............. behaviour + failure paths checked
 4  Eval scorecard ..... scenario pack + rubric + quality verdict
 5  Output quality ..... a human inspected usefulness
 6  Browser proof ...... the visible web path was actually run + recorded
 7  Computer proof ..... the desktop/OS path was actually run + recorded
 8  Tool readiness ..... required tools verified before trusting the run
 9  Crabbox proof ...... isolated remote run evidence collected
10  Autoreview ......... brief-fit / minimality / claims / safety reviewed
11  PR/ship safety ..... no secrets, private paths, junk, unsafe live actions

Weak proof ("it builds", "the model answered", "file exists", "browser opened" without a completed path) is named and rejected. Closeout labels, exactly one per job: fail · needs repair · needs judgement · merge candidate. "Exited zero" is never "ready"; ready = the proof matches the risk.

1.3 How an agent actually loads it (routing)

This is the technically interesting part, and the part that makes it portable. The repo is an agent-operable kit, not a prompt dump:

AGENTS.md  (root router)
   └─ codex/how-i-engineer/LOAD-FIRST.md   "keep startup light"
        └─ KERNEL.md                       always-loaded doctrine
        └─ pick ONE skill from .agents/skills/
        └─ load a topic doc only when the skill routes you there

"Do not load the whole repo as startup context" is an explicit instruction. An agent reads the router, the kernel, and one small skill — then inspects only the live files that matter. Eight skills cover the lanes:

Skill (.agents/skills/…)When it fires
conversation-briefthe ask is still fuzzy → turn talk into a buildable brief
workflow-shipbuild/customise one small automation from a clear brief
orchestratorthe work genuinely splits into independent worker lanes
eval-frameworkoutput quality / routing / confidence is part of the claim
autoreviewindependent review of a build or merge candidate
real-user-qaa visible browser / desktop path a real user would touch
crabbox-proofproof needs an isolated remote box, not the laptop
pr-ship-safetybefore submitting / merging / presenting anything public

Each skill is a Markdown file with YAML front-matter (name + description) — the same shape Claude Code skills and Factory skills use. That is why the kit drops into either tool almost verbatim (§3, §5).

1.4 The orchestrator / worker model

When work splits, an orchestrator owns the judgement (smallest slice, which lanes, allowed data, forbidden actions, what proof is required) and hands each worker exactly one objective, one allowed scope, one proof expectation, via a worker-brief contract. Lanes: research, builder, eval, autoreview, QA, browser, computer, Crabbox, PR/ship. The orchestrator reads worker output critically — "looks good" without proof is rejected — and integrates in an intentional order. Crucially, the repo warns against "pretending internal subagents are real independent worker owners": the model is only worth it when the work truly crosses lanes, never for tiny edits where coordination costs more than the work.

1.5 The eval spine (the most transferable idea)

In plain terms

This is the piece most teams don't have and the piece worth stealing. Instead of trusting that an AI feature "seems fine," you write a small pack of realistic scenarios (including the ones that should fail), score each candidate against a weighted rubric where some failures are fatal no matter how high the average, and get a scorecard that tells you which strategy to ship — or that the honest answer is "needs a human."

The public shape is deterministic and runnable: scenario pack → candidate outputs → rubric → deterministic scorer → scorecard → merge judgement. The reference harness (examples/teachclaw-scrubbed-eval-harness) is real working Python, not pseudocode — it validates that rubric weights sum to 1.0, that every scenario×strategy pair is scored, applies fatal gates, and emits both JSON (for machines) and Markdown (for humans).

Detail What the reference scorecard actually proves

Two strategies over three scenarios. The numbers make the judgement visible:

StrategyAvgFatal failsVerdict
Single-pass draft3.111 (forced confidence on thin evidence)not_ready
Draft + checker + targeted repair4.540recommended_with_review_gate

The thin-evidence-marking-feedback scenario fails the single-pass strategy outright on a safety_boundary gate — "confidence forced despite thin evidence; missing uncertainty flag" — even though its average looked passable. That is the whole point: a high average must not hide a safety failure, and "mechanically sound but still needs judgement" is a legitimate, honestly-labelled outcome (needs_judgement), not a forced green.

1.6 Deterministic enforcement — what stops it being just nice prose

Three small Python scripts and a Makefile turn the doctrine into gates that actually run:

  • scripts/repo_doctor.py — asserts the kit's own structure: every required file exists, AGENTS.md routes to LOAD-FIRST.md, every skill has front-matter and is routed. Self-checking docs.
  • scripts/public_safety_check.py — a real regex scanner for secrets (sk-…, AIza…, ghp_…), local absolute paths, private-workspace markers, and accidental binary/zip/log artifacts, with code-plumbing allow-lists so os.environ.get(...) doesn't false-positive.
  • make check = doctor + smoke + test + safety, run identically by the developer and by GitHub Actions on every push/PR. The CLI is the source of truth; CI just re-runs it.

Practical character. Running it feels less like "an agent did magic" and more like a calm release checklist: the conversation forces clarity, the slice rule keeps it small, the eval refuses false confidence, the autoreview deletes the cruft, and every claim has to point at a named proof surface. It is slower per change than "just vibe it" — and far less likely to ship something that only looked done.

2Comparison against our current workflow

In plain terms

Two comparisons matter. First, against our own engineering doctrine — the rules already written into Mumble's four core docs (this is "our Engineer Analysis process"). Second, against the tools we actually run — Claude Code, Factory, and Mission Control. The headline: we already do a surprising amount of what How I Engineer preaches, but we do it as prose habits, not as enforced gates — and we're missing its two sharpest tools entirely.

3Integration with Mission Control

In plain terms

Mission Control already is an orchestrator-with-workers. So the How I Engineer orchestration chapter is, for us, mostly redundant — Factory does that part for real (actual parallel agent sessions, git handoffs, automatic recovery) where the kit only describes the pattern in prose. The win is the other direction: Mission Control runs the machine; How I Engineer makes the machine's agents disciplined and honest. We don't reimplement orchestration — we feed Mission Control the doctrine and the proof gates it doesn't ship with.

3.1 What Mission Control already provides

Confirmed against Factory's documentation and launch material:

  • An orchestrator that decomposes a goal into features/milestones and steers execution to completion through validation gates.
  • Fresh worker sessions per feature with clean context (no single session holds the whole project), coordinated through git handoffs.
  • Milestone validation — workers review accumulated work, run tests, check regressions, verify integration.
  • User-facing QA run against the app to validate each feature and self-correct; automatic failure recovery.
  • Runs are long and real: median ≈ 2 hours, a third run > 4 hours.
  • It loads project steering from AGENTS.md, plus custom droids (.factory/droids/), skills (.factory/skills/), hooks, and MCP.

3.3 How to actually wire them together

Because Mission Control reads AGENTS.md, .factory/skills/, and .factory/droids/, integration is configuration, not engineering:

  1. Doctrine into AGENTS.md. Put the kernel essentials (slice rule, autonomy boundary, truth model, evidence ladder, closeout labels) where every Mission worker loads them. For Mumble this largely means pointing AGENTS.md at the existing core docs and adding the few missing primitives (§5).
  2. Lanes into custom droids. Author an eval droid and an autoreview droid (and optionally a safety droid) in .factory/droids/. These are precisely the milestone-validation steps Mission Control doesn't ship by default — they slot in as extra validation lanes.
  3. Skills into .factory/skills/. Drop the adapted conversation-brief, eval-framework, and autoreview skills so any droid can invoke them.
  4. Evals as a milestone gate. Make "AI-lane eval scorecard is green (no fatal gate)" a defined exit criterion for any milestone that changes the Big Shift, the prompt constitution, or routing — alongside the tests Mission Control already runs.

Net effect: Mission Control keeps doing the heavy autonomous lifting (the 2-hour, multi-feature, port-spanning jobs), but now its workers brief before building, refuse to overbuild, prove AI quality with a scorecard, and label their claims by proof surface.

4Integration into chat-based development

In plain terms

Most Mumble work isn't a dedicated multi-hour engineering mission — it's an ordinary chat: "fix this island artifact," "tune the mode inference," "add PDF import to the Reader." The full ceremony would be overkill there. The trick is a lightweight version that costs almost nothing per turn and folds straight into the completion checklist we already write.

The kit itself says use one skill by default and don't orchestrate tiny edits — so the chat-scale adoption is just four habits, three of which we already half-do:

  1. A 30-second brief, in your head or one line. Before editing: who's this for, what's the input, what's the output, what must it never do. For Mumble that's usually one sentence; it stops "fixed the wrong thing" before it starts.
  2. Deterministic before AI. Already our default — keep choosing a rule in formatting.py over a model call when a rule suffices.
  3. Name the proof surface when you claim done. Extend the §8 completion line from "✓ Feature A" to "✓ Feature A — proof: offline test + manual island render." This is the single cheapest, highest-trust change: it makes the existing honesty bar visible and kills accidental overclaiming.
  4. One autoreview question before sign-off. "Did this stay in the smallest slice, and do my claims match the evidence?" Thirty seconds; catches scope creep and the "live-verified" claims that were really only compiled.

Concrete proposal: add two optional lines to the README §8 completion checklist — a Proof surface line (which evidence ladder rung backs each ✓) and a Minimality/autoreview line (one sentence: what was deliberately not built). Scale them to the work: a one-line fix gets a one-line proof; a Big Shift change gets a scorecard reference. Nothing else about how we chat needs to change.

5Recommended architecture for Mumble

In plain terms

Don't copy the repo's folder layout, and don't adopt the parts built for publishing a public teaching repo. Instead, take four layers — doctrine, skills, execution, proof — express them in Mumble's existing idiom (HTML core docs, the completion checklist, the offline test loop), and wire the deterministic ones into the verify step we already run.

5.1 The four layers, mapped to this repo

Doctrine layer

Lives in: the four core docs (already our constitution) + a thin AGENTS.md at the repo root that points agents at them.

Add: the evidence ladder vocabulary, closeout labels, and an explicit autoreview/minimality rule — grafted into README §8 and HANDBOOK §5/§7, not a new doc.

Skills layer

Lives in: .claude/skills/ (Claude Code) and/or .factory/skills/ (Factory) — same front-matter shape.

Adopt 5: conversation-brief, workflow-ship, orchestrator, autoreview, eval-framework. Plus a Mumble-tuned real-user-qa for the island/mic/port live checks.

Execution layer

Mission Control for big autonomous multi-surface jobs (local-LLM lane end-to-end; port parity; the stale-zip rebuild). Claude Code for surgical/interactive work. Both obey the doctrine + skills above.

Proof layer

Lives in: the existing verify loop + a new Internal/app/evals/. Mechanical rungs stay (pytest/flake8/compileall); add an AI-lane eval harness and a light secret scanner, runnable as one command and (optionally) in CI.

6Phased implementation plan

In plain terms

If we adopt, do it in small reversible steps, cheapest-and-highest-trust first. Each phase ships something usable on its own — nothing here is a big-bang rewrite, and you can stop after any phase and still be better off.

0
Doctrine graft · ~½ day

Edit README §8 + HANDBOOK §5/§7 (HTML, in place): add the evidence ladder, closeout labels, the minimality/autoreview rule, and two new completion-checklist lines (Proof surface, Minimality). Add a thin root AGENTS.md that routes agents to the four core docs. Output: the honesty bar becomes named and enforceable. Zero code risk.

1
AI-lane eval harness · ~1–2 days highest value

Create Internal/app/evals/: a fixture scenario pack (dictation→shape; mode routing; foreign-boost decisions; prompt-constitution structure; list lead-in preservation), a weighted rubric with a fatal privacy/honesty gate (e.g. any audio-egress or depicted-but-not-real implication = fatal), a deterministic scorer, and a Markdown+JSON scorecard. Offline-first (no key). Wire eval into the verify loop. Output: first real measurement of Big Shift quality.

2
Deterministic gates · ~½ day

Add a secret/leak scanner (adapted regexes, Mumble-tuned) and an optional core-docs doctor to the verify step; optionally a GitHub Action mirroring it. Output: invariant #2 enforced by a machine, not just discipline.

3
Skills + droids pack · ~½–1 day

Adapt 5–6 skills into .claude/skills/ and .factory/skills/; author matching eval / autoreview / orchestrator custom droids in .factory/droids/. Output: Claude Code and Mission Control load the same operating procedures.

4
Run a real mission through it · ongoing

Drive one genuine multi-surface job (e.g. wire the local-LLM lane end-to-end across Windows + both ports, or the stale-Mumble.zip rebuild) through Mission Control with the eval + autoreview lanes as milestone gates. Output: the workflow proves itself on real Mumble work, or we learn precisely where it doesn't fit.

Total to full adoption: ~3–4 focused days, front-loaded so the highest-trust wins (Phases 0–1) land first and the rest is optional polish.

7Practical engineering evaluation

In plain terms

A blunt scorecard across the dimensions that decide whether a workflow is worth its overhead — judged for this project, not in the abstract.

DimensionAssessment for Mumble
Implementation complexityLow for the parts we'd adopt. The eval harness is ~1 deterministic Python file + JSON fixtures; the doctrine graft is doc edits; skills are Markdown. No new runtime dependency, no architecture change.
Setup effort~½ day to value (Phase 0); ~3–4 days to full adoption. Front-loaded so trust arrives early.
Maintenance burdenMostly the eval scenario packs — they need updating as the AI lanes evolve. That cost is proportional to how much you trust those lanes (for the Big Shift: worth it). Everything else is near-zero maintenance.
ScalabilityScales down gracefully (one-line proof for a one-line fix) and up cleanly (scenario packs grow; Mission Control handles parallel lanes). The "one skill by default, orchestrate only when work crosses lanes" rule prevents ceremony creep.
Workflow improvementMeaningful: closes the two real gaps (quality proof, anti-overengineering review) without disrupting what already works.
ProductivitySlightly slower per change; faster across a release, because less time is lost to rework from shipping something that only looked done, and to debating "is this good?" with no measurement.
Code-quality improvementIndirect but real: the minimality gate fights the overbuild that bloats a codebase, and deterministic-first keeps logic testable rather than hidden in prompts.
Debugging advantagesStrong. A scorecard that says which scenario regressed on which rubric dimension turns "the AI feels worse" into a located, reproducible failure — far better than today's "tests pass but mode inference seems off."

Collaboration benefitsFor a solo-owner + AI project the main win is agent-to-agent handoff: a Mission Control worker and a Claude Code session reading the same skills behave consistently. Lower value than for a human team, but not zero.

Where it excelsExactly Mumble's risky surfaces: the Big Shift inference, the prompt constitution, foreign-mode decisions, provider routing/fallback, and any future local-LLM swap — all quality-sensitive, all currently unmeasured.

8Final recommendation

In plain terms

Adopt the discipline, not the repository. Take three things — the AI-lane eval harness, the autoreview pass, and the evidence-ladder vocabulary in the completion checklist — express them in Mumble's existing HTML-docs idiom, and feed that same doctrine to Mission Control's workers. Skip the orchestration prose (Mission Control wins it), the remote-proof box (we run locally), and the public-repo scrub ceremony (we ship a closed product).

The reasoning, in one breath

Mumble is an unusual case: it is already strong where most AI-built projects are weak — a real doctrine (four core docs), a strict completion checklist, an explicit honesty bar, deterministic-first design, and a mature offline test suite. So the question isn't "do we need discipline?" (we have it) but "what discipline are we missing?" The answer is precise and small:

  1. We never measure AI output quality. Our tests prove the code runs; nothing proves the Big Shift inferred the right shape, the constitution wrote a good prompt, or foreign-boost made the right call. How I Engineer's eval spine is the missing instrument, and it's cheap because the scorer is deterministic and offline-first.
  2. We have no separate skeptic. "Smallest change" and "no depicted-but-not-real" are principles we hold but never independently check. An autoreview pass with authority to delete makes overbuild and overclaim visible before sign-off.
  3. Our proof is unnamed. "Verified" doesn't say how. The evidence ladder + closeout labels make every claim point at a surface — turning the honesty bar from a value into a gate, at the cost of two checklist lines.

Everything else in the kit is either already ours (briefs, slice rule, autonomy boundary, deterministic-first), better served by a tool we already run (orchestration → Mission Control), or solving a problem we don't have (publishing scrubbed public examples; remote proof for a local app). Adopting it wholesale would import ceremony for no gain; adopting these three pieces closes the exact gaps at ~3–4 days of work, front-loaded so the trust arrives on day one.
