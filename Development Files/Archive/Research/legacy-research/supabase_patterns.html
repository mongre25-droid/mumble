In plain terms

Supabase is a hosted database (Postgres) with a friendly Python library wrapped around it. This doc is a field guide for using that library: how to connect, how to sign users in, how to read and write rows, how to lock data down so each user only sees their own, how to get live updates when something changes, and how to keep everything in sync when the app goes offline and comes back.

Most of the page is real code and SQL. Each chunk is tucked inside a collapsible "Code" panel so you can skim the plain-English explanation first and only open the technical detail when you need it. Nothing has been removed — every snippet, table, and caveat from the research is here.

This is a research summary of the current Supabase Python client (supabase-py, package name supabase on PyPI, "Python Reference v2.0") as of mid-2026. Official Supabase docs were fetched 2026-06-23. Some doc pages scrape tabbed code examples incompletely; where the official Python snippet was not captured, the equivalent JS snippet from the same guide is shown alongside the documented Python method name. The Python API mirrors the JS API (supabase.channel(...).on_postgres_changes(...).subscribe(...)).

1Install and Initialize

In plain terms

First you install one Python package. It quietly pulls in everything Supabase needs — auth, the data layer, realtime, and file storage — so you don't manage those separately. Then you create a "client" object using your project's web address and an access key, and that object is your handle for talking to the database.

There are two flavours of client: a plain one for normal reads and writes, and an async one you must use if you want live updates (subscriptions), because those run on an event loop.

Install

One pip install gets the whole stack (requires Python > 3.8).

Code pip install 
pip install supabase        # Python > 3.8

The supabase distribution bundles supabase-py, gotrue (auth), postgrest-py, realtime-py, and storage-py.

Enable Data API access (one-time per project)

supabase-py talks to Postgres through the Data API. Before any table is reachable, you must expose it once: either flip it on in the Dashboard (Data API integrations settings), or grant the right permissions in SQL — but only after Row-Level Security and its policies are in place, so you don't briefly expose unprotected rows.

Code SQL — grant Data API access (after RLS) 
alter table public.your_table enable row level security;
-- create policy ... on public.your_table ...;

grant select on public.your_table to anon;
grant select, insert, update, delete on public.your_table to authenticated;
grant all on public.your_table to service_role;

grant execute on function public.your_function to authenticated, service_role;

Initialize (sync client)

For ordinary apps, read the project URL and key from environment variables and create a client. Use the anon / publishable key for client-side apps — never the service role key (see section 8).

Code Python — sync client 
import os
from supabase import create_client, Client

url: str = os.environ.get("SUPABASE_URL")
key: str = os.environ.get("SUPABASE_KEY")   # anon/publishable key for client apps
supabase: Client = create_client(url, key)

Initialize (async client — required for realtime subscriptions)

The async client is what you need whenever you call .subscribe() on a channel, because subscription callbacks run in an event loop. Use asyncio.create_task() to schedule coroutines from inside a sync callback.

Code Python — async client 
import asyncio, os
from supabase import acreate_client, AsyncClient

async def create_supabase() -> AsyncClient:
    url = os.environ.get("SUPABASE_URL")
    key = os.environ.get("SUPABASE_KEY")
    supabase: AsyncClient = await acreate_client(url, key)
    return supabase

ClientOptions

You can pass an options object — create_client(url, key, options=ClientOptions(...)) — to change auth behaviour. The notable knobs:

  • auto_refresh_token (default True) — refresh the JWT before it expires.
  • persist_session (default True) — store the session (in-memory in the Python client; supply a custom storage object to persist to disk/keyring).
  • storage — a custom storage adapter implementing get_item / set_item / remove_item (sync or async). For a desktop app, point this at a local file or OS keyring so the session survives restarts.
  • postgrest_client_timeout — request timeout (e.g. ClientOptions(postgrest_client_timeout=30)).

2Authentication

In plain terms

Everything about users — signing up, logging in, logging out, and knowing who is currently signed in — lives under supabase.auth. When someone logs in they get a short-lived "access token" (a JWT, the badge that proves who they are) and a longer-lived "refresh token" used to get a fresh badge when the old one expires.

Two safety facts to remember: the access token expires (default 1 hour), and the refresh token can only be used once. If you reuse an old refresh token you'll invalidate the whole session, so always store only the newest pair.

All auth methods live on supabase.auth. Key behaviours:

  • persist_session=True by default; the session is held in memory (or your custom storage).
  • Email links/OTPs expire after 24h by default.
  • Access token (JWT) lifetime is configurable (default 1h) in Dashboard → JWT settings.
  • A refresh token never expires but can only be used once (with a 10s reuse window).

Sign up (register) with email + password

Register a new account. If Confirm email is enabled (the default), session is None until the user clicks the email link; if disabled, you get both user and session immediately. You can pass options: {"email_redirect_url": ..., "data": {...user_metadata...}}.

Code Python — sign_up 
response = supabase.auth.sign_up({
    "email": "user@example.com",
    "password": "strong-password",
})
# response.user, response.session

Sign in (login) with email + password

Log an existing user in; the session is persisted automatically.

Code Python — sign_in_with_password 
response = supabase.auth.sign_in_with_password({
    "email": "user@example.com",
    "password": "strong-password",
})
# response.user, response.session  -> session persisted automatically

Get / refresh the session

There's an important trust distinction here: get_session() only reads what's in local storage, so you must not trust it server-side. For verified user data on a server, call get_user() (which hits the Auth server) or get_user(jwt=...) to verify a specific JWT against the JWKS endpoint. refresh_session() exchanges the refresh token for a new access token.

Code Python — get/refresh session 
session = supabase.auth.get_session()      # local session from storage/memory (untrusted on server)
user     = supabase.auth.get_user()        # verified user from Auth server (use on server)
session  = supabase.auth.refresh_session() # exchange refresh token for a new access token

Restore a session from stored tokens

Useful after restarting the app: load tokens from your custom storage and call set_session to hydrate the client.

Code Python — set_session 
supabase.auth.set_session(access_token, refresh_token)

Sign out

By default sign-out uses scope="global", which revokes all the user's sessions. Pass scope="local" to sign out only the current device.

Code Python — sign_out 
supabase.auth.sign_out()   # default scope="global" revokes all the user's sessions
# supabase.auth.sign_out({"scope": "local"})  # only this device

Listen for auth state changes

Register a callback that fires on events like "SIGNED_IN", "SIGNED_OUT", and "TOKEN_REFRESHED". Use this to drive UI state and to trigger a sync push/pull when the user signs in.

Code Python — on_auth_state_change 
def on_auth_event(event, session):
    print(event, session)   # e.g. "SIGNED_IN", "SIGNED_OUT", "TOKEN_REFRESHED"

supabase.auth.on_auth_state_change(on_auth_event)

Token refresh strategy (for local-first apps)

  • The client auto-refreshes before the JWT expires when auto_refresh_token=True.
  • For long-running desktop processes, persist the latest access_token + refresh_token to your storage adapter on every TOKEN_REFRESHED event so a restart can call set_session.
  • Refresh tokens are single-use (with a 10s reuse grace window); do not cache an old refresh token and reuse it later — you'll invalidate the whole session.

3CRUD Operations

In plain terms

CRUD is the four basic things you do with data: Create, Read, Update, Delete. With this library you build each request like a sentence: pick a table, choose an operation, add filters that narrow down which rows, then call execute() to actually run it. The result hands you back the rows (.data) and optionally a count.

The one rule that prevents accidents: always attach a filter to updates and deletes, otherwise the operation hits every matching row.

All data access is builder-style: supabase.table(name).<op>().<filter>().execute(). execute() returns an object with .data and .count.

Insert

Add one row, many rows at once, or insert and return only specific columns.

Code Python — insert 
# single row
resp = supabase.table("notes").insert({"id": 1, "title": "Hello"}).execute()

# bulk
resp = supabase.table("notes").insert([
    {"id": 1, "title": "A"},
    {"id": 2, "title": "B"},
]).execute()

# return only specific columns
resp = supabase.table("notes").insert({"id": 3, "title": "C"}).select("id, title").execute()

Options: count="exact"|"planned"|"estimated", returning="minimal"|"representation", default_to_null=False (use column defaults instead of NULL for bulk inserts).

Select (with filters)

Read rows, narrowing with filters and shaping the result with modifiers. Order matters: the filter chain must come after select() and before modifiers (order, range, limit, single, maybe_single, csv).

Code Python — select with filters 
resp = (
    supabase.table("notes")
    .select("*")
    .eq("user_id", uid)
    .order("updated_at", desc=True)
    .limit(50)
    .execute()
)

Common filters:

MethodMeaning
.eq(col, v) / .neqequal / not equal
.gt / .gte / .lt / .ltecomparisons
.like(col, "%pat%") / .ilikecase (in)sensitive LIKE
.is_(col, "null")IS NULL / TRUE / FALSE
.in_(col, [a, b])IN array
.contains(col, [...]) / .contained_byarray/jsonb/range
.overlaps(col, [...])array/range overlap
.match({"k": v, ...})shorthand multi .eq
.or_("id.eq.2,name.eq.Mars")OR (PostgREST raw syntax)
.not_.is_(col, "null")negate
.filter("col", "in", '("a","b")')raw PostgREST
.text_search(col, "'eggs' & 'ham'", options={"config":"english"})FTS

Modifiers: .order(col, desc=True, nullsfirst=False), .limit(n), .range(start, end) (0-based inclusive), .single() (returns one object, errors if 0 or many), .maybe_single() (returns one or None), .csv().

Default row cap is 1,000 per request; paginate with .range().

Update

Always pair update() with a filter (otherwise all matching rows update). For last-write-wins sync, also add .lte("updated_at", incoming_ts) so a stale local write doesn't overwrite a newer server value.

Code Python — update 
resp = (
    supabase.table("notes")
    .update({"title": "edited", "updated_at": "2026-06-23T12:00:00Z"})
    .eq("id", 1)
    .execute()
)

Upsert

Upsert = insert if new, update if it already exists. The primary key must be included. You can do it in bulk, ignore duplicates, and tell it which column(s) define a conflict.

Code Python — upsert 
# PK must be included
resp = supabase.table("notes").upsert({"id": 1, "title": "x"}).execute()

# bulk, ignore duplicates, conflict target
resp = (
    supabase.table("notes")
    .upsert(rows, on_conflict="id", ignore_duplicates=True)
    .execute()
)

Options: on_conflict (column(s) for the UNIQUE constraint resolution), ignore_duplicates=True, default_to_null.

Delete

Delete by id or by a set of ids. Note: with RLS on, only rows visible through a SELECT/ALL policy are deletable, so you need at least a SELECT policy on the table.

Code Python — delete 
resp = supabase.table("notes").delete().eq("id", 1).execute()
resp = supabase.table("notes").delete().in_("id", [1, 2, 3]).execute()

RPC (call a Postgres function)

RPC runs a function you've defined inside the database. Use it for server-side logic that must bypass per-row client filters (e.g. a SECURITY DEFINER sync function).

Code Python — rpc 
resp = supabase.rpc("hello_world").execute()
resp = supabase.rpc("get_notes", {"user_id": uid}).execute()

4Row-Level Security (RLS) Patterns

In plain terms

Row-Level Security is the database's own bouncer. Instead of trusting your app code to filter "show only this user's rows," you write a rule once at the database level, and Postgres silently enforces it on every query as if an invisible WHERE clause were always attached. This is what makes it safe to put a public key in a client app.

The classic pattern: give each table a user_id column, then write four policies (select, insert, update, delete) that all say "the signed-in user must own this row." A handful of correctness rules below keep it both safe and fast.

RLS is mandatory for any table in an exposed schema (public). Enable it, then write policies that act like implicit WHERE clauses.

Enable + grant

Turn RLS on for the table and grant the appropriate roles.

Code SQL — enable + grant 
alter table public.notes enable row level security;

grant select, insert, update, delete on public.notes to authenticated;
grant all on public.notes to service_role;

The canonical "user owns their rows" pattern

Add a user_id uuid references auth.users column to every user-scoped table, then write one policy per operation. For UPDATE, using checks the existing row and with check checks the new row.

Code SQL — owner policies (select / insert / update / delete) 
-- SELECT
create policy "owner select" on public.notes
  for select to authenticated
  using ( (select auth.uid()) = user_id );

-- INSERT
create policy "owner insert" on public.notes
  for insert to authenticated
  with check ( (select auth.uid()) = user_id );

-- UPDATE (using = existing row check; with check = new row check)
create policy "owner update" on public.notes
  for update to authenticated
  using      ( (select auth.uid()) = user_id )
  with check ( (select auth.uid()) = user_id );

-- DELETE
create policy "owner delete" on public.notes
  for delete to authenticated
  using ( (select auth.uid()) = user_id );

Critical correctness rules

  1. Always wrap auth.uid() in (select ...) so Postgres caches it per statement instead of calling it per row (huge perf win).
  2. Guard against null: auth.uid() returns null when unauthenticated, and null = user_id is always false. Prefer using (auth.uid() IS NOT NULL AND (select auth.uid()) = user_id) for clarity.
  3. Specify TO authenticated on every policy so anon requests short-circuit before evaluating the expression.
  4. Add a btree index on user_id for every policy-filtered table.
  5. Always add an explicit .eq("user_id", uid) filter in the client query even though the policy enforces it — Postgres builds a better plan with the explicit filter (94% faster in benchmarks).
  6. UPDATE requires a matching SELECT policy to find the rows.
  7. Views bypass RLS by default; use with (security_invoker = true) (PG15+) so a view runs as the caller and respects underlying policies.

Helper functions

  • auth.uid() — requesting user's id.
  • auth.jwt() — the JWT. Use raw_app_meta_data (not user-editable) for authorization data; raw_user_meta_data is user-editable and unsafe for authz. Remember the JWT may be stale until refreshed.

Service role bypass

The service_role key bypasses RLS entirely. Never ship it in a client app. Use it only server-side for admin/migration/sync operations.

5Real-time Subscriptions

In plain terms

Realtime is the part that lets your app react the instant data changes, instead of polling. You open a "channel" and Supabase pushes you a message whenever a row is inserted, updated, or deleted. There are two ways to get those messages, with a trade-off between simplicity and scale.

The big-picture advice: treat a realtime event as a doorbell, not as the delivered package. When it rings, go do a normal secure read to fetch the trusted data — don't trust the event's contents as the final word. That keeps your security rules in one place.

Realtime is the live-update channel layer (Phoenix Channels under the hood). Two mechanisms:

Broadcast

Recommended for scale/security. A Postgres trigger calls realtime.broadcast_changes('topic:<id>', TG_OP, TG_OP, TG_TABLE_NAME, TG_TABLE_SCHEMA, NEW, OLD) and clients subscribe to a private channel for that topic. Requires a broadcast authorization policy on realtime.messages.

Postgres Changes

Simpler, less scalable. Subscribe directly to WAL (write-ahead log) changes on a table.

Enable Postgres Changes (per project)

You publish the table to the realtime publication. To also receive the old row values on UPDATE/DELETE, set the table's replica identity to full.

Code SQL — enable Postgres Changes 
drop publication if exists supabase_realtime;
create publication supabase_realtime;
alter publication supabase_realtime add table notes;
-- to get old row values on UPDATE/DELETE:
alter table notes replica identity full;
Note: when RLS is on and replica identity full, only the primary key is sent to clients on DELETE (RLS is not applied to delete statements over Realtime).

Python subscribe (async client)

Open a channel, register a callback for the event you care about, then subscribe. The payload's payload["new"] holds the changed row.

Code Python — subscribe to postgres changes 
import asyncio
from supabase import acreate_client, AsyncClient
from supabase.types import RealtimeSubscribeStates

def on_subscribe(status, err):
    if status == RealtimeSubscribeStates.SUBSCRIBED:
        print("subscribed")

def handle_insert(payload):
    print("INSERT", payload)   # payload["new"] has the row

async def main():
    sb = await acreate_client(URL, KEY)
    channel = sb.channel("notes-changes")
    channel.on_postgres_changes(
        {"event": "INSERT", "schema": "public", "table": "notes"},
        callback=handle_insert,
    )
    await channel.subscribe(on_subscribe)

asyncio.run(main())

event may be "INSERT", "UPDATE", "DELETE", or "*" (all). Add a filter (e.g. {"event":"UPDATE","schema":"public","table":"notes","filter":"user_id=eq.<uid>"}) to limit to a user's rows. Chain multiple .on_postgres_changes(...) calls on one channel for different events.

Broadcast (client-to-client / low-latency)

For low-latency, client-to-client messages (like live cursor positions), send and receive broadcast events on a channel.

Code Python — broadcast send/receive 
channel = sb.channel("room1")

def on_subscribe(status, err):
    if status == RealtimeSubscribeStates.SUBSCRIBED:
        asyncio.create_task(channel.send_broadcast("cursor-pos", {"x": 0.5, "y": 0.5}))

def handle_broadcast(payload):
    print("got", payload)

channel.on_broadcast(event="cursor-pos", callback=handle_broadcast)
await channel.subscribe(on_subscribe)

Presence

Attach on_presence_sync(), on_presence_join(), on_presence_leave() callbacks; presence auto-enables when callbacks are attached.

Cleanup

Remove a channel to free it (and its server resources), or list the active channels.

Code Python — channel cleanup 
await sb.remove_channel(channel)   # frees the channel + server resources
channels = sb.get_channels()        # list active channels

Supabase auto-cleans a channel ~30s after the client disconnects.

Relevance to local-first sync

Realtime is best used as a notification signal ("something changed, pull now") rather than a transport for the data itself. For correctness, treat a Realtime event as a trigger to run a select pull (which goes through RLS and returns trusted data), not as authoritative state. This keeps conflict resolution server-side and avoids duplicating RLS logic on the client.

6Best Practices for Local-First / Last-Write-Wins Sync

In plain terms

"Local-first" means the app works offline against a local copy of the data and syncs with the server when it can. "Last-write-wins" (LWW) is the simplest way to settle conflicts: whichever edit has the newest timestamp wins. To make that reliable you design tables a certain way — give every row a stable ID, a timestamp clock, and a "deleted" flag instead of really deleting things.

The flow has three parts: push your offline edits up, pull the server's newer changes down, and merge them locally. The trick that keeps it correct is a database-side guard that refuses any incoming write older than what's already stored — so a stale offline edit can never clobber a newer one.

Table schema for LWW sync

Every syncable table should carry a few standard columns: a client-generated UUID key, the owner's user_id, a deleted soft-delete flag, an updated_at LWW clock, a created_at, and optionally a monotonic client_rev counter.

Code SQL — syncable table schema 
create table notes (
  id          uuid primary key default gen_random_uuid(),
  user_id     uuid not null references auth.users,
  content     text,
  deleted     boolean not null default false,   -- soft delete, never hard-delete on sync
  updated_at  timestamptz not null default now(), -- LWW clock
  created_at  timestamptz not null default now(),
  client_rev  bigint not null default 0          -- optional: monotonic per-client counter
);

alter table notes enable row level security;
create index notes_user_updated_idx on notes (user_id, updated_at desc);

Rules:

  • updated_at is the LWW timestamp. Always set it client-side (UTC ISO-8601) on every mutation and use it as the conflict arbiter.
  • Soft deletes via a deleted flag. Hard deletes break sync because a client that was offline can't distinguish "deleted by another device" from "never existed". Tombstones (deleted=true) sync naturally.
  • Stable primary keys (UUID generated client-side) so an offline insert can be upserted later without collisions.
  • Index (user_id, updated_at desc) for fast incremental pulls.

Push (client → server)

On reconnect, push the local outbox with an upsert plus a server-side guard.

Code Python — push via upsert 
supabase.table("notes").upsert(
    {"id": row_id, "user_id": uid, "content": content,
     "deleted": False, "updated_at": ts},
    on_conflict="id",
).execute()

For true LWW, enforce the arbiter server-side so a stale push can't clobber a newer row. Two options:

  1. Conditional update (client filter): only push if your local updated_at is newer than the server's — but you can't see the server value from the client atomically.
  2. DB-side guard (preferred): a BEFORE INSERT OR UPDATE trigger that rejects the write when NEW.updated_at < OLD.updated_at:
Code SQL — LWW guard trigger 
create or replace function notes_lww_guard()
returns trigger language plpgsql as $$
begin
  if TG_OP = 'UPDATE' and OLD.updated_at > NEW.updated_at then
    -- stale write; keep the newer server row
    return null;
  end if;
  NEW.updated_at := coalesce(NEW.updated_at, now());
  return NEW;
end $$;

create trigger notes_lww before insert or update on notes
  for each row execute function notes_lww_guard();

Or use a single RPC that does the compare-and-swap atomically and returns the winning row so the client can reconcile.

Pull (server → client, incremental)

Pull only the rows that changed since your last sync by filtering on updated_at > last_sync_ts. Track last_sync_ts locally as the max updated_at seen. Page with .range() for large initial pulls. Combine with a Realtime subscription to trigger immediate pulls on change notifications.

Code Python — incremental pull 
resp = (
    supabase.table("notes")
    .select("*")
    .eq("user_id", uid)
    .gt("updated_at", last_sync_ts)   # only changed rows
    .order("updated_at", desc=False)
    .limit(500)
    .execute()
)

Merge locally

For each pulled row: if local updated_at < server, overwrite local; if equal, tie-break by client_rev or id. Because the DB guard already prevented stale pushes, the server row is always the winner, simplifying the client merge.

7Offline Mode and Background Sync

In plain terms

The Supabase Python library is just a thin client — it has no built-in offline queue or conflict resolver. So for a real offline-capable app, you build the sync layer around it. The shape is always the same: a local database the UI reads and writes instantly, an "outbox" listing changes waiting to go up, and background loops that push, pull, and listen for live notifications whenever the network is available.

The numbered architecture below is the recommended blueprint. The key resilience details are about tokens (store only the newest pair, since refresh tokens are single-use) and about backing off gracefully when the network is down.

supabase-py itself is a thin HTTP/WebSocket client — it has no built-in offline queue or conflict resolver. For a local-first desktop/mobile app you build the sync layer around it.

Recommended architecture

1
Local store

SQLite, DuckDB, or JSON files is the source of truth the UI reads/writes. Every write updates updated_at and appends to a local outbox table (pending_changes).

2
Auth restore on startup

Load stored access_token/refresh_token, call supabase.auth.set_session(...). Subscribe to on_auth_state_change to persist refreshed tokens.

3
Connectivity detection

A watchdog loop pings or watches Realtime channel status. When offline, writes only hit the local store + outbox.

4
Push loop (on reconnect)

Drain the outbox with upsert(..., on_conflict="id"), gated by the server-side LWW guard. On success, remove the outbox row; on network error, leave it and retry with backoff.

5
Pull loop

Incremental select(...).gt("updated_at", last_sync_ts), merge into the local store, advance last_sync_ts. Run on (a) app start, (b) Realtime notification, (c) periodic timer.

6
Realtime as a wake signal

Subscribe to postgres_changes for the user's tables; on any event, trigger a pull. Keep the subscription resilient — realtime-py reconnects automatically, but you should re-subscribe after sign_in / token refresh (supabase.realtime.set_auth() equivalent).

7
Background sync

Run the push/pull loops in a background thread/asyncio task with a short interval (e.g. 30s) plus event-driven runs. Guard against concurrent sync runs with a lock.

8
Exponential backoff

On auth/network errors; surface a "sync pending / synced / offline" indicator to the UI.

Token/session resilience across offline

  • Persist tokens to disk/keyring via a custom storage adapter.
  • refresh_session() will fail while offline; catch the error and retry on reconnect.
  • A refresh token is single-use — only persist the latest pair, written on every TOKEN_REFRESHED event, to avoid reuse-detection invalidating the session.

8Anon Key vs Service Role Key

In plain terms

Supabase gives you two keys, and the difference between them is a security cliff edge. The anon key is meant to be public — it's safe to embed in a client app because Row-Level Security still gates every request. The service role key is the master key: it ignores all security rules and can touch every row in every table. It belongs only on servers you control and must never be shipped in an app.

Rule of thumb: client apps get the anon key; trusted server scripts get the service role key. If the service role key ever leaks, rotate it immediately.

Supabase issues two API keys per project. They map to Postgres roles and determine whether RLS is enforced.

KeyPostgres roleRLSSafe to ship in client?
anon / publishable key anon (unauth) → authenticated (after sign-in) ✓ Enforced — policies apply ✓ Yes Designed to be public; security comes from RLS policies.
service role key service_role Bypassed — full table access, ignores all policies No Equivalent to DB admin. Keep server-side only (env var, secrets manager). Never embed in a desktop/mobile/SPA binary.

Rules

  • Initialize the client app with the anon/publishable key. After sign_in_*, the client's requests run as authenticated and RLS policies like (select auth.uid()) = user_id gate access to that user's rows.
  • Use the service role key only in trusted server code (CLI tools, migrations, server-side batch jobs, a sync API you control). Anyone with the service role key can read/write every row in every table regardless of policies.
  • Treat the service role key like a database password: load from environment/secrets, never commit it, never log it, never ship it in a client bundle. If it leaks, rotate it immediately in Dashboard → Project Settings → API.
  • auth.admin.* methods (list_users, get_user_by_id, delete_user, etc.) require the service role key and bypass RLS — use them only server-side.

Practical split for a local-first app

Client process

create_client(URL, ANON_KEY). All user data access goes through RLS; users see only their own rows.

Server/admin script (optional)

For support/migration: create_client(URL, SERVICE_ROLE_KEY) run on infrastructure you control, never on the user's machine.
