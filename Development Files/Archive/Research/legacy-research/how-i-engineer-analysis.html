1What "How I Engineer" actually is

In plain terms

"How I Engineer" is not a framework, not a library, not a product. It is a published operating pattern — a set of habits, file structures, contract templates, and runnable examples that encode one person's method for shipping AI-assisted software without the usual chaos. It was extracted from real product work (a teacher-facing tool called TeachClaw) and scrubbed of private data so others can study, fork, and adapt the pattern.

The central insight is simple but powerful: most failed AI-augmented projects fail not because the model is weak, but because the operating model is weak. Vague briefs, orchestration before understanding, no deterministic baseline, hidden local state, no proof chain, accidental leaks — these are engineering failures, not intelligence failures.

The pipeline in one line

problem conversation → tight brief → smallest slice → orchestrator (if needed) → build → eval → autoreview → proof → PR → CI/CD → merge

2The kernel: six operating principles

The file codex/how-i-engineer/KERNEL.md distills the entire philosophy into six principles. They read like a constitution for agent-assisted engineering:

1. The Promise

"The work only counts if less useful human work exists afterwards."

Every automation must answer: What repeated human workflow gets easier after this ships? Prefer real user pain over impressive agent theatre, useful output over process narration, deterministic baseline over model dependency.

2. The Truth Model

"Current files beat old docs."

Use WORK-DONE.md for history, but inspect the actual checkout, git status, tests, generated outputs, CI/CD checks, and safety scans for what is true now. Never create stale "current state" docs.

3. The Autonomy Boundary

"Local autonomy is high. External autonomy is low."

Agents may act freely on code, docs, tests, fake data, and local proof. They must stop before sending email, writing to CRMs, posting publicly, mutating live systems, scraping private systems, or publishing secrets.

4. The Slice Rule

"Build the smallest coherent version that produces useful output and can be proved."

Smallest coherent = one persona, one input shape, one output format, one smoke command, one clear proof standard. Avoid platform building, broad integrations, and AI as the only source of correctness.

5. The Autoreview Rule

"Non-trivial work gets a separate review pass before it is called ready."

Autoreview checks: brief fit, minimality (did every file earn its place?), proof claims (did the closeout only claim what was actually run?), and safety (no private data leaked). The reviewer may recommend deleting work.

6. The Evidence Ladder

"Do not let one layer stand in for another."

11 distinct proof levels — from "file exists" up to "PR/ship safety scan." Each level must be independently satisfied; a green smoke test does not prove output quality.

Key takeaway: This kernel is not a checklist to be skimmed. It is an operating doctrine — if you violate it, the output may look right but the process will fail at scale. The kernel answers "how do we keep agentic development from becoming a sprawling mess?"

3The agent roles unpacked

The HIE repo models work as a set of bounded worker lanes, each with a narrow job. No worker does everything. This matters because most naive agentic setups collapse all of these into a single giant prompt — which cannot hold itself accountable.

RoleWhat it doesReal-world analogue
Problem Conversation Turns a vague request into a grounded slice: user, pain, input, output, risk, limits, proof Product manager doing discovery
Orchestrator Defines worker lanes, acceptance tests, non-goals, allowed data, and what evidence counts Tech lead / engineering manager
Research Worker Checks workflow reality: what the user currently does, data shape, what a useful output looks like UX researcher / domain expert
Builder Worker Implements the smallest useful CLI or local app — deterministic first, AI only where it improves results Senior engineer
Eval Worker Runs scenario packs, rubrics, pairwise comparisons, scorecards — answers "is the output useful enough?" QA engineer / data scientist
Autoreview Worker Reviews the artifact against the brief: scope creep, overengineering, proof claims, safety Code reviewer / architect
QA Worker Tries to break the artifact: tests, failure modes, docs, .env boundaries, leak-prone files QA / penetration tester
Browser E2E Worker Tests the owner-facing path with real browser tooling: open app, enter input, run, inspect output E2E test engineer
Computer Use Worker Tests OS-level flows: file pickers, PDFs, native dialogs, drag/drop Manual QA / desktop tester
Crabbox Runner Runs isolated proof on a short-lived remote box: hydrate tools, sync tree, run, collect evidence, release CI runner / ephemeral test environment
PR / Ship Worker Creates merge-ready shape: clean git, safety scan, no generated junk, no private history Release engineer
Why this matters: Each lane produces one kind of evidence. The orchestrator is accountable for integrating them. No single agent can credibly claim to have built, tested, reviewed, and safety-checked its own work — the lanes must be separable so the system can challenge itself.

4The proof ladder — why "it builds" is not enough

HIE defines an 11-rung evidence ladder. Each rung is a distinct kind of proof, and no rung can substitute for another. This is perhaps the most transferable concept in the entire repo.

RungProof TypeWhat it actually means
1Code shapeFiles exist and commands are documented
2CLI smokeSample input produces sample output (e.g. make smoke)
3TestsImportant behavior and failure paths are checked
4Eval scorecardScenario pack, rubric, and quality verdict are explicit
5Output qualityA human can inspect whether the output is useful
6Browser proofThe visible local app path was actually run and recorded
7Computer proofThe desktop or OS-level visible path was actually run and recorded
8Tool readinessRequired tools (browser, MCP, CLI, packages) were checked before the run
9Crabbox proofIsolated run evidence was actually collected
10AutoreviewBrief fit, minimality, proof claims, and safety independently checked
11PR/ship safetyNo secrets, private paths, generated junk, or unsafe live actions

The repo is explicit about weak proof — things that sound like evidence but are not: "it builds," "the model answered," "file exists," "browser opened" (without completing the user path), "tool installed" (without the proof command actually using it).

Closeout labels

Every piece of work gets exactly one verdict: fail, needs repair, needs judgement, or merge candidate. Never call a workflow ready just because a command exited zero. Call it ready when the proof matches the risk.

5Mumble's existing development process

In plain terms

Mumble already has a disciplined engineering process — arguably more disciplined than most solo or small-team projects. It has a session ritual, four core living documents, a substantial test suite, a port-sync procedure, and a deploy pipeline. Understanding what Mumble already does is essential before we can talk about what to add.

The session ritual

Every Mumble development session follows a fixed start and end ritual, documented in HANDBOOK §1:

Session start

  1. Read the four core docs (HANDBOOK, README, STATUS, LOGS)
  2. Restate the request as a ☐ checklist before touching code
  3. Read the code you will actually change — the module + its tests + its callers
  4. Confirm the operating mode (default: Autonomous)

Session end

  1. Verify — run the offline test suite + lint + compile check
  2. Resolve the checklist — every line ✓ or ☐; every ☐ gets a reason AND goes into STATUS
  3. Update the docs to match reality (STATUS, HANDBOOK, README, LOGS)
  4. Commit with a clear message; deploy/sync; confirm
  5. Sign off with the completion report and · docs updated if any core doc changed

The four core docs

DocPurposeHIE equivalent
READMEPhilosophy, standards, and user-facing overview. The "what and why."README.md + KERNEL.md (the promise)
HANDBOOKArchitecture, data flow, rules, session ritual, port-sync, deploy. The "how."LOAD-FIRST.md + docs/agentic-build-loop.md + docs/orchestrator-worker-system.md
STATUSCurrent health, active priorities, known bugs, tech debt, roadmap, live TODO. The "now."The "current truth" concept from KERNEL.md — inspect the checkout, not old docs
LOGSDated history of what shipped and when. The "then."WORK-DONE.md pattern for scrubbed history

Testing

Mumble has 15 offline + 3 live test files (test_*.py) covering formatting, mode selection, bindings, presets, favorites, stream seams, WebUI API, UI, cloud sync, foreign boost, local engine, reader, and more. Tests are run via .venv\Scripts\python.exe test_*.py.

Bug-fixing protocol (HANDBOOK §7)

  1. Reproduce first — never fix a bug you cannot trigger
  2. Write a failing test that proves the bug
  3. Fix the code; the test goes green
  4. Check all callers for the same pattern
  5. Add a regression note to STATUS

Port-sync procedure (HANDBOOK §8)

When Windows code changes, the macOS and Linux ports must be kept in sync. The procedure involves copying platform-agnostic modules, running port tests, and recording the sync in STATUS.

Commit expectations (HANDBOOK §9)

Commits must be atomic, must pass the full test suite, must update the core docs if reality changed, and must never contain secrets, private paths, or generated junk.

7Where Mumble already aligns

Mumble's existing process is remarkably close to the HIE philosophy. It was not modeled on HIE — it evolved independently — but the convergence is striking:

Strong alignments (require no change)

  • Deterministic core before AI: formatting.py is the offline text engine; cloud AI in ai.py is opt-in and user-key-gated. This is exactly the HIE rule: "deterministic logic first, AI only where it improves the result."
  • Current files beat old docs: The session-start ritual mandates reading the actual code before editing. STATUS is versioned and verified against the codebase. This mirrors HIE's truth model.
  • Session ritual as operating loop: The start/end ritual in HANDBOOK §1 is essentially the HIE build loop in microcosm — read, scope, build, verify, document, ship.
  • Checklist-driven work: The ☐ checklist requirement at session start maps to HIE's "tight brief" phase. Every incomplete item gets a reason and goes into STATUS — similar to HIE closeout labels.
  • Privacy boundaries: Mumble's "audio never leaves the device" invariant is a stronger privacy guarantee than HIE's "don't publish secrets" rule, but they share the same spirit.
  • Test suite: 15+ test files covering core behavior and failure modes — this covers HIE proof rungs 1-3 (code shape, smoke, tests).

Partial alignments (could be strengthened)

  • Proof ladder: Mumble has tests and manual verification, but does not explicitly label proof levels (CLI proof, browser proof, eval proof). The concept is implicit.
  • Doc system: HANDBOOK/README/STATUS/LOGS map well to HIE's doc structure, but Mumble lacks a formal agent-routing entry point like AGENTS.md.
  • Safety scan: The .gitignore prevents most leaks, but there's no automated pre-commit or pre-PR safety scan.
  • Slice rule: The checklist naturally bounds work, but there's no explicit "smallest coherent slice" discipline enforced by the process.

8Where Mumble could absorb HIE patterns

Not everything in HIE is worth adopting. Some patterns are specific to multi-agent orchestration (Mumble uses a single Droid agent) or to the TeachClaw domain. But several ideas would genuinely strengthen Mumble's process without adding bureaucracy:

8.1 An explicit proof ladder

Right now, Mumble's verification is binary: tests pass or they don't. HIE's ladder adds granularity. For Mumble, a tailored proof ladder might look like:

LevelMumble proofCommand / check
L1Code shapeAll modules import cleanly; no syntax errors
L2CLI smokeApp starts in console mode; hotkey registered
L3Unit tests.venv\Scripts\python.exe test_*.py — all pass
L4Lint / safetyNo secrets, private paths, or generated junk; .env.example only
L5Port syncmacOS/Linux cores are byte-identical to Windows (verified)
L6Live smokeApp runs on real hardware; dictation produces output
L7Docs matchHANDBOOK/README/STATUS/LOGS match the current checkout

Each session-end sign-off could name the highest rung reached. Instead of "verified," the sign-off becomes "L4 proved (tests + safety scan)."

8.2 A pre-commit safety scanner

HIE's scripts/public_safety_check.py is a simple scanner that detects secrets, local paths, private-workspace markers, generated release junk, and accidental binary artifacts. Mumble could adopt this pattern with a lightweight Python script that checks:

  • No .env files with real keys (only .env.example)
  • No absolute paths pointing to C:\Users\... or /home/...
  • No settings.json committed (already gitignored, but a double-check is cheap)
  • No generated zip files or build artifacts accidentally tracked
  • No private session files (*.session) in the tree

This could run as part of the session-end ritual or as a pre-commit hook.

8.3 A formal automation brief template

HIE's templates/automation-brief.md is a structured questionnaire that forces clarity before any code is written. Mumble could adopt a lightweight version for non-trivial feature work:

# Feature brief
- Who uses it:
- What they do manually today:
- What input they already have:
- What output should they get back:
- What the feature must never do:
- What proof would make this trustworthy:
- Smallest shippable slice:
- Affected modules:
- Test plan:

This would live alongside the existing checklist system — it does not replace it, but adds upstream clarity for complex changes.

8.4 An agent router (AGENTS.md)

Mumble already has a de facto agent router: the HANDBOOK's session-start ritual tells the agent what to read. But an explicit AGENTS.md file — short, always-loaded, pointing to the right docs — would make Mumble more agent-friendly without changing any existing habit:

# AGENTS.md — Mumble

## Load first
1. Read DEVELOPMENT/Core/README.html (philosophy + standards)
2. Read DEVELOPMENT/Core/HANDBOOK.html (architecture + rules + session ritual)
3. Read DEVELOPMENT/Core/STATUS.html (current state, bugs, roadmap)
4. Read the code you will actually change + its tests + its callers

## Scope
- Mumble is a local-first Windows voice-to-text app
- Audio stays on-device; only transcribed text may touch cloud AI
- Never commit secrets, settings.json, .venv/, or private paths

8.5 Eval harness for Smart Mode quality

This is the most ambitious idea — and the one most directly inspired by HIE. Mumble's Smart Modes (Text, Prompt, Email, List, Reply, Foreign, Convert) could benefit from an eval harness.

Currently, mode quality is judged by "does the output look right when I test it manually." An eval harness would add:

  • Scenario packs: 10-20 test dictations per mode, each with an expected quality label
  • Rubric dimensions: task completion, tone appropriateness, structure compliance, safety boundary
  • Strategy comparison: single-pass vs draft+checker+repair, cheap model vs premium model
  • Scorecard: a machine-readable verdict per mode per strategy

This would be especially valuable when switching AI providers or models — instead of "it seems fine," Mumble would have data about whether the new model's formatting quality matches the old one's.

Note: Mumble already has the infrastructure for this. The offline formatting.py engine is deterministic and testable; the cloud ai.py lanes produce structured output. An eval harness would be a consumer of the existing pipeline, not a rewrite.

8.6 CI/CD for the test suite

HIE runs make check on every push and PR via GitHub Actions. Mumble has no CI/CD pipeline. Adding even a minimal GitHub Actions workflow that runs the offline test suite on push would catch regressions before they reach the owner's machine. The workflow would need to:

  1. Set up Python 3.12
  2. Create a venv and install from requirements.txt
  3. Run the offline test files (excluding live tests that need real hardware)
  4. Run a safety scan

9A concrete integration roadmap

Rather than adopting HIE wholesale — which would be overkill for a single-agent project — here is a phased, low-risk integration path that adds the highest-value pieces first.

Phase 1 — This week (zero disruption)

  • Add AGENTS.md to the repo root — a 15-line router that points agents at the four core docs
  • Add a lightweight safety scanner script (scripts/safety_check.py) that checks for secrets, paths, and junk
  • Run the safety scanner as part of the session-end ritual

Phase 2 — This sprint (minor additions)

  • Adopt the proof-ladder language in session sign-offs ("L4 proved: tests + safety scan")
  • Create a feature-brief template for non-trivial changes
  • Set up GitHub Actions CI to run the offline test suite on push

Phase 3 — When a mode changes (targeted)

  • Build an eval harness for the Smart Mode whose behavior is changing
  • Create scenario packs with 10-20 test dictations
  • Define a rubric and produce a scorecard
  • Use the scorecard to gate the mode change

Phase 4 — When Mumble outgrows single-agent (future)

  • Split work into orchestrator + worker lanes
  • Add Crabbox-style isolated proof for port testing
  • Add browser E2E proof for the web UI
  • Formalize the autoreview pass before merge

10Risks and anti-patterns to avoid

Over-engineering the process

HIE describes a system used by someone shipping AI-assisted products professionally across multiple worker lanes. Mumble is a single-agent project. Adopting the full 11-role worker model would be counterproductive noise — it would add ceremony without adding value. The right approach is to absorb the principles (proof ladder, deterministic baseline, safety scan, brief template) without the machinery (multi-agent orchestration, Crabbox, browser workers).

Eval harness scope creep

An eval harness is valuable for Smart Mode quality — but building one for every mode at once would be a multi-week project that delivers zero user-facing value. Phase 3 should start with one mode (likely Text mode, since it's the default and most-used) and prove the harness works before expanding.

Process as substitute for judgement

HIE itself warns about this: "never call a workflow ready just because a command exited zero." Adding proof labels and safety scanners must not become a checkbox exercise. The point is to make better decisions, not to generate more paperwork. Every piece of process added must answer: "what decision does this enable that we could not make before?"

Factory Mission Control vs HIE — they solve different problems

Factory's Mission Control is a runtime environment for agentic work — it provides the shell, the tools, the skills, and the session management. HIE is a design pattern for structuring that work — the lanes, the proof ladder, the eval harness. They are complementary, not competing. Mission Control gives you the room; HIE tells you how to arrange the furniture. Mumble already operates inside Droid (which is Factory's agent runtime), so the comparison is not "which one should we use" but "how much of HIE's furniture should we bring into the room."

Summary

The bottom line

How I Engineer is not a product to install — it is a pattern to study. Its core contributions are (1) the proof ladder (11 distinct evidence levels, no substitution allowed), (2) the eval harness (scenario packs + rubrics + scorecards for quality-sensitive changes), (3) the autoreview gate (independent review for scope creep and safety before merge), and (4) the worker-lane decomposition (bounded jobs with narrow accountability).

Mumble already does much of this implicitly. Its session ritual, four-doc system, deterministic-first architecture, and privacy boundaries are strongly aligned with HIE's kernel. The gaps are in explicitness: Mumble lacks named proof levels, an automated safety scanner, a feature-brief template, and CI/CD.

The recommended path is to adopt the lightest, highest-value pieces first (AGENTS.md, safety scanner, proof labels) and reserve the heavier machinery (eval harness, worker lanes, Crabbox) for when Mumble's complexity genuinely demands them. The goal is not to become HIE — it is to make Mumble's already-strong process legible and verifiable in the way HIE demonstrates.
