Engineering Blueprint

Local Post-Processing Engine

◆Date: 2026-06-27
◆Target app: Mumble (Python desktop, faster-whisper speech-to-text, CPU-first, Windows is the source of truth)
◆Companion research: local_nlp — the lightweight-language-tech survey this builds on
◆Status: a design spec, plus two finished and offline-tested modules (Internal/foreign_boost.py and Internal/local_engine.py), plus the owner-approval-gated plan for the rest
In plain terms

Mumble turns your speech into text. When you have an internet API key, the heavy "make it read well" work happens in the cloud. But lots of people have no key or want everything to stay on their own computer. This document is the plan for giving those offline users a genuinely good experience — done entirely on their machine — without ever weakening the cloud experience for people who paid for it.

"Post-processing" just means the clean-up that happens after the raw words are recognised: fixing punctuation, formatting an email, repairing a foreign word the recogniser misheard, and so on.

One-line thesis. Give the no-key / offline user a genuinely capable on-device engine for the five primary lanes (Prompt, Email, List, Reply, Foreign) instead of weak templated output — while keeping the cloud the primary authority whenever a key is present (the legacy pipeline the paying user opted into). Never load a model the user's hardware or language doesn't need.

Cloud-dominance hierarchy (owner directive, 2026-06-27 — supersedes any "local-first by default" framing below). Cloud is the primary authority for final text transformation. Local post-processing is gated: it runs only when there is no cloud key OR the user has flipped an explicit Local-Only toggle. When a key is present, the pipeline is the legacy one — local does raw speech-to-text + inline // uncertainty marking only, then the raw transcript goes straight to cloud; no intermediate local reasoning intervenes. Local-only never hard-blocks: it best-efforts every task and appends (never interrupts) a notice when a task exceeds edge capability. This reconciles the original "make local the default" brief (true for the offline majority) with the owner's quality bar for key-holders.

1Cloud-vs-local routing (Brief §1 + the dominance directive)

In plain terms

Every time you dictate, Mumble has to decide one thing: who does the final clean-up — the cloud, or your own computer? The rule is simple. If you have a key and haven't asked to stay offline, the cloud does it (best quality). If you have no key, or you flipped the "Local-Only" switch, your computer does it. That single decision is made in one place, by a function called route().

1.1 The gate — one branch decides everything

One yes/no question — "is this a local-only run?" — picks the path. It's local-only when there's no cloud key, or when you turned on the Local-Only switch.

Logic The exact rule 
local_only = (no cloud key)  OR  (explicit Local-Only toggle)

  cloud-augmented  (key present, toggle off)  ->  CLOUD is primary
  local-only       (no key, or toggle on)     ->  LOCAL engine, best-effort

local_engine.route() is the single source of truth. The controller asks where does final transformation happen? and never hard-codes provider logic in the hot path.

1.2 Cloud-augmented (a key is present) — the legacy pipeline

Cloud is the authority. The only local work is at the transcription stage:

  1. Local faster-whisper produces the raw transcript.
  2. Low-confidence / foreign tokens are marked inline with // (formatting.annotate_uncertain, foreign_boost.mark_uncertainty — marking, not resolving).
  3. The raw transcript + markers is packaged and sent straight to the cloud lane (ai.py) for all final formatting/cleanup. No intermediate local reasoning or restructuring runs.

So when a key is present, route(lane, cloud_key_present=True) returns CLOUD for every lane — text, foreign, prompt, email, list, reply, and every Deck preset. This preserves the earlier architecture exactly for users who opted into Pro Mode.

1.3 Local-only (no key, or the offline toggle) — best-effort, never blocks

LaneEngineNotes
text, foreignLOCALformatting.py / foreign_boost.py resolve fully on-device.
prompt, email, list, replyLOCAL_LLM if ready, else LOCALLocal GGUF (Strategy B) if installed; else the deterministic formatting.build_* builder.

classify_task() flags a job as heavy when a preset is tagged requires="cloud", the lane is a heavy Deck lane, there are ≥ 2 source documents, or a reasoning input exceeds the edge budget (HEAVY_WORDS = 1500).

1.4 The graceful notification — appended, never interrupts (directive §3)

Local-only never hard-blocks. When a task exceeds edge capability it still produces best-effort output, and the result carries a notice the UI appends at the output stage:

Code The decision object that carries the notice 
RouteDecision(engine="local" | "local_llm",      # it still runs
              reason="local-best-effort-degraded",
              degraded=True,
              notice="For enhanced results on this task, enable AI Pro Mode "
                     "or connect a cloud API key.",
              suggested_provider="cerebras", suggested_key_setting="cerebras_api_key")

cloud_fallback_hint() returns the structured form for a "Link Cerebras (free)" affordance that deep-links to Settings → Pro Mode → Cerebras key (settings.cerebras_api_key; Cerebras = fastest free tier, gpt-oss-120b ~0.4–0.5 s). cloud_fallback_hint(strong=True) returns the original exact phrasing — "This specific preset requires cloud acceleration. Please link a cloud API key." — preserved as CLOUD_REQUIRED_MESSAGE for any UI that wants it.

1.5 Privacy invariant is untouched

The matrix changes where text is processed, never what leaves the device. Audio is still 100% local. local/local_llm send nothing anywhere. cloud sends only text (raw + // markers), only with a user key (HANDBOOK §5.1). The local-only user sends nothing at all.

2Loading the right speech model (Brief §2)

In plain terms

The "model" is the AI brain that turns sound into words. There are small ones (fast, light, but English-only) and big ones (understand 99 languages, but use more memory). The goal: load the smallest model that fits the user's computer and the language they actually speak — never waste memory on a 99-language brain for someone who only dictates in English. Most of this is already built; we just add a clearer onboarding question and per-language tuning.

2.1 What already exists (don't rebuild it)

  • Resolver: branding.resolve_model(tier, english_only) maps a PC class × language scope to a concrete faster-whisper id via MODEL_BY_TIER:
TierEnglish-only (.en)Multilingual
weakbase.enbase
midsmall.ensmall
powerfuldistil-large-v3large-v3-turbo
  • Single-resident guarantee (already enforced): mumble._try_load releases the old model before assigning the new one, then gc.collect() — so Mumble is never holding two whisper models at once. This is precisely the "don't hold multiple idle models" requirement, already done.
  • Lazy + unload: _ensure_local_model (load on demand), _unload_local_model (drop when cloud speech-to-text is active), _warm_model (two-pass warm so the first dictation is full-speed).
  • Auto-probe: branding.detect_hardware_tier (cores/RAM) → cached in hardware_tier_resolved.

The "English-only client must not allocate a 99-language model" waste is therefore already avoided: an English user on small.en never loads the multilingual small.

2.2 The gaps to close

(a) The explicit onboarding question. Today onboarding step #ob-lang is a language card that sets english_only = (lang === "en"). Reframe it as the brief's question and make the consequence legible:

"Do you speak more than one language while dictating?"
• No — I dictate in English. → loads the fast English-only engine (lighter RAM, more accurate for English).
• Yes — I switch languages mid-sentence. → loads the multilingual engine so foreign phrases decode correctly.

This sets english_only (already wired through finish_onboarding → _apply_hardware_model). No new plumbing — a copy + UX change in webui/app.js + index.html.

(b) Primary-language fine-tuned swap. The brief wants: primary language = French/German → load a model optimised for that tongue, swapping memory maps so idle models aren't held. The resolver currently only branches English-only vs generic-multilingual. Add a language-targeted tier so a committed French user gets a French-leaning model rather than the generic multilingual:

Code Proposed branding.py addition 
# branding.py — proposed addition
MODEL_BY_LANGUAGE = {
    # language -> {tier: model_id}.  faster-whisper has no per-language *.fr builds,
    # so "fine-tuned for a tongue" means: the multilingual model PINNED to that
    # language (decoder language token forced) + the matching initial_prompt +
    # that language's vocabulary/foreign pack. Distil/CTranslate2 community models
    # (e.g. distil-large-v3-fr) drop in here as they appear.
    "en": {"weak": "base.en",  "mid": "small.en",       "powerful": "distil-large-v3"},
    "__multi__": {"weak": "base", "mid": "small",        "powerful": "large-v3-turbo"},
}

def resolve_model(tier, english_only=True, primary_language="en"):
    if english_only or primary_language == "en":
        return MODEL_BY_LANGUAGE["en"][tier]
    return MODEL_BY_LANGUAGE["__multi__"][tier]   # pinned to primary_language at transcribe time

The real lever for a single target language is not a different file (faster-whisper ships one multilingual model) but forcing the decoder language token + a language-specific initial_prompt. mumble._warm_model already computes lang; the live transcribe call passes language=. So "swap to the French model" = (multilingual model resident) + language="fr" + French vocabulary/foreign pack. The swap is memory-cheap because the multilingual weights are shared; only the decode-time language token and the prompt change. When a true per-language distilled model exists (community CTranslate2 builds), it slots into MODEL_BY_LANGUAGE and the existing set_model hot-swap (with its single-resident guarantee) handles the rest.

(c) Track primary_language. Add settings.primary_language (default "en"); on change in Settings, call _apply_hardware_model(force=True) (already the handler shape at mumble.py:1924, which watches hardware_tier/english_only). The dashboard's "Primary Spoken Language" dropdown writes this; the resolver reads it.

3Foreign Mode — repairing misheard words (Brief §3)

In plain terms

An English speech model has never "heard" the word juz (a part of the Quran), so when you say it, the model writes down the closest English word it knows — "just". The real foreign word vanishes. Foreign Mode catches these and puts the right word back.

The hard part: do it without breaking ordinary English. If you actually said "I just left", it must stay "just". The pipeline below uses several clues — a dictionary of known mishearings, surrounding foreign context words, and how unsure the recogniser was — to decide safely.

Shipped: Internal/foreign_boost.py (+ 18 passing tests). This section is both the design and the as-built parsing-workflow breakdown the brief asks for.

3.1 The algorithmic problem

An English-tuned acoustic model has no token for "juz", "gracias" or "croissant". It force-maps the foreign acoustics onto the nearest English string it does have: juz → "just", gracias → "grassy us", croissant → "kwasont". The foreign word never appears in the output; a plausible English word sits in its acoustic slot.

3.2 The repair pipeline, stage by stage

Input is the stream of recognised words, plus (optionally) a per-word confidence score the recogniser already produces. It flows through seven stages:

1
Tokenise

_WORD_RE runs over the stream and splits it into an ordered list of individual word-tokens.

2
Lexicon match

Check each token against the user's chosen secondary-language packs:

(a) exact known-mishearing hit → start at BOOST (high precision).  (b) phonetic-signature hit (a ≥4-character consonant skeleton, exact) → start at OFFER.  (c) token already equals the canonical word → LEAVE it (don't re-flag a correct "juz").

3
Context strength

Scan the sentence for unmistakably-foreign anchor words ("quran", "imam", "amigo"…). One or more present ⇒ the engine can be bolder about a repair.

4
Acoustic slot

If the recogniser's confidence for that word (word.prob) is below the threshold (0.6), it was unsure — that slot is a strong candidate for being a misheard foreign word.

5
Decision gate

The heart of the system. Combines the three clues above to choose BOOST, OFFER, or LEAVE — see the table in §3.3.

6
Flag injection

BOOST → //Juz (applied; leading flag).  OFFER → just//Juz (candidate; infix flag).  LEAVE → untouched.

7
Render

Offline: strip_flags() → "Juz" for applied boosts.  Cloud on: hand the //-marked stream to ai.cerebras_foreign() to resolve the remaining OFFERs.

3.3 The decision gate (Stage 5)

The crux is never silently corrupting ordinary English while still catching genuine foreign interjections. The gate combines three signals — lexicon tier, foreign-context, acoustic confidence — and a hard guard on common English words:

Token is…LexiconContextLow-conf slot→ Decision
not an English wordexact mishearinganyanyBOOST //Term
not an English wordphonetic-only+ gateway+ low-confBOOST
not an English wordphonetic-onlyelse—OFFER heard//Term
common English wordexact mishearing+ gateway+ low-confBOOST (the juz→//Juz case)
common English wordexact mishearinggateway or low-conf—OFFER
common English wordanynonenormalLEAVE ("I just left" stays)

This is why foreign_boost.boost("I just left the room", ["arabic"]) returns the text unchanged, but boost("I memorized the first just of the Quran", word_probs=[…0.40…]) returns "…the first //Juz of the Quran" — gateway Quran + low-confidence slot promote the homophone to an applied boost. Both are covered by tests.

3.4 The //JUZ notation (two tiers, one stream)

  • //Term (leading slashes) = an applied boost. The engine was confident; the token was replaced. strip_flags("//Juz") → "Juz".
  • heard//Term (infix slashes) = an offered candidate, the existing islamic_terms.annotate_foreign notation. Resolved downstream — offline strip_flags keeps the recognizer's word (safe); with the cloud on, ai.cerebras_foreign picks from context.

So the local engine upgrades the existing system: high-confidence cases resolve on-device (an offline user finally gets "Juz"), and the cloud lane only ever sees the residual ambiguous offers — fewer tokens, cheaper, higher hit-rate.

3.5 Language packs (multilingual by data, not code)

A pack is (canonical, [known_mishearings]) + a gateway set. Adding a language = adding a list.

  • Arabic reuses islamic_terms.ISLAMIC_TERMS verbatim (~250 entries) — single source of truth, no fork.
  • Spanish / French ship as compact, high-precision starter packs (amigo, gracias, señor, jalapeño; croissant, café, rendez-vous, déjà vu…).
  • Packs are selected from settings.foreign_languages (already a list, default ["arabic"]), with aliases (es/español, fr/français, ar).

3.6 Phonetic signature (zero-dependency)

A cross-lingual consonant skeleton folds the spelling variation that separates a foreign term from its English mis-map (j/g, k/c/q, s/z, f/v, silent vowels): juz/juzz, café/cafe, croissant/kroissant collapse to one key. Indexed only at length ≥ 4 (short skeletons collide: saw and Sa'i both reduce to s — the source of every false positive in the first test run, now gated out). Recall path = exact signature match; precision path = the curated mishearing table.

3.7 Integration

In code, Foreign Mode is just a few lines added where Mumble already handles the foreign lane: run the booster, then either hand the result to the cloud (if a key is present) or strip the flags and finish on-device.

Code The mumble._cloud_generate foreign lane 
# mumble._cloud_generate, foreign lane — augment the existing two lines:
if mode_hint == "foreign":
    langs = self.settings.get("foreign_languages") or ["arabic"]
    result = foreign_boost.boost(content, languages=langs, word_probs=words_probs)

4Smart modes & grammar steering (Brief §4)

In plain terms

"Smart modes" are when Mumble doesn't just transcribe but reshapes your words — into an email, a bulleted list, a reply. Offline, it currently does this with fixed templates (correct, but stiff). A small AI model running on your computer can make it read naturally. The trick that makes a tiny model reliable is a grammar: a rule that makes a wrong shape literally impossible to produce (e.g. "you may only output bullet points"). This is an opt-in, owner-approved feature because it needs a sizeable download.

4.1 The real gap

The offline builders (formatting.build_prompt/email/list) produce correct but templated output — build_prompt emits a fixed You are {role}. # Task … # Instructions … scaffold. The cloud lanes produce fluent output. A small on-device LLM, constrained by a grammar, closes most of that gap for the structured lanes without the cloud.

local_nlp.md §2d is right to caution that a 1 B model free-running on CPU is multi-second. The mitigation is structural: grammar-constrained, short, structured lanes (List, Email) are where small models are both fast enough and good enough; free-form Prompt/Reply stay cloud-preferred. This is encoded in LANE_POLICY (all four prefer local_llm but fall back to cloud) and the phasing in §5.

4.3 GBNF grammar models (structural constraint)

GBNF binds the sampler so a malformed shape is impossible — not merely discouraged by the prompt. local_engine.GBNF ships three production grammars:

  • list — output is forced to "- " text "\n" items. The model literally cannot emit a paragraph; it can only emit bullets.
  • json_object — a minimal valid-JSON grammar for structured-extraction presets (the only way to guarantee a parseable object from a 1 B model).
  • email — Subject? → greeting → body → sign-off skeleton.

grammar_for(lane) returns the grammar (or None for free-form prose lanes). LlamaCppBackend compiles it via LlamaGrammar.from_string and caches it.

4.4 Context-injected reference documents (style steering)

local_engine.STYLE_SHEETS are compact, byte-stable system fragments (one per lane) + a shared UK-English rule. Stability matters: a llama.cpp prompt cache keeps the fixed prefix warm, so the style guidance costs ~0 tokens per dictation after the first. This is the local mirror of ai.py's system prompts, trimmed to what a small model can actually follow. build_local_request(lane, text, prefs, context) assembles the (system, user, grammar) triple — the same framing discipline ai.py uses (delimited transcript, "output ONLY…"), so behaviour is consistent across engines.

4.5 The backend seam (shipped)

A "seam" is a clean swap-point. By default Mumble uses a do-nothing backend, so the whole feature is present but dormant — it only activates if someone installs the optional engine and a model. Nothing breaks if they don't.

Architecture The backend class shape 
LocalLLMBackend (abstract)         available() / generate(system, user, grammar, max_tokens)
 ├─ NullBackend          DEFAULT — available()=False → router routes to cloud/builder
 └─ LlamaCppBackend      import-guarded; available()=False until llama-cpp-python AND a
                          GGUF file are present; lazy-loads the model on first generate
set_backend()/get_backend()/local_llm_ready()   process-wide, swapped once at boot

Because the default is NullBackend, the entire engine imports, runs and unit-tests with no llama-cpp installed — and the router degrades exactly as designed. Installing the package + model and calling set_backend(LlamaCppBackend(model_path=…)) is the only step that lights up the local_llm lane.

4.6 The honest trade-off (owner decision required)

Local LLM was deliberately removed in v3.17.0 ("could not be configured by a non-technical user … implied functionality that wasn't production ready" — settings._migrate, local_provider_retired_applied). Re-introducing it is a product-direction call, and adding llama-cpp-python + a multi-hundred-MB model is a heavy dependency (README §5: "no new heavy dependency without a clear reason and owner awareness"). This blueprint therefore:

  1. Builds everything around the dependency (router, seam, grammars, style sheets) so it ships today with zero new deps and the lanes degrade gracefully.
  2. Recommends the local LLM as an opt-in "Edge AI" toggle, default off, surfaced only on powerful (or mid with explicit consent), with a one-time model download behind a progress UI — not a second app to install (the thing that failed before).
  3. Keeps the deterministic builder as the universal floor and Cerebras as the quality ceiling, so the local LLM is purely additive — it can never strand a user.

4.7 Architecture choice + passive runtime footprint (directive §4)

The local LLM must be a good background citizen: low thermal impact, low CPU/GPU contention, no perceptible hit to system responsiveness while the user multitasks. Two architectures were weighed:

Strategy A — UnifiedStrategy B — Segregated (chosen)
ShapeExtend/fine-tune the speech-to-text model so grammar + formatting happen inside decoding (single pass)A separate ~1–3 B edge LM runs after transcription, async
ProsLower architectural complexity; no inter-model overhead; tight couplingModular; post-processing optimised independently; clean upgrade path (swap the GGUF)
ConsCouples two concerns; re-training faster-whisper/CTranslate2 is a research project; no GBNFSlight dual-model overhead (RAM + a second process)
Footprint controlLimited — bound to the speech-to-text decode loopFull — own thread priority, own schedule, own quantisation

Chosen: Strategy B, segregated, with an aggressive passive-footprint policy:

  • Aggressive quantisation — Q4_K_M GGUF (≈0.9–2.0 GB) keeps the model in cache-friendly RAM and CPU-only viable.
  • Low-priority, throttled threads — run llama.cpp below normal priority (SetThreadPriority THREAD_PRIORITY_BELOW_NORMAL on Windows; nice/SCHED_IDLE on the ports) and cap its threads (n_threads = cores − 2, shared budget with speech-to-text), so it yields to the foreground instantly.
  • Strict async scheduling, never blocks transcription — the post-processing model runs on its own worker off the capture/STT thread, behind the existing generation counter (HANDBOOK §2.3) so a newer dictation cancels a stale in-flight pass. Transcription latency is never on the LLM's critical path.
  • Lazy + evictable — the model loads on first local-LLM use (never at boot) and can be unloaded under memory pressure, mirroring mumble._unload_local_model for the speech-to-text model. Only ever one STT model + at most one GGUF resident (the single-resident discipline of §2.3).
  • Tiered enablement — off by default; offered on powerful (or mid with consent); skipped entirely on weak, which stays on the rule builder.

This is exactly what LlamaCppBackend is built to host: lazy _ensure(), a n_threads cap, and n_gpu_layers=0 by default (CPU-first). Thread-priority + scheduling are the P3 wiring.

6The full Mumble flow, start to finish

In plain terms

This is the whole journey of one dictation — from pressing the hotkey to text appearing where your cursor is. It's grounded in the real code (verified against the Internal/ folder), not a guess. Notice step 6 splits in two: the cloud path (if you have a key) or the local path (if you don't).

1
Audio ingestion

Hotkey (Ctrl+Win, via bindings.py) → mumble.start_recording. sounddevice captures float32 audio at SAMPLE_RATE on a worker thread. The island overlay (overlay.py + island_render.py) shows "listening". Audio never leaves the device.

2
Local transcription (always on-device)

Hotkey again → capture stops → mumble._process(audio, …). faster-whisper (model resolved by §2: tier × language) runs with vad_filter=True; per-segment {avg_logprob, compression_ratio, no_speech_prob} and per-word {word, prob} are captured. Model orchestration (_try_load / _ensure_local_model / _unload_local_model) keeps exactly ONE model resident (release-before-swap).

3
Raw stage + uncertainty encoding

Output is RAW at this stage. Segment gating (formatting.gate_segments) drops silence / looping hallucinations. Low-confidence + foreign tokens are marked inline with // (formatting.annotate_uncertain / foreign_boost.mark_uncertainty) — MARKING only, no resolution yet.

4
Mode selection (UI only)

In-text mode keywords are DEPRECATED. The lane is whatever the Island / UI state says: Prompt toggle on → "prompt"; Deck action → its preset; else plain "text" (foreign if Foreign Mode is on). No in-text scanning.

5
Routing — the dominance gate (local_engine.route)

local_only = (no cloud key) OR (Local-Only toggle). Cloud-augmented → engine = CLOUD (every lane). Local-only → text/foreign = LOCAL; smart = LOCAL_LLM | LOCAL; heavy = best-effort + appended notice.

6
The split — cloud path or local path

6a · Cloud-augmented (legacy)

Raw transcript + // markers → ai.py lane (cerebras_polish / _prompt / _email / _list / _reply / _foreign / _intent). Cloud makes the FINAL call. A 429 → capped retry → offline builder fallback. _collect_text drains the stream.

6b · Local-only

formatting.format_transcript (clean + punctuation + commas + deloop), build_prompt/email/list, or foreign_boost.boost + strip_flags. The local_llm lane uses local_engine.build_local_request (GBNF + style sheet) if installed. Heavy → append decision.notice.

7
Output rendering

_clean / _extract_final_prompt finalise the text. Paste at cursor (save → set clipboard → paste → verified restore). Saved to history.py; stats.py updated; island flashes "done". Any degraded notice is appended here.

Preset / prompt execution (Deck): a Deck action sends its preset's full instruction as the system message via ai.cerebras_intent over selected material (cloud-augmented), or runs the local builder/LLM best-effort (local-only). Prompt mode sends the Master Constitution (prompt_constitution.py) on every call. UI state: the Island (overlay.py) is the live status surface and the only mode control (Prompt/Deck companion bar); the web UI (webui/) mirrors status and hosts Settings/onboarding. Privacy throughout: audio never leaves; only text (raw + // markers) is ever sent, only when a key is present.
