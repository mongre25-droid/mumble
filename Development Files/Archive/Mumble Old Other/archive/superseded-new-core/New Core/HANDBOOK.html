01

Orientation

Mumble is one background controller with two UI bodies, specialised engines and JSON-based local persistence.

Runtime root

Internal/app/

Canonical controller, UI bridge, engines, stores, platform helpers, tests and release assets.

Primary entry

mumble.py

Owns lifecycle, application state, audio capture, orchestration, hotkeys, tray, island and authenticated commands.

Web surfaces

webui_shell.py

One separate pywebview host lazily owns the full workspace and the compact Search launcher, each with a narrow Python bridge.

◎

The architectural pressure point

The controller, Web bridge, island and Lite UI remain large and coupled. New work should move toward explicit services and thin platform adapters; it should not add another parallel implementation.

02

Runtime topology

The controller is the authority. The Web UI is a separate process. The island lives in the controller’s Tk process.

Process and boundary modelWindows canonical runtime
!

Shutdown is intentionally forceful

The controller tears down the Web UI process tree, closes runtime resources and ultimately uses os._exit(0) because UI/input libraries can leave non-daemon threads alive. Irreplaceable data must therefore be durable before shutdown reaches that point.

03

Startup sequence

UI appears early; expensive model loading is deliberately moved behind the visible shell.

Acquire single-instance ownership

Bind loopback port 49517. A later launch authenticates and asks the running instance to open its window.

Create the controller UI spine

Start the hidden Tk root, in-process island, tray thread and Tk dispatch queue.

Recover durable work

Create the Meeting recorder and start recovery for pending or interrupted recordings already on disk.

Register essential input and IPC

Register record, latest-paste, Deck, search and mode bindings independently; start the authenticated command server.

Open the main window

Spawn webui_shell.py before the speech model finishes loading, so the product becomes visible quickly.

Warm audio and resolve models

Probe PortAudio, choose a hardware/language-aware local model and load it unless cloud transcription deliberately defers local loading.

Begin non-blocking services

Start clipboard monitoring when enabled, validate configured AI access and check updates only if a signed publisher channel is configured.

Settings route contract

The saved selection and effective route are different facts. A missing key, unsupported saved provider or device-only override keeps processing on-device without deleting provider, key, model or language choices. Settings exposes the reason and lets the user resolve it in the relevant Transcription or Processing section.

✓

Safe wording pattern

“Audio stays on this device in Local transcription. Cloud transcription sends the clip to [provider]. AI shaping sends transcript text and selected context, not the original audio.”

10

Verification discipline

The isolated subprocess runner is the authoritative Windows offline entry point. Its complete baseline was green on 15 July 2026.

Always safe and useful

  • python -m compileall Internal/app for Python syntax/import bytecode generation.
  • node --check Internal/app/webui/app.js for JavaScript syntax when Node is available.
  • git diff --check for whitespace and conflict artifacts.
  • python run_tests.py --list to inspect the offline set without executing it.
  • python run_tests.py --pattern core_regressions for the real local/cloud STT regression seam.
  • python run_tests.py --json test-results.json for the full isolated offline baseline.

Use deliberately

  • Do not bypass run_tests.py with broad discovery in a user-configured data directory; procedural scripts can have import-time behaviour.
  • The runner sets a separate MUMBLE_TEST_DATA_DIR per script and strips credential-shaped environment variables in offline mode.
  • Live-provider tests require both --live and MUMBLE_RUN_LIVE_TESTS=1.
  • Do not count a source-inspection test as end-to-end behavioural coverage.
✓

Windows baseline recorded

run_tests.py --timeout 180 --json windows-audit-final.json completed 65/65 offline scripts in 402.14 seconds on 15 July 2026. This proves the isolated software seams, not physical microphone/paste, live providers or release-package lifecycle.

11

Release gates

A source change is not a shipped release. Version 1.0 requires all of these gates, not a subset.

Product correctness

Core loop green; privacy copy route-aware; no false success; Meeting and Reader durability tested.

Build integrity

Clean environment, locked dependencies, archive rebuilt from current source and install/uninstall smoke-tested.

Trust chain

Signed application artifacts; Ed25519-signed update manifest; live HTTPS feed; no unsigned downgrade.

Test authority

The Windows offline gate has one runner, isolated data, explicit live opt-in, timeouts and machine-readable results.

Platform claim

Shared-core parity or clearly scoped platform support, verified on native Windows, macOS and Linux.

Documentation truth

User guide, onboarding, settings, privacy statements and this Core agree with the released build.

The live gate status and ordered remediation plan are in STATUS.
