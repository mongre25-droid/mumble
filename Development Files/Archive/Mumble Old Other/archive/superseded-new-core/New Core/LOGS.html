01

What this log is for

It answers one question: “What durable result changed in Mumble?”

Include

Shipped or completed outcomes, the small set of affected areas and the verification that matters.

Keep elsewhere

Current blockers and next actions belong in STATUS. System explanation belongs in HANDBOOK.

Exclude

Brainstorms, dead ends, superseded behaviour, old feature inventories, chat narration and repeated details.

◎

Version control remains the full forensic record

This page is an index of meaningful outcomes, not a substitute for commits, diffs, tests or release notes.

02

Writing rules

Short enough to scan; precise enough to trust.

  • Add an entry only after a coherent outcome is complete.
  • Use one heading, one sentence and at most three result bullets.
  • Name observable behaviour, not the session that produced it.
  • Record verification in a single compact bullet.
  • Do not preserve an old feature name for context.
  • Do not copy TODOs, risks or “next time” notes into LOGS.
  • Do not repeat architecture already explained in HANDBOOK.
  • Do not say “fixed” when the relevant path was not verified.
