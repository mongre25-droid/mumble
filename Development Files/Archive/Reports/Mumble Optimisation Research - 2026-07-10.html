How to make Mumble feel instant

A read-only analysis of Mumble’s transcription path, runtime timing evidence, cross-platform acceleration options, and current open-source speech-to-text engines. It recommends what to change; it does not implement or execute the changes.

01 · Executive verdict

Mumble’s engine is reasonable. Its orchestration is the main latency problem.

Mumble already uses a strong baseline—faster-whisper, CPU INT8, CUDA FP16 when available, greedy decoding, an explicit language, a warm model, and live decoding. Replacing that engine everywhere would be a mistake. The largest gains come from fixing how the engine is selected and scheduled, then adding native backends where the current runtime leaves hardware idle.

Observed local baseline
0.35 median RTF

567 filtered cpu/int8/small.en log samples. About 1.75 s compute for a 5 s chunk.

First target
0.5–1.0 s

Conservative target from Stop to Paste for a warm, ordinary 3–10 s dictation, excluding optional cloud rewriting.

Long-form opportunity
≈50% CPU

Upstream faster-whisper’s batch-size-8 CPU benchmark halves 13-minute processing time; the trade-off is RAM.

Highest-value conclusion. Build one real transcription router and three duration policies: a short-utterance fast path, stateful streaming for normal dictation, and VAD + batching for long audio. Then make macOS genuinely native. This is more valuable than micro-optimising NumPy copies or replacing PortAudio.
  • P0 correctness/performance: the current live worker calls _local_transcribe() directly. A Cloud-selected plain dictation longer than about five seconds can therefore load and use the local model instead of the chosen cloud backend.
  • P0 dead acceleration: the platform-dispatch functions are not called by the production path. Windows DirectML, Apple Silicon, and Linux Vulkan adapters do not accelerate a normal dictation today.
  • P0 measurement: local STT is timed, but Stop→Paste, worker join, LLM formatting, cleanup, clipboard and UI are not captured as one span. Optimising only RTF can miss the actual wait.
  • P1 latency: fixed non-overlapping five-second chunks are a coarse approximation of streaming. They create hard word/context seams and still leave up to a full chunk to decode after Stop.
  • P1 long-form: meeting/file transcription uses full-array, non-batched processing. The official faster-whisper benchmark shows an immediate batching opportunity; the meeting recorder also retains avoidable large buffers.

05 · Bottleneck register

The issues to address before changing models

P0 — Selected backend and live backend are different

_transcribe() respects Cloud mode, but _stream_worker() calls _local_transcribe(). For a normal unarmed dictation, the worker starts at five seconds, loads the local model on demand, and its result becomes the base transcript. This defeats Cloud mode’s latency/memory intent and makes duration change engine behaviour.

Recommendation: all calls go through one TranscriptionRouter that owns backend, streaming session, fallback, telemetry and finalisation.

P0 — Platform acceleration is specification code, not production acceleration

transcription.get_platform_transcriber() has no production caller. The Linux implementation explicitly returns unavailable and is a stub. The Windows adapter requires unlisted packages and a manually placed SenseVoice model. The macOS adapter expects Python modules named fluid_audio and parakeet_tdt, while upstream FluidAudio is a Swift package/CLI; the macOS port does not even contain the canonical platform package.

Recommendation: do not “wire it in” as-is. Replace it with tested backend contracts and real packaging.

P0 — No authoritative Stop→Paste metric

RTF is logged inside local STT, but the 3 s join, cloud request, local/cloud formatting, clipboard wait, retries and GC are outside a single trace. The optimisation target should be user-perceived latency, not model time alone.

Recommendation: record p50/p90/p95 for stop_to_paste_ms and child spans: join, stt, shape, persist, paste. Tag OS, model, device, duration bucket, mode and cold/warm state.

P1 — Fixed chunks are not a streaming algorithm

Independent 5 s windows with no overlap, stable-prefix policy or prior prompt can split phonemes/words and lose context. The upstream Whisper-Streaming research explicitly warns that naive fixed windows fail at boundaries; LocalAgreement/AlignAtt exist to commit only stable text.

P1 — One policy is used for incompatible workloads

A 2.5 s dictation, a 20 s paragraph and a one-hour meeting should not share the same decode policy. Short clips need minimal fixed overhead; normal dictation needs low finalisation latency; long audio needs VAD segmentation, batching, bounded memory and durable progress.

P1 — Thread heuristic can over-subscribe CPUs

Mumble uses os.cpu_count() - 2, which counts logical CPUs. CTranslate2 recommends not exceeding physical cores with total inter×intra threads. Hybrid Intel/AMD and Apple CPUs need calibration; more threads can worsen short-clip latency and battery use.

P1 — Long-form batching is unused

faster-whisper’s own small-model CPU benchmark falls from 1m42s to 51s on 13 minutes with batch size 8. GPU large-v2 drops from 59s to 16s. Mumble uses the ordinary generator for meetings/files and leaves this throughput on the table.

P1 — Plain text can pay an LLM round trip

When a Pro key is present, _generate() attempts cloud generation before the local pipeline even for the text lane. Once STT is under a second, this becomes the most likely dominant wait. Plain dictation should have an explicit “Fast text” contract; semantic rewriting belongs to selected modes or an opt-in second pass.

P2 — Cloud transport is optimisable but is not first

OpenRouter’s JSON path base64-encodes WAV, adding about one third to payload size. Requests are constructed manually and no application-level connection pool is visible. Direct provider routing, a long-lived client and FLAC only for large files should be benchmarked. Groq itself recommends WAV for low latency and FLAC for size.

P2 — Synchronous GC and buffer copies need measurement

gc.collect() runs after every dictation and meeting/import paths copy large audio arrays. Move full collection to idle/memory-pressure conditions and stream meetings to bounded chunks. These are likely memory and tail-latency wins, not the main median-latency win.

P2 — Copied Windows/macOS/Linux trees multiply performance drift

The current audit already shows substantial port divergence. A performance fix that lands in one mumble.py can fail to reach the others. Shared core services with thin platform adapters are a prerequisite for trustworthy cross-platform tuning.

06 · Prioritised portfolio

Recommended optimisations, in delivery order

  1. Instrument Stop→Paste and create a reproducible corpus

    P0SmallAll OS

    Add one trace ID per utterance and stage timings. Build a fixed corpus spanning 1, 3, 5, 10, 30 and 60 seconds; clean/noisy; English/multilingual; vocabulary terms. This prevents “faster” changes that quietly worsen WER or p95.

    Direct saving: none. Decision value: essential.

  2. Unify routing and make streaming backend-aware

    P0MediumAll OS

    One backend interface: start(), push_pcm(), partial(), finish(), cancel(), health(). Local, native and cloud implementations share fallback and telemetry. Cloud mode never silently invokes local live chunks.

    Expected saving: avoids seconds of surprise local model load; restores the selected cloud latency for >5 s clips.

  3. Adopt duration-aware scheduling

    P1Medium
    • <6 s: one warm pass; avoid a worker that cannot commit useful work. For a true streaming transducer, keep 160/320 ms state instead.
    • 6–45 s: stateful streaming with stable-prefix commit and an explicitly finalised tail.
    • >45 s / files: speech-segment queue + batching + ordered merge + progress checkpoints.

    Expected saving: 1.0–1.5 s after Stop on typical plain dictation; ≈50% CPU compute on long-form batching.

  4. Ship a real Apple Silicon backend

    P1Medium–largemacOS

    Use a small signed Swift sidecar/XPC helper around FluidAudio or Argmax WhisperKit, communicating over stdin/socket with raw PCM and JSON results. Do not depend on unverified Python bridge module names. Retain faster-whisper for Intel Mac and as a fallback.

    Expected saving: conservatively 0.9–1.3 s for short warm dictation; upstream M4 batch throughput indicates >95% for long full passes, pending Mumble integration benchmarks.

  5. Benchmark two Windows/Linux native candidates

    P1SpikeWindows · Linux

    Candidate A: whisper.cpp for a uniform C API with CUDA, Vulkan, ROCm, OpenVINO, Metal/CoreML and quantisation. Candidate B: sherpa-onnx with a genuinely streaming Zipformer/Parakeet model. Keep faster-whisper for NVIDIA and CPU until the corpus proves a better speed/accuracy point.

    Expected saving: 35–75% post-Stop with a streaming model; 20–70% full-pass compute on hardware currently missed by CUDA-only selection. High variance—benchmark required.

  6. Enable adaptive batching for meetings and imports

    P1Medium

    Use BatchedInferencePipeline after VAD segmentation. Start at batch 4 CPU / 8 GPU, increase only within measured RAM/VRAM budgets. Keep ordinary dictation unbatched: batching helps throughput, not one tiny request.

    Expected saving: about 50% CPU or 73% GPU in the cited upstream configurations; not guaranteed for Mumble’s model/hardware.

  7. Calibrate threads and compute type once per device/model

    P1Small–medium

    Try a short set of thread counts bounded by physical cores; cache the fastest result. Compare INT8, INT8-float16 and FP16 only where supported. Re-run after model/runtime/hardware change.

    Expected saving: 5–25% local CPU time; larger p95/battery benefit on hybrid CPUs.

  8. Make plain Text a fast lane

    P1Small

    For ordinary text, apply deterministic vocabulary/punctuation/cleanup and paste. Run a cloud/local LLM only for explicitly selected Prompt/Email/Reply or an opt-in “polish before paste”. If async replacement is considered, require a clear UX and never overwrite user edits.

    Expected saving: one whole LLM request on affected dictations—likely larger than the remaining STT wait, but Mumble does not currently time this stage.

  9. Tune VAD by workload, not globally

    P2Spike

    Push-to-talk short clips may be faster with VAD disabled after clean capture; long audio benefits from a shorter silence threshold and pre-segmentation. A/B WER, clipped first/last words, hallucination rate and RTF before changing defaults.

  10. Bound audio memory and move GC off the critical path

    P2Medium

    Write meeting PCM incrementally, process bounded windows, avoid full float32 duplication, and trigger full GC during idle or on measured pressure. Keep the existing careful clipboard delay until event-based restoration is proven across target apps.

07 · Platform strategy

One shared policy, different acceleration

Keep

  • faster-whisper CPU INT8 fallback.
  • faster-whisper CUDA FP16 for NVIDIA.
  • 16 kHz mono capture and model warm-up.

Add

  • Hardware probe for NVIDIA, AMD and Intel GPU—not just CUDA.
  • whisper.cpp Vulkan/OpenVINO candidate for non-NVIDIA GPUs.
  • sherpa-onnx streaming model candidate for lowest finalisation latency.

The current DirectML file is not deployable as a feature: sherpa-onnx/onnxruntime-directml are not in requirements, the model is not managed by the downloader, and production does not call it. SenseVoice also covers a narrower language set than Whisper, so it cannot silently replace the default.

Apple Silicon

  • Preferred spike: FluidAudio Parakeet EOU for streaming and Parakeet TDT for batch.
  • Alternative: Argmax WhisperKit when Whisper compatibility/language breadth matters.
  • Implement in Swift; package/sign/notarise the helper.

Intel Mac

  • Keep CPU INT8 faster-whisper or benchmark whisper.cpp.
  • Do not show Apple Neural Engine options.
  • Use the same shared duration/router policy.

FluidAudio’s published M4 Pro batch result is roughly 190× real time (one hour in about 19 seconds), and its M2 streaming EOU benchmark reports 19.25× throughput at 320 ms chunks with 4.88% LibriSpeech test-clean WER. These are upstream results, not Mumble measurements.

x86-64 desktop

  • faster-whisper CPU INT8 remains safe.
  • whisper.cpp can expose Vulkan, CUDA, ROCm and OpenVINO from one backend.
  • Detect X11/Wayland only for hotkey/paste; STT policy stays shared.

ARM / small systems

  • Current Vulkan adapter is explicitly a stub.
  • Benchmark quantised whisper.cpp versus small sherpa-onnx streaming models.
  • Prefer bounded memory and a Resource Saver profile.

Do not restrict Linux acceleration to ARM Vulkan as the current selector does. Most desktop Linux users are x86-64, and AMD/NVIDIA/Intel paths matter more.

Do not optimise these first

  • Replacing PortAudio: the existing architecture review estimates only ~5 ms difference—irrelevant next to 1–2 s STT/network waits.
  • Removing clipboard waits without an event-based proof: this risks truncated paste and clipboard corruption for a small gain.
  • Increasing CPU threads further: current selection may already over-subscribe logical/hybrid cores.
  • Enabling heavy noise suppression globally: evaluate WER and a small latency budget first.
  • Making platform adapters “available” by returning true: packaging, models, fallback and native tests are part of the feature.
11 · Benchmark specification

The test needed before promising percentages

Corpus

  • Durations: 1, 3, 5, 10, 30, 60 s; 10, 30, 60 min.
  • Clean headset, laptop mic, fan/café noise, clipped/quiet.
  • Accents and every advertised language.
  • Proper nouns and personal vocabulary.
  • Silence at start/end and mid-sentence pauses.

Metrics

  • Stop→first partial and Stop→Paste p50/p90/p95.
  • RTF, WER/CER, first/last-word loss, seam errors.
  • Cold load, warm load, RSS/VRAM peak, energy.
  • Cloud upload/request breakdown and error/fallback time.
  • Meeting timestamp and speaker accuracy.
