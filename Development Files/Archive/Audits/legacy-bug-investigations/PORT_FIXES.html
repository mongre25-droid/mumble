Port Fixes

◆Scope: Bug-fixes verified against MacMumble/app/ and LinuxMumble/app/ at current HEAD
◆Status: Verified but not applied live — a sync/zip watcher keeps reverting the port dirs
◆Windows: The matching mumble/ fixes were unaffected and are already applied
◆Each fix: a literal find → replace; python -m py_compile every changed file after applying
In plain terms

Mumble ships in three builds: Windows, macOS, and Linux. The Windows build already got a batch of bug-fixes. The Mac and Linux copies need the same fixes — but every time someone edits those folders, a background program on this machine (OneDrive syncing, plus a step that rebuilt MacMumble.zip mid-session) silently rewrites the files back to their old state within seconds. So the fixes below were written down and double-checked, but couldn't actually be saved into the code yet.

This page is the recipe. Pause the sync, then apply each find → replace exactly as written, and run a quick compile check. Nothing here is lost — every fix, file path, and platform note is preserved.

Why these couldn't be applied live. An external process is running (the OneDrive sync service, and MacMumble.zip was rebuilt mid-session) that keeps reverting MacMumble/ and LinuxMumble/ to their committed state within seconds. To apply: pause OneDrive sync (and any sync/zip watcher) for this folder, then make the edits below (or ask Claude to re-apply them). Each is a literal find → replace. After applying, python -m py_compile each changed file.

1macOS fixes — MacMumble/app/

In plain terms

Four fixes for the Mac build. One makes "start at login" actually install itself; one stops the clipboard watcher from quietly burning CPU; one stops Mumble from claiming it pasted when it didn't; and one tells the user when macOS is silently blocking the global hotkeys.

autostart.py — add the missing no-op HIGH

Symptom: autostart never enabled. Append the following after set_enabled. On Windows this method removed a legacy registry Run key; on macOS there's no equivalent, but the shared boot path still calls it unconditionally. Without a definition, the AttributeError it raised was swallowed by _boot()'s try/except and skipped the autostart-enable that follows it — so login autostart was never installed on a fresh install.

Code Append after set_enabled 
def remove_legacy_run_key():
    """No-op on macOS. The Windows edition removed a legacy registry Run key
    here; there's no macOS equivalent. Defined so the shared boot path can call
    it unconditionally — without this, the AttributeError it raised was swallowed
    by _boot()'s try/except and skipped the autostart-enable that follows it,
    so login autostart was never installed on a fresh install."""
    return False

clipboard.py — _clipboard_seq macOS branch idle CPU drain

Symptom: the clipboard watcher never gets a change-counter on macOS, so it can't skip work and shells out to osascript (via ImageGrab.grabclipboard) roughly 1.4×/second forever. The fix adds an NSPasteboard.changeCount() branch — the direct analogue of GetClipboardSequenceNumber — which bumps on every clipboard change. changeCount can legitimately be 0 on a fresh pasteboard, so it's returned as-is (the caller compares for equality).

Code Replace — original (Windows-only branch) 
    try:
        import ctypes
        n = int(ctypes.windll.user32.GetClipboardSequenceNumber())
        return n or None   # 0 == failure / no WINSTA access → always-poll fallback
    except Exception:
        return None
Code With — adds the macOS NSPasteboard fast-path 
    try:
        import ctypes
        n = int(ctypes.windll.user32.GetClipboardSequenceNumber())
        return n or None   # 0 == failure / no WINSTA access → always-poll fallback
    except Exception:
        pass
    try:
        # macOS: NSPasteboard.changeCount() bumps on EVERY clipboard change — the
        # direct analogue of GetClipboardSequenceNumber. Without this the watcher
        # never skips, so it shells out to osascript (via ImageGrab.grabclipboard)
        # ~1.4x/second forever. changeCount can legitimately be 0 on a fresh
        # pasteboard, so return it as-is (the caller compares for equality).
        from AppKit import NSPasteboard
        return int(NSPasteboard.generalPasteboard().changeCount())
    except Exception:
        return None

mumble_mac.py — _focused_editable AX probe false "Pasted!"

Symptom: Mumble reports a successful paste even into a non-editable target. Replace the body of _focused_editable (the comment block ending in return True) with a best-effort AXUIElement probe that falls back to True on any error (so there's no regression when the probe can't tell).

Code New _focused_editable body 
        try:
            from ApplicationServices import (
                AXUIElementCreateSystemWide, AXUIElementCopyAttributeValue)
            import HIServices  # noqa: F401 — ensures the AX symbols are loaded
            syswide = AXUIElementCreateSystemWide()
            err, focused = AXUIElementCopyAttributeValue(
                syswide, "AXFocusedUIElement", None)
            if err or focused is None:
                return True  # can't tell → assume editable (no regression)
            err, role = AXUIElementCopyAttributeValue(focused, "AXRole", None)
            if err or not role:
                return True
            editable = {"AXTextField", "AXTextArea", "AXComboBox", "AXSearchField"}
            return str(role) in editable or str(role) == "AXUnknown"
        except Exception:
            return True

mumble_mac.py — Accessibility-permission check in _boot silent dead hotkeys

Symptom: global hotkeys need macOS Accessibility (and Input Monitoring on recent versions). Without it, pynput's listeners start but receive no events — every hotkey is silently dead with no diagnosis. The fix surfaces a notification instead. Insert after the hotkey-registration for loop, just before self._start_cmd_server().

Code Insert before self._start_cmd_server() 
        # Global hotkeys need macOS Accessibility (and Input Monitoring on recent
        # versions). Without it, pynput's listeners start but receive NO events —
        # every hotkey is silently dead with no diagnosis. Surface it instead.
        try:
            from ApplicationServices import AXIsProcessTrusted
            if not AXIsProcessTrusted():
                self._notify(
                    "Mumble needs Accessibility access",
                    "Turn on Mumble in System Settings → Privacy & Security → "
                    "Accessibility (and Input Monitoring) so the hotkeys work.")
        except Exception:
            pass

2Linux fixes — LinuxMumble/app/

In plain terms

Three fixes for the Linux build. Linux has no cheap way to ask "did the clipboard change?", so the watcher was launching a helper program many times a second. These fixes throttle that, pick the right clipboard tool on modern (Wayland) desktops, and stop Mumble from firing Ctrl+V when there's provably no clipboard backend to paste from.

clipboard.py — throttle image grab + probe for a tool HIGH

Symptom: subprocess every 0.7s. On Linux there is no cheap clipboard change-counter (the Windows sequence-number fast-path returns None), so ImageGrab.grabclipboard() would fork a wl-paste/xclip subprocess on every 0.7s poll forever. The fix probes once for a clipboard tool: if none exists, image polling is disabled entirely (no per-cycle error spam); otherwise it's throttled to a slow cadence. Text-clipboard history is unaffected and still runs each cycle.

Code In __init__, after self._own_hashes = deque(maxlen=120) 
        # On Linux there is no cheap clipboard change-counter (the Windows
        # sequence-number fast-path returns None), so ImageGrab.grabclipboard()
        # would fork a wl-paste/xclip subprocess on EVERY 0.7s poll forever.
        # Probe once for a clipboard tool: if none exists, disable image polling
        # entirely (no per-cycle error spam); otherwise throttle it to a slow
        # cadence. Text-clipboard history is unaffected and still runs each cycle.
        import shutil
        try:
            self._img_ok = any(shutil.which(t) for t in ("wl-paste", "xclip", "xsel"))
        except Exception:
            self._img_ok = False
        if not self._img_ok:
            print("clipboard: no wl-paste/xclip/xsel found — image-clip history "
                  "disabled (text history still works).")
        self._img_every = 8   # ~ every 5.6s at the 0.7s loop interval
        self._img_tick = 0
Code In _loop, after the text-capture block, before grabbed = ImageGrab.grabclipboard() 
                # Image clipboard is throttled on Linux (no cheap change counter;
                # each grab forks wl-paste/xclip), and skipped entirely when no
                # clipboard tool is installed. The image block is the last work in
                # the loop body, so `continue` simply skips it for this cycle.
                self._img_tick += 1
                if not self._img_ok or (self._img_tick % self._img_every) != 0:
                    continue

mumble_linux.py — copy_image Wayland detection MEDIUM

Symptom: wrong clipboard tool. The app pins GDK_BACKEND=x11 on Wayland (so the GTK island renders), which made the old not GDK_BACKEND.startswith("x11") test always False on real Wayland — so an image copy used xclip (XWayland clipboard) even with wl-clipboard installed, and native-Wayland apps couldn't paste it. The fix uses the INPUT session type instead of GDK_BACKEND.

Code Replace — original (GDK_BACKEND test) 
        wayland = bool(os.environ.get("WAYLAND_DISPLAY")) and \
            not os.environ.get("GDK_BACKEND", "").startswith("x11")
Code With — session-type detection 
        # Use the INPUT session type, NOT GDK_BACKEND: the app pins
        # GDK_BACKEND=x11 on Wayland (so the GTK island renders), which made the
        # old `not GDK_BACKEND.startswith("x11")` test always False on real
        # Wayland — so an image copy used xclip (XWayland clipboard) even with
        # wl-clipboard installed, and native-Wayland apps couldn't paste it.
        try:
            wayland = bindings._session_type() == "wayland"
        except Exception:
            wayland = bool(os.environ.get("WAYLAND_DISPLAY"))

mumble_linux.py — pyperclip backend probe + paste guard MEDIUM

Symptom: blind Ctrl+V pastes stale content. On a headless or minimal Linux box no pyperclip backend exists (xclip/xsel/wl-clipboard/qt/gtk), so clipboard writes fail and a blind Ctrl+V would paste stale content. The probe is conservative: only the explicit "no mechanism" error marks it unavailable; any other error assumes a backend exists, so a paste is never wrongly suppressed.

Code In __init__, after self.clipboard = Clipboard(...) 
        # Probe once for a pyperclip clipboard backend (xclip/xsel/wl-clipboard/
        # qt/gtk). On a headless or minimal Linux box none exists, so clipboard
        # writes fail and a blind Ctrl+V would paste stale content. Conservative:
        # only the explicit "no mechanism" error marks it unavailable; any other
        # error assumes a backend exists so we never wrongly suppress a paste.
        try:
            import pyperclip as _pc
            try:
                _pc.paste()
                self._pyperclip_ok = True
            except _pc.PyperclipException:
                self._pyperclip_ok = False
                print("clipboard: no pyperclip backend found (install xclip/xsel "
                      "or wl-clipboard) — text paste will be limited.")
            except Exception:
                self._pyperclip_ok = True
        except Exception:
            self._pyperclip_ok = True
Code In _paste_impl — capture the write result and bail when no backend 
            wrote = self._set_clipboard(text)
            if not wrote and not self._pyperclip_ok:
                # No clipboard backend at all: the write provably failed, so
                # firing Ctrl+V would paste whatever stale content is on the
                # clipboard. Skip it and report not-landed so the caller shows the
                # honest "Saved · …" fallback instead of a paste that didn't happen.
                print("paste skipped: no clipboard backend available")
                return False

Change the existing self._set_clipboard(text) call (the one right before the modifier-release loop) to the guarded version above.

3Notes — skipped & shared modules

In plain terms

A couple of tiny issues were deliberately left alone because they don't actually bite in practice. And there's a shortcut: many of these bugs also live in the files shared across all three builds, so copying those shared files over from the Windows folder brings the Windows fixes along for free.

Skipped as cosmetic / masked in practice

  • The small.en vs base.en default-model literal mismatch — settings.py always populates model, so it's never hit.

Apply those too if you want strict cleanliness.

Shared modules — bring the ports to parity

The shared modules (ai.py, transcription.py, presets.py, reader_store.py, the Reader UI) carry the same bugs the Windows fixes addressed. If you bring the ports to parity by copying those from mumble/, the Windows fixes come with them.
