Builder's guide

Mumble's runtime is in Internal/app/. The development material is separate so the shipped application remains easy to identify. Windows is the reference platform; macOS and Linux provide focused platform seams.

1Session routine

1
Orient

Read the current Core records and inspect the exact source and tests involved.

2
Change

Make one bounded change. Keep runtime code, UI, tests, ports, and product claims consistent.

3
Verify

Reach the evidence level required for this stage: focused confidence for an isolated candidate, combined evidence after candidates converge, and final acceptance before release.

4
Record

Update STATUS for open work, HANDBOOK for procedure changes, README for product/layout changes, and LOGS for completed milestones.

Accepted samples enter a bounded queue; one writer forms 30-second default immutable PCM16 segments through the Stage A lock/flush/checksum/atomic-replace contract. Startup recovery uses the same timestamp ownership rule with local transcription, saves once to History, and never replays an insertion that may already have been sent. Content-free trace summaries report p50/p90/p95/max by versioned corpus, split cold and warm model-residency distributions, and identify the largest measured stage for each lifecycle. The accelerated corpus drives real controller start/callback/Stop trace emission with deterministic audio and time rather than claiming physical latency.

Exactly two reusable child processes isolate native Windows Search SystemIndex/ADO work; the provider worker initializes and balances COM, an ignored deadline remains honestly owned, and final application shutdown terminates and joins both children. Every shortcut action carries one operation identity; the resident keeps a locked, bounded terminal-outcome store so lost replies and concurrent duplicate delivery cannot apply a second toggle. Focus restoration revalidates HWND, thread, process, and process-creation identity without bypassing Windows foreground or privilege policy, and it never changes the Issue #15 insertion lease. Current deadlines and occupied provider capacity preserve usable app-only results; only replaced generations are superseded. Its local no-match, degraded, and error states remain local. Shortcut registration, migration, toggling, and live rebinding are independent; a collision preserves the prior live binding. 3Privacy and safety boundaries

  • Local transcription keeps recorded audio on the device unless Cloud transcription is selected.
  • processing_route.py is the authority for Dictation, Prompt, Email, Reply, Deck, Meetings, Reader summary, Reader speech, and future text-shaping routes. Do not reconstruct provider permission inside a feature.
  • The immutable input snapshot records the requested/effective route and freezes routing, readiness, language, vocabulary, user/prompt preferences, and gathered context for the whole invocation.
  • Private or user-derived snapshot fields, including credentials, name, vocabulary, preferences, context, and mode configuration, must stay out of repr, logs, UI payloads, and public_dict.
  • Every actual provider adapter requires and validates the frozen decision, including a direct feature or test call. It must reject device-only, hosted-off, missing-key, unsupported-provider, and provider-mismatch decisions before egress.
  • Reader speech fallback may try a compatible model only within the frozen provider; it must never cross to another provider.
  • Cloud processing receives text, not raw audio, unless the explicitly selected Cloud transcription path is being used.
  • Provider keys belong only in local settings and must never be committed or logged.
  • The Settings page must fail closed as one actionable subtree while its initial state is loading or failed; a successful current hydration response is the only event that restores actions.
  • The local command channel is authenticated per session; do not replace it with unauthenticated control.
  • Target-bound exact-once delivery uses one deep insertion module with begin, deliver, and status-only status seams. Ordinary dictation captures one immutable destination and operation identity at Stop and carries both through delayed mode selection and shaping; Deck captures before dismissal and may restore a retained target only when Mumble demonstrably displaced it. Native identity includes the foreground window, process, thread, focused child, and process-creation identity. Focused UI Automation runtime identity is optional supporting evidence: equal evidence strengthens the match and reliably different evidence proves a changed field, but missing, timed-out, transient, or one-sided UI Automation evidence never blocks a stable native target. Control class, caret, editability, read-only, and protected signals are diagnostics or adapter-selection inputs, not global eligibility gates.
  • Clipboard text, image, and rich payload plus counted Ctrl+V is the first adapter. The complete snapshot acquisition uses one absolute monotonic deadline and reads every supported format under one successful clipboard open; it does not restart the wait budget per format. The adapter preserves a restorable snapshot, writes the exact payload, and restores only while Mumble still owns it. A text operation may use counted direct Unicode input only after clipboard delivery proves that it sent nothing; image and rich payloads have no direct-input fallback. Every adapter records NO_SEND, MAY_HAVE_SENT, or SENT, and only NO_SEND permits another adapter.
  • A known higher-integrity destination routes to the private elevated-helper seam. The immediate candidate deliberately ships no helper: it reports Permission needed — saved in Mumble. Installing, authenticating, signing, packaging, and physically validating that helper is a dependent stage.
  • Deck text and image submission uses one operation identity and fingerprint. A bridge timeout polls that same operation without resubmitting input, then returns either one authoritative terminal result or an explicit bounded unknown result that tells the user not to retry automatically.
  • The prior clipboard is restored only when an ownership check inside the same open-clipboard critical section, immediately before clearing, still matches Mumble's temporary sequence and exact payload fingerprint. The result explicitly distinguishes restored, skipped because newer external ownership was observed, and failed restoration. Normal completion, early exit, text, image, rich payload, and owned partial-write recovery use this rule; if ownership cannot be proved, Mumble does not clear the clipboard. Text writes also request exclusion from Windows clipboard history and Cloud Clipboard, but this is not protection from third-party clipboard managers.
  • One insertion-module lock and registry owns prepared, pending, unknown, and terminal lifecycle truth. Delivery receives one monotonic pending deadline; status, repeat delivery, abandonment, and capacity cleanup consult that same authority. Expiry publishes explicit unknown truth without resubmission, while a late completion from the original attempt may publish its truthful terminal result. Exact records and fixed-memory replay protection stay bounded, so neither polling nor cleanup can authorize another native send.

Web Search privacy boundary: selected or dictated words remain in one bounded local request until the centred UI names the frozen provider and the user chooses Search online. Keep-private, expiry, replay, or consent-surface failure makes no browser request. Mumble Find must never call that seam or turn a local no-match into online work.

Chromium focused-element correction: one long-lived Windows UI Automation client remains on its owning COM thread so runtime identities stay comparable across Stop/Finish-time captures. Only one capture may be outstanding; after a timeout, later requests return timed out until the existing work completes instead of accumulating. Each capture samples at most four times, rejects returned Chromium container elements that do not report keyboard focus, and publishes only the first two consecutive matching keyboard-focused runtime identities. An observed sequence that never settles is explicit unstable evidence and cannot authorize input or exact restoration. A differing focused runtime identity remains blocking, including when reusable leaf metadata such as Automation ID, class, type, or rectangle happens to match; missing, timed-out, transient, or one-sided UI Automation evidence remains non-gating for a stable native target.

4Risk-based evidence policy

Mumble uses three evidence levels. The aim is to run the smallest checks that can expose the likely defect during isolated work, then spend broader test time once several reviewed candidates have been brought together. Moving up a level adds evidence; it does not erase an earlier failure or turn an unavailable physical check into a pass.

Level A — Focused confidence

Level A is the normal target for one implementation, correction, or independent focused review. It is enough to decide whether an isolated candidate should be corrected or accepted for later convergence, but it is never full-product proof.

  • Add and run a red/green regression for the reported defect when feasible: first show that the check detects the old failure, then show that the candidate passes it.
  • Test the changed behaviour at its direct production boundary, plus one nearby caller or integration smoke check.
  • Check syntax, compilation or static validity for changed paths, inspect the candidate diff, and run clean-diff and whitespace checks.
  • Run one deterministic browser, native, or accessibility check only when that surface is directly relevant.
  • Risk floor: privacy, security, credential authorization, clipboard or data-loss, migrations, installers, and destructive paths must always run their critical targeted safety checks. Small scope is not permission to omit them.
Boundary: Level A can support an isolated task candidate and its independent review. It does not prove full regression safety, platform parity, packaging, physical use, exact-head CI, deployment, or release.

Level B — Combined candidate

Level B begins after several independently accepted candidates are converged onto the latest verified main. It checks interactions that isolated work cannot prove.

  • Run one serialized trusted full suite per host, relevant integration/browser/native smokes, package membership and extraction checks, conflict-sensitive tests, and exact-head CI.
  • Never overlap two Mumble full runners on the same host.
  • Retain the first failure in machine-readable output. Do not rerun merely to obtain green; explain and investigate the earlier red result first.
  • Level B may support merge when the issue contract is satisfied. Physical use, owner acceptance, deployment, and release remain separate gates.

Level C — Final acceptance

Level C completes the feature and platform ledger before release. It covers real applications and hardware, Linux desktop matrices where available, physical macOS/signing/notarization gates where available, installers and lifecycle/update behaviour, performance, accessibility, security and licence evidence, plus deployment and release evidence.

MachineFinal-campaign responsibility
Windows PCFocus, clipboard, hotkeys, microphone, UI, Office, Electron, real Windows applications, accessibility tools, and Windows packaging.
Linux VPSHeadless full suites, Linux packages, static/security/licence checks, deterministic builds, and long benchmarks.

Duplicate only the highest-risk platform-neutral contracts across both machines. The Linux VPS does not prove Windows desktop behaviour, and neither machine proves physical macOS behaviour, signing, or notarization. Missing devices, owner decisions, credentials, or signing identities remain truthful blockers.

Evidence receipt for every issue or session handoff

Every issue or feature must keep a durable receipt so a later reviewer can see exactly what was and was not proved. Record:

  • the issue or feature name;
  • the exact candidate commit and its parent or base;
  • the evidence level achieved;
  • the host, platform, and relevant environment;
  • the exact focused checks and results;
  • failures, timeouts, and unavailable checks, including the retained first failure;
  • package, CI, and physical-test status;
  • untested gates and the next required evidence level; and
  • whether the candidate is isolated, accepted for convergence, merged to main, green in exact-head CI, physically accepted, deployed, or released.

Detailed per-issue receipts belong in GitHub issue comments. STATUS is the compact programme ledger. LOGS records only meaningful completed milestones, not each test session.

Shared-resource scheduling

  • Allow only one full Mumble runner per host. Before starting one, inspect running processes for another Mumble full runner and wait if one exists.
  • Serialize browser, native, clipboard, and focus tests on the Windows desktop because they compete for the same visible session and operating-system state.
  • Parallel sessions may read, inspect code, run isolated focused checks, or implement non-conflicting work.
  • Use test-owned temporary data. Do not connect tests to the live Mumble controller or a real provider.
  • Do not rerun an unexplained red check solely to obtain a green result.

5Shared Web UI foundation

The packaged Web UI has one Focus Stage foundation in webui/focus-stage.js and webui/focus-stage.css. It keeps the six primary destinations centred, provides reusable state and control contracts, and applies the same focus, reduced-motion, and forced-colour rules across existing pages. The Home dictation workflow uses the Control Rail for its actions and one persistent State Surface while recording or reporting an error. Unchanged controller polls do not replace or mutate that live region; real state, message, and recovery-action changes update it in place while preserving focus. Individual page redesigns remain separate work; use the foundation rather than introducing an alternate application shell.

The effects setting maps its existing lite, standard, and enhanced values to the public Focus Stage light, standard, and full tiers. The contract records gold/green/red status semantics and permits at most one primary action on a state surface.

Stats and Reader reuse that foundation without replacing their established information architecture. Stats must identify when its snapshot was generated, define measured or estimated metrics, keep unavailable sections distinct from genuine zero activity, and retain text-table chart alternatives. Reader remains library-first; voice and speed are the primary human choices, provider/model details stay secondary, and closing Find or Summary restores a useful focus target without moving the saved reading or playback position.

Development Files/Tooling/focus-stage/verify-production-ui.ps1 opens the real packaged webui/index.html in a browser. It is deliberately not a prototype test: it checks navigation, state anatomy, persistent live-region behaviour, keyboard and dialog behaviour, browser-managed 200% tab zoom, narrow reflow, effects, contrast, reduced motion, forced colours, production Control Rail/State Surface use, and screenshots. The focused -Case stats-reader path covers Stats loading/no-data/partial-data truth, Reader ordering and focus restoration, narrow reflow, reduced motion, and deterministic screenshots. The zoom probe uses Chromium's own chrome.tabs.setZoom API in automatic per-tab mode: Chromium must report factor 2, the effective CSS viewport must change from 1440×1000 to 720×500, the pixel scale must change from 1 to 2, document CSS zoom must remain 1, and the physical screenshot surface must remain 1440×1000. This is separate from the narrow-viewport checks.

Add -Capture only after the production sequence is final and refreshed evidence images are wanted. Each capture is repeated in the same browser session for pixel determinism, and evidence-manifest.json binds the committed image hashes to the exact production UI and harness source hashes. This automated evidence does not verify a physical display, operating-system display scaling, assistive-technology output, microphone input, hardware hotkeys, paste, or clipboard restoration.

The runner discovers every matching module and chooses its execution protocol: pytest and unittest modules run through pytest so every collected case is counted; legacy procedural scripts run as one atomic module case because their internal checks do not expose a standard machine-readable count. A pytest/unittest module that collects zero cases fails. JSON records both module and case totals, while JUnit records each standard case for GitHub and other reporting tools.

A full runner belongs at Level B or Level C unless a critical Level A risk cannot be tested safely any other way. Every result is evidence for the checked environment only; it does not prove physical hardware behaviour or a public release.

7Continuous integration evidence

The GitHub workflow runs security audits, application tests, website checks, Windows website-checkout cleanliness, platform packaging, and the Linux install lifecycle as independent jobs. The Windows cleanliness job creates a fresh short-path checkout with core.autocrlf=true, installs the exact lock, runs the maintained release check, build, and Astro diagnostics, confirms the required declarations were regenerated under ignored .astro/, and requires empty final porcelain. Test JSON and JUnit are diagnostic artifacts and may be uploaded after failure. Package and website candidates are uploaded only by successful jobs. A candidate becomes promotable only in a manually started workflow where every required evidence job succeeds.

Linux tests use a system-site-packages virtual environment because GTK and Ayatana AppIndicator are operating-system libraries installed through Ubuntu, while Python-only test dependencies such as psutil remain pinned in requirements-dev.txt. Installed-package smoke imports must run from the extracted app/ directory so they verify the packaged import layout rather than the repository checkout.

A green local run is not a green GitHub run. Before using CI artifacts for release preparation, verify that the successful workflow commit exactly matches the reviewed commit.

8Packaging and ports

The website's .astro/ directory is generated metadata, not maintained source. Keep it untracked and covered only by Development Files/Marketing/Website/.gitignore; astro build and astro check regenerate required declarations such as content.d.ts and types.d.ts. Do not restore generated declarations after verification or use a repository-wide line-ending workaround.

Development Files/Tooling/_rebuild_zip.py builds Internal/Releases/Mumble.zip deterministically from the live runtime, then copies those exact bytes to Development Files/Marketing/Website/public/Mumble.zip. The maintained website destination must already exist; a missing destination is a visible build failure and the builder must not recreate an unexpected project structure. The builder normalizes supported packaged text files to LF line endings independently of the source checkout while preserving binary bytes unchanged. It includes the launcher, project licence, Internal launchers, runtime, and processing_route.py while excluding tests, ports, caches, virtual environments, and development-only files. test_release_builder.py keeps the required destination and byte-identity boundary under regression coverage.

Internal/app/processing_route.py is the authoritative maintained processing-route source. Run Development Files/Tooling/sync_processing_route.py to generate normalized macOS/Linux copies and --check to detect drift; do not edit three independent implementations.

macOS and Linux source lives under Internal/app/Ports/. Each port owns its input, paste, overlay, storage, installer, and release seams. Shared behaviour should be changed in the Windows source first, then ported deliberately and tested in that platform. Their offline builders must produce reproducible archives, verify membership and integrity, and support a clean extracted import. Those checks do not prove installation, signing, notarization, or physical use.

9Release discipline

  1. Verify the source tree and package from a clean, reviewable state.
  2. Run clean extraction, install, launch, update, and uninstall checks.
  3. Test microphone, hotkeys, focus, paste, clipboard restoration, and shutdown on physical hardware.
  4. Complete signing, publisher, release-note, and rollback checks.
  5. Only then describe the build as a public release.
