Builder's guide

Mumble's runtime is in Internal/app/. The development material is separate so the shipped application remains easy to identify. Windows is the reference platform; macOS and Linux provide focused platform seams.

1Session routine

1
Orient

Read the current Core records and inspect the exact source and tests involved.

2
Change

Make one bounded change. Keep runtime code, UI, tests, ports, and product claims consistent.

3
Verify

Reach the evidence level required for this stage: focused confidence for an isolated candidate, combined evidence after candidates converge, and final acceptance before release.

4
Record

Update STATUS for open work, HANDBOOK for procedure changes, README for product/layout changes, and LOGS for completed milestones.

3Privacy and safety boundaries

  • Local transcription keeps recorded audio on the device unless Cloud transcription is selected.
  • Cloud processing receives text, not raw audio, unless the explicitly selected Cloud transcription path is being used.
  • Provider keys belong only in local settings and must never be committed or logged.
  • The local command channel is authenticated per session; do not replace it with unauthenticated control.
  • Paste must preserve the user's clipboard and modifier state when the operation completes or fails.

4Risk-based evidence policy

Mumble uses three evidence levels. The aim is to run the smallest checks that can expose the likely defect during isolated work, then spend broader test time once several reviewed candidates have been brought together. Moving up a level adds evidence; it does not erase an earlier failure or turn an unavailable physical check into a pass.

Level A — Focused confidence

Level A is the normal target for one implementation, correction, or independent focused review. It is enough to decide whether an isolated candidate should be corrected or accepted for later convergence, but it is never full-product proof.

  • Add and run a red/green regression for the reported defect when feasible: first show that the check detects the old failure, then show that the candidate passes it.
  • Test the changed behaviour at its direct production boundary, plus one nearby caller or integration smoke check.
  • Check syntax, compilation or static validity for changed paths, inspect the candidate diff, and run clean-diff and whitespace checks.
  • Run one deterministic browser, native, or accessibility check only when that surface is directly relevant.
  • Risk floor: privacy, security, credential authorization, clipboard or data-loss, migrations, installers, and destructive paths must always run their critical targeted safety checks. Small scope is not permission to omit them.
Boundary: Level A can support an isolated task candidate and its independent review. It does not prove full regression safety, platform parity, packaging, physical use, exact-head CI, deployment, or release.

Level B — Combined candidate

Level B begins after several independently accepted candidates are converged onto the latest verified main. It checks interactions that isolated work cannot prove.

  • Run one serialized trusted full suite per host, relevant integration/browser/native smokes, package membership and extraction checks, conflict-sensitive tests, and exact-head CI.
  • Never overlap two Mumble full runners on the same host.
  • Retain the first failure in machine-readable output. Do not rerun merely to obtain green; explain and investigate the earlier red result first.
  • Level B may support merge when the issue contract is satisfied. Physical use, owner acceptance, deployment, and release remain separate gates.

Level C — Final acceptance

Level C completes the feature and platform ledger before release. It covers real applications and hardware, Linux desktop matrices where available, physical macOS/signing/notarization gates where available, installers and lifecycle/update behaviour, performance, accessibility, security and licence evidence, plus deployment and release evidence.

MachineFinal-campaign responsibility
Windows PCFocus, clipboard, hotkeys, microphone, UI, Office, Electron, real Windows applications, accessibility tools, and Windows packaging.
Linux VPSHeadless full suites, Linux packages, static/security/licence checks, deterministic builds, and long benchmarks.

Duplicate only the highest-risk platform-neutral contracts across both machines. The Linux VPS does not prove Windows desktop behaviour, and neither machine proves physical macOS behaviour, signing, or notarization. Missing devices, owner decisions, credentials, or signing identities remain truthful blockers.

Evidence receipt for every issue or session handoff

Every issue or feature must keep a durable receipt so a later reviewer can see exactly what was and was not proved. Record:

  • the issue or feature name;
  • the exact candidate commit and its parent or base;
  • the evidence level achieved;
  • the host, platform, and relevant environment;
  • the exact focused checks and results;
  • failures, timeouts, and unavailable checks, including the retained first failure;
  • package, CI, and physical-test status;
  • untested gates and the next required evidence level; and
  • whether the candidate is isolated, accepted for convergence, merged to main, green in exact-head CI, physically accepted, deployed, or released.

Detailed per-issue receipts belong in GitHub issue comments. STATUS is the compact programme ledger. LOGS records only meaningful completed milestones, not each test session.

Shared-resource scheduling

  • Allow only one full Mumble runner per host. Before starting one, inspect running processes for another Mumble full runner and wait if one exists.
  • Serialize browser, native, clipboard, and focus tests on the Windows desktop because they compete for the same visible session and operating-system state.
  • Parallel sessions may read, inspect code, run isolated focused checks, or implement non-conflicting work.
  • Use test-owned temporary data. Do not connect tests to the live Mumble controller or a real provider.
  • Do not rerun an unexplained red check solely to obtain a green result.

Reference commands

Run only the command that matches the required evidence level. These examples run from C:\Mumble and do not publish anything.

# Full isolated application suite with machine-readable evidence
Internal\app\.venv\Scripts\python.exe Internal\app\run_tests.py --timeout 180 --json Internal\app\test-results.json --junit Internal\app\test-results.xml

# Compile Python without running the application
Internal\app\.venv\Scripts\python.exe -m compileall -q Internal\app

# Rebuild and verify the Windows distributable
Internal\app\.venv\Scripts\python.exe "Development Files\Tooling\_rebuild_zip.py" C:\Mumble

# Verify Windows launcher paths and startup contract
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "Development Files\Tooling\verify_windows_launch.ps1"

# Website checks
Set-Location "Development Files\Marketing\Website"
npm ci
npm run build
npx astro check
npm audit --audit-level=moderate

The runner discovers every matching module and chooses its execution protocol: pytest and unittest modules run through pytest so every collected case is counted; legacy procedural scripts run as one atomic module case because their internal checks do not expose a standard machine-readable count. A pytest/unittest module that collects zero cases fails. JSON records both module and case totals, while JUnit records each standard case for GitHub and other reporting tools.

A full runner belongs at Level B or Level C unless a critical Level A risk cannot be tested safely any other way. Every result is evidence for the checked environment only; it does not prove physical hardware behaviour or a public release.

5Continuous integration evidence

The GitHub workflow runs security audits, application tests, website checks, platform packaging, and the Linux install lifecycle as independent jobs. Test JSON and JUnit are diagnostic artifacts and may be uploaded after failure. Package and website candidates are uploaded only by successful jobs. A candidate becomes promotable only in a manually started workflow where every required evidence job succeeds.

Linux tests use a system-site-packages virtual environment because GTK and Ayatana AppIndicator are operating-system libraries installed through Ubuntu, while Python-only test dependencies such as psutil remain pinned in requirements-dev.txt. Installed-package smoke imports must run from the extracted app/ directory so they verify the packaged import layout rather than the repository checkout.

A green local run is not a green GitHub run. Before using CI artifacts for release preparation, verify that the successful workflow commit exactly matches the reviewed commit.

6Packaging and ports

Development Files/Tooling/_rebuild_zip.py builds Internal/Releases/Mumble.zip from the live runtime. It includes the launcher, project licence, Internal launchers, and runtime while excluding tests, ports, caches, virtual environments, and development-only files.

macOS and Linux source lives under Internal/app/Ports/. Each port owns its input, paste, overlay, storage, installer, and release seams. Shared behaviour should be changed in the Windows source first, then ported deliberately and tested in that platform.

7Release discipline

  1. Verify the source tree and package from a clean, reviewable state.
  2. Run clean extraction, install, launch, update, and uninstall checks.
  3. Test microphone, hotkeys, focus, paste, clipboard restoration, and shutdown on physical hardware.
  4. Complete signing, publisher, release-note, and rollback checks.
  5. Only then describe the build as a public release.
