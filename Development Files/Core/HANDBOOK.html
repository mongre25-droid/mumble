Builder's guide

Mumble's runtime is in Internal/app/. The development material is separate so the shipped application remains easy to identify. Windows is the reference platform; macOS and Linux provide focused platform seams.

1Session routine

1
Orient

Read the current Core records and inspect the exact source and tests involved.

2
Change

Make one bounded change. Keep runtime code, UI, tests, ports, and product claims consistent.

3
Verify

Reach the evidence level required for this stage: focused confidence for an isolated candidate, combined evidence after candidates converge, and final acceptance before release.

4
Record

Update STATUS for open work, HANDBOOK for procedure changes, README for product/layout changes, and LOGS for completed milestones.

3Privacy and safety boundaries

  • Local transcription keeps recorded audio on the device unless Cloud transcription is selected.
  • processing_route.py is the authority for Dictation, Prompt, Email, Reply, Deck, Meetings, Reader summary, Reader speech, and future text-shaping routes. Do not reconstruct provider permission inside a feature.
  • The immutable input snapshot records the requested/effective route and freezes routing, readiness, language, vocabulary, user/prompt preferences, and gathered context for the whole invocation.
  • Private or user-derived snapshot fields, including credentials, name, vocabulary, preferences, context, and mode configuration, must stay out of repr, logs, UI payloads, and public_dict.
  • Every actual provider adapter requires and validates the frozen decision, including a direct feature or test call. It must reject device-only, hosted-off, missing-key, unsupported-provider, and provider-mismatch decisions before egress.
  • Reader speech fallback may try a compatible model only within the frozen provider; it must never cross to another provider.
  • Cloud processing receives text, not raw audio, unless the explicitly selected Cloud transcription path is being used.
  • Provider keys belong only in local settings and must never be committed or logged.
  • The Settings page must fail closed as one actionable subtree while its initial state is loading or failed; a successful current hydration response is the only event that restores actions.
  • The local command channel is authenticated per session; do not replace it with unauthenticated control.
  • Target-bound exact-once delivery uses one deep insertion module with begin, deliver, and status-only status seams. Ordinary dictation captures one immutable destination and operation identity at Stop and carries both through delayed mode selection and shaping; Deck captures before dismissal and may restore a retained target only when Mumble demonstrably displaced it. Native identity includes the foreground window, process, thread, focused child, and process-creation identity. Focused UI Automation runtime identity is optional supporting evidence: equal evidence strengthens the match and reliably different evidence proves a changed field, but missing, timed-out, transient, or one-sided UI Automation evidence never blocks a stable native target. Control class, caret, editability, read-only, and protected signals are diagnostics or adapter-selection inputs, not global eligibility gates.
  • Clipboard text, image, and rich payload plus counted Ctrl+V is the first adapter. The complete snapshot acquisition uses one absolute monotonic deadline and reads every supported format under one successful clipboard open; it does not restart the wait budget per format. The adapter preserves a restorable snapshot, writes the exact payload, and restores only while Mumble still owns it. A text operation may use counted direct Unicode input only after clipboard delivery proves that it sent nothing; image and rich payloads have no direct-input fallback. Every adapter records NO_SEND, MAY_HAVE_SENT, or SENT, and only NO_SEND permits another adapter.
  • A known higher-integrity destination routes to the private elevated-helper seam. The immediate candidate deliberately ships no helper: it reports Permission needed — saved in Mumble. Installing, authenticating, signing, packaging, and physically validating that helper is a dependent stage.
  • Deck text and image submission uses one operation identity and fingerprint. A bridge timeout polls that same operation without resubmitting input, then returns either one authoritative terminal result or an explicit bounded unknown result that tells the user not to retry automatically.
  • The prior clipboard is restored only when an ownership check inside the same open-clipboard critical section, immediately before clearing, still matches Mumble's temporary sequence and exact payload fingerprint. The result explicitly distinguishes restored, skipped because newer external ownership was observed, and failed restoration. Normal completion, early exit, text, image, rich payload, and owned partial-write recovery use this rule; if ownership cannot be proved, Mumble does not clear the clipboard. Text writes also request exclusion from Windows clipboard history and Cloud Clipboard, but this is not protection from third-party clipboard managers.
  • One insertion-module lock and registry owns prepared, pending, unknown, and terminal lifecycle truth. Delivery receives one monotonic pending deadline; status, repeat delivery, abandonment, and capacity cleanup consult that same authority. Expiry publishes explicit unknown truth without resubmission, while a late completion from the original attempt may publish its truthful terminal result. Exact records and fixed-memory replay protection stay bounded, so neither polling nor cleanup can authorize another native send.

Web Search privacy boundary: selected or dictated words remain in one bounded local request until the centred UI names the frozen provider and the user chooses Search online. Keep-private, expiry, replay, or consent-surface failure makes no browser request. Mumble Find must never call that seam or turn a local no-match into online work.

Chromium focused-element correction: one long-lived Windows UI Automation client remains on its owning COM thread so runtime identities stay comparable across Stop/Finish-time captures. Only one capture may be outstanding; after a timeout, later requests return timed out until the existing work completes instead of accumulating. Each capture samples at most four times, rejects returned Chromium container elements that do not report keyboard focus, and publishes only the first two consecutive matching keyboard-focused runtime identities. An observed sequence that never settles is explicit unstable evidence and cannot authorize input or exact restoration. A differing focused runtime identity remains blocking, including when reusable leaf metadata such as Automation ID, class, type, or rectangle happens to match; missing, timed-out, transient, or one-sided UI Automation evidence remains non-gating for a stable native target.

4Risk-based evidence policy

Mumble uses three evidence levels. The aim is to run the smallest checks that can expose the likely defect during isolated work, then spend broader test time once several reviewed candidates have been brought together. Moving up a level adds evidence; it does not erase an earlier failure or turn an unavailable physical check into a pass.

Level A — Focused confidence

Level A is the normal target for one implementation, correction, or independent focused review. It is enough to decide whether an isolated candidate should be corrected or accepted for later convergence, but it is never full-product proof.

  • Add and run a red/green regression for the reported defect when feasible: first show that the check detects the old failure, then show that the candidate passes it.
  • Test the changed behaviour at its direct production boundary, plus one nearby caller or integration smoke check.
  • Check syntax, compilation or static validity for changed paths, inspect the candidate diff, and run clean-diff and whitespace checks.
  • Run one deterministic browser, native, or accessibility check only when that surface is directly relevant.
  • Risk floor: privacy, security, credential authorization, clipboard or data-loss, migrations, installers, and destructive paths must always run their critical targeted safety checks. Small scope is not permission to omit them.
Boundary: Level A can support an isolated task candidate and its independent review. It does not prove full regression safety, platform parity, packaging, physical use, exact-head CI, deployment, or release.

Level B — Combined candidate

Level B begins after several independently accepted candidates are converged onto the latest verified main. It checks interactions that isolated work cannot prove.

  • Run one serialized trusted full suite per host, relevant integration/browser/native smokes, package membership and extraction checks, conflict-sensitive tests, and exact-head CI.
  • Never overlap two Mumble full runners on the same host.
  • Retain the first failure in machine-readable output. Do not rerun merely to obtain green; explain and investigate the earlier red result first.
  • Level B may support merge when the issue contract is satisfied. Physical use, owner acceptance, deployment, and release remain separate gates.

Level C — Final acceptance

Level C completes the feature and platform ledger before release. It covers real applications and hardware, Linux desktop matrices where available, physical macOS/signing/notarization gates where available, installers and lifecycle/update behaviour, performance, accessibility, security and licence evidence, plus deployment and release evidence.

MachineFinal-campaign responsibility
Windows PCFocus, clipboard, hotkeys, microphone, UI, Office, Electron, real Windows applications, accessibility tools, and Windows packaging.
Linux VPSHeadless full suites, Linux packages, static/security/licence checks, deterministic builds, and long benchmarks.

Duplicate only the highest-risk platform-neutral contracts across both machines. The Linux VPS does not prove Windows desktop behaviour, and neither machine proves physical macOS behaviour, signing, or notarization. Missing devices, owner decisions, credentials, or signing identities remain truthful blockers.

Evidence receipt for every issue or session handoff

Every issue or feature must keep a durable receipt so a later reviewer can see exactly what was and was not proved. Record:

  • the issue or feature name;
  • the exact candidate commit and its parent or base;
  • the evidence level achieved;
  • the host, platform, and relevant environment;
  • the exact focused checks and results;
  • failures, timeouts, and unavailable checks, including the retained first failure;
  • package, CI, and physical-test status;
  • untested gates and the next required evidence level; and
  • whether the candidate is isolated, accepted for convergence, merged to main, green in exact-head CI, physically accepted, deployed, or released.

Detailed per-issue receipts belong in GitHub issue comments. STATUS is the compact programme ledger. LOGS records only meaningful completed milestones, not each test session.

Shared-resource scheduling

  • Allow only one full Mumble runner per host. Before starting one, inspect running processes for another Mumble full runner and wait if one exists.
  • Serialize browser, native, clipboard, and focus tests on the Windows desktop because they compete for the same visible session and operating-system state.
  • Parallel sessions may read, inspect code, run isolated focused checks, or implement non-conflicting work.
  • Use test-owned temporary data. Do not connect tests to the live Mumble controller or a real provider.
  • Do not rerun an unexplained red check solely to obtain a green result.

One release-provenance contract

Development Files/Tooling/release_provenance.py is the single machine-readable provenance authority for every package format the project actually supports: Windows x86_64 ZIP, macOS arm64 ZIP, macOS x86_64 ZIP, Linux x86_64 tar.gz, and Linux x86_64 ZIP. Builders must call generate_release_provenance(...), embed its canonical UTF-8 RELEASE-PROVENANCE.json, and call validate_release_provenance(provenance_bytes, repo_root=..., members=...) against the completed archive. The schema identity is mumble.release-provenance.v1. A builder must not keep a private schema copy or silently accept another platform/architecture/format tuple.

Each provenance document binds one full Git commit and an input-closure digest to the exact platform, architecture, format, entry point, optional installer/uninstaller, and every payload member except the provenance document itself. The ordered member manifest records canonical POSIX path, SHA-256, byte size, and permission mode. It also names every required packaged asset and migration/configuration input, including the applicable settings/schema resources. Missing members, undeclared extra members, unsafe or case-colliding paths, stale hashes, changed modes, contradictory package facts, or a closure digest that no longer matches the source/package/member tuple must fail the build or validation.

The package must contain the exact platform requirements.txt, matching complete profile lock, DEPENDENCY-CLOSURE.json, THIRD_PARTY_NOTICES.md, project LICENSE, applicable retained third-party licence files, and byte-identical RELEASE-INVENTORY.json. Canonical Development Files/Legal/dependency-lock.json records every direct and transitive distribution, exact version, upstream licence/source, matching CPython minor, platform/architecture profile, and SHA-256 for every compatible upstream wheel or source artifact. The installer selects the exact profile, installs all pins, runs pip check, and uses verify_dependency_closure.py to reject missing, extra, or version-drifted distributions. Direct pins must remain an exact subset of that profile; ambiguous licences, missing or stale locks, unsupported architectures, absent artifact hashes, or contradictory facts fail closed. Wheels and interpreters are not bundled, so this is verified external dependency provenance rather than an installed-machine pass.

The same inventory records the CPython runtime boundary and every downloadable model/tokenizer identity, role, upstream source, revision, bundled state, artifact-hash status, and redistribution status. Current candidates bundle neither Python nor model/tokenizer bytes: the installer chooses and version-checks a host interpreter, model downloads are user initiated, unavailable package-wide upstream snapshot hashes carry a reason and null value, and model/tokenizer redistribution is explicitly not_applicable. A missing runtime/model/tokenizer fact, a stale canonical inventory, an unsupported claim that bytes are bundled, or a contradiction between the package and inventory fails validation.

Update, rollback, critical-workflow smoke, and physical evidence are four separate objects. Each has exactly status, reference, and reason. passed requires an exact non-empty reference; unavailable and not_applicable require a null reference and a plain reason. Automated builders are forbidden from recording physical evidence as passed. Use unavailable when the required machine, installed-product boundary, owner-safe environment, or real hardware was not available; use not_applicable only when the candidate genuinely has no such boundary. Archive inspection, extracted imports, injected desktop doubles, and source tests belong under automated smoke/update/rollback references and never become physical, signing, notarisation, release, or owner acceptance.

The authoritative builders are Development Files/Tooling/_rebuild_zip.py for Windows, Internal/app/Ports/macOS/build_release.py (called for both architectures by build_mac_release.sh) for macOS, and Internal/app/Ports/Linux/build_release.py for both Linux formats. Each validator must inspect the archive it actually wrote, not a repository-side approximation, and must reject stale source, missing notices or licences, dependency drift, unexpected members, missing runtime/model/tokenizer provenance, inconsistent platform facts, and any automated claim of a physical pass. Deterministic replay requires the same exact source and inputs to reproduce the same ordered members, metadata, provenance bytes, and final archive bytes; it is still not installation evidence.

Development Files/Tooling/_rebuild_zip.py derives one ordered canonical release manifest from the live runtime, builds Internal/Releases/Mumble.zip deterministically from that manifest, then copies those exact bytes to Development Files/Marketing/Website/public/Mumble.zip. The maintained website destination must already exist; a missing destination is a visible build failure and the builder must not recreate an unexpected project structure. The builder normalizes supported packaged text files, including cloud_schema.sql, to LF line endings independently of whether the source checkout uses CRLF or LF, while preserving binary bytes unchanged. It includes the launcher, project licence, Internal launchers, runtime, and processing_route.py while excluding tests, ports, caches, virtual environments, and development-only files. The current accepted candidate adds exactly six package members to the historical 141-member Issue #33/#26/#27 convergence manifest: Mumble/DEPENDENCY-CLOSURE.json, Mumble/Internal/app/model_provenance.py, Mumble/Internal/app/requirements-lock-win-x86_64-cp313.txt, Mumble/Internal/app/verify_dependency_closure.py, Mumble/RELEASE-INVENTORY.json, and Mumble/RELEASE-PROVENANCE.json. The resulting current manifest contains 147 unique members; both maintained ZIPs are byte-identical, 1,207,711 bytes, at SHA-256 70794B4D13C1C38662425DEB5700865728955F4FAC78DC2D083436F63FB99493. test_release_builder.py keeps the required destination and byte-identity boundary under regression coverage, proves the complete canonical manifest remains byte-identical when the SQL source uses CRLF or LF, and opens each tracked archive to require clean CRC, unique exact canonical membership, and exact canonical packaged bytes for every member. This source binding must be checked after runtime changes; comparing the two tracked ZIPs only to one another cannot detect that both are stale.

The Windows updater treats Mumble/, not only Internal/app/, as the replaceable and rollback-safe product. A valid update must contain exactly one complete root with Mumble.exe, LICENSE, and the required app runtime and lifecycle scripts. Each canonical installation derives a private update identity and pending-script directory from its full product path, so sibling installations cannot overwrite or apply one another's transaction. The swap carries the excluded Internal/app/.venv forward, refreshes dependencies and branding, preserves the captured run-at-login choice while refreshing shortcuts, prefers the updated root launcher, and moves the current product only into a unique transaction-owned backup. The previous rollback receipt remains authoritative until every required move and refresh succeeds. Rollback accepts only a same-installation receipt plus a matching marker inside a complete sibling backup, uses a new collision-safe path for the version being replaced, and never deletes an unrelated Mumble.old or other sibling. Installer and uninstaller process shutdown requires the exact executable path paired with its leading mumble.py or webui_shell.py entry point, or the exact root launcher. Focused source tests and temporary transactions do not replace a disposable clean install, normal launch, update, rollback, uninstall, and residue check.

Internal/app/processing_route.py and Internal/app/model_authority.py are the authoritative maintained route sources. Run Development Files/Tooling/sync_processing_route.py to generate newline-normalized macOS/Linux copies and --check to detect semantic drift across checkout line-ending styles; do not edit three independent implementations. Platform Settings modules retain only their storage and locking adapters, and platform controllers retain only their communication adapters. Every provider-selection surface must call ModelDiscoveryAuthority.activate_provider(); the generic settings bridge must reject llm_provider.

macOS and Linux source lives under Internal/app/Ports/. Each port owns its input, paste, overlay, storage, installer, and release seams. Shared behaviour should be changed in the Windows source first, synchronized deliberately, and tested at the shared contract plus the relevant platform adapter. Internal/app/dictation_session.py owns durable transcript reconciliation and selected transcription-route result semantics; run both Development Files/Tooling/sync_macos_shared_contracts.py and Development Files/Tooling/sync_dictation_session.py after changes so the maintained macOS and Linux copies cannot drift. Each release allowlist must include both route-authority modules. Offline builders must produce reproducible archives, verify membership and integrity, extract into a clean temporary directory, and import the shared authority from the extracted app/ directory rather than the repository checkout. Those checks do not prove installation, signing, notarization, or physical use.

For the maintained macOS tree, run Development Files/Tooling/sync_macos_shared_contracts.py after an accepted shared dictation, insertion, Mumble Find, Meetings, History, Stats, or Web UI change, then require --check in focused verification. Like the processing-route checker, the generator normalizes CRLF and LF representations before comparing maintained text, writes generated text with LF newlines, and still rejects every other content difference. Apart from line-ending representation, it uses exact shared content except for a small deterministic macOS transform covering native shortcuts, Safari, Start at Login, the macOS data-folder label, removal of Windows-only setup copy, and the macOS permission-recovery card. macOS-only behaviour belongs in the macos_*, Spotlight, AppKit drag, permission, focus, controller, menu-bar, audio, and release seams. Adapter tests with injected doubles are source evidence only: physical TCC, hotkeys, microphone/audio devices, AppKit drag/focus/windows, Apple Silicon/Intel artifacts, installation, signing, and notarisation require separate macOS evidence.

Issue #27 Linux parity uses linux_desktop.py for truthful session/search/audio capability facts, portal_shortcuts.py for compositor-approved Wayland global shortcuts, linux_insertion.py for native-session clipboard and exact-once delivery adapters, linux_native_drag.py for controller-resolved X11 GTK URI drag, and linux_dictation.py plus the shared immutable session contract for bounded durable capture. Production Mumble Find must query GNOME LocalSearch/Tracker or KDE Baloo; plocate is a labelled stale filename-only fallback, and absence of an index is unsupported rather than an unbounded folder crawl. Wayland must never fall through to XWayland clipboard, input, target identity, or drag claims. A generic D-Bus/GTK library is not shortcut capability: the bounded probe must establish the live org.freedesktop.portal.GlobalShortcuts interface. Autostart readiness must parse the enabled entry's own Exec command and prove that it resolves to the current installed Mumble launcher or the current virtual-environment Python plus Mumble entry point; a separate usable launcher cannot rescue a missing, stale, mismatched, or unresolvable enabled target. GTK preparation occurs before one deadline-owned native-drag claim, with the deadline checked immediately before the external drag side effect; a timed-out operation can neither begin late nor publish success. Compositor-limited drag retains Open and Show in folder alternatives, and an on-time GTK drag start is still not proof that a physical target accepted the drop.

For the focused Linux parity boundary, run the new Linux functional, insertion, durable-dictation, and correction pytest modules with the existing Linux adapter/security/UI modules; run the narrow Windows/shared durable-transcription regressions; run the procedural platform modules directly with UTF-8 output; run the Linux release-builder pytest, Development Files/Tooling/sync_processing_route.py --check, Development Files/Tooling/sync_dictation_session.py --check, changed-file syntax/static checks, and only directly affected browser cases. These checks must keep GNOME Wayland, KDE Wayland, representative X11, distribution dependencies, Flatpak/Snap restrictions, physical audio/input/focus/clipboard/drag, package installation, exact-head CI, and owner acceptance as separate gates.

A lean VPS lifecycle may use an isolated HOME/XDG prefix and explicitly labelled native doubles for host components that are absent, but the receipt must name every double and must not convert that result into physical desktop evidence. A valid lifecycle still uses the real built archive, real installer and launcher, packaged imports, current autostart parser, controlled stop, real uninstaller, unrelated-entry preservation, and residue checks. An injected WebKitGTK or xdg-open boundary proves only package control flow; physical windows, browser/file opening, tray, clipboard, input, microphone, native search freshness, drag, and compositor behaviour remain open.

9Release discipline

  1. Verify the source tree and package from a clean, reviewable state.
  2. Run clean extraction, install, launch, update, and uninstall checks.
  3. Test microphone, hotkeys, focus, paste, clipboard restoration, and shutdown on physical hardware.
  4. Complete signing, publisher, release-note, and rollback checks.
  5. Only then describe the build as a public release.
