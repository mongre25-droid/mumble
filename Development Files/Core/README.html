In plain terms

Mumble is a local-first voice workspace. Press a hotkey, speak, and Mumble turns your speech into useful text at the cursor. The current product also includes the Deck, meetings, Reader, statistics, and local search on supported platforms.

1What Mumble is

Mumble is a desktop dictation and voice-workspace application. Windows is the product-contract source; macOS and Linux reuse the shared engine and provide platform-specific seams.

Local
Speech-to-text is local by default with faster-whisper.
Deck
Searchable history, clipboard capture, favourites, and AI jobs.
Meetings
Recording, transcription, search, and export workflows.
Reader
Documents, reading progress, statistics, and optional voice.

The current interface is the golden-black liquid-glass Web UI in Internal/app/webui/, supported by the floating Island overlay. The app is not defined by older mockups or plans; the running source is the authority.

2The current user flow

1
Activate

A global hotkey starts a recording through the controller in Internal/app/mumble.py.

2
Transcribe

Audio is processed locally by default. Cloud transcription is a visible, opt-in setting and sends the recorded clip to the selected provider.

3
Shape

Offline cleanup and mode inference run first. Optional local or cloud processing can shape text for Prompt, Email, Reply, Convert, or other Deck workflows.

4
Paste and remember

The result is pasted at the cursor, stored in local history, reflected in statistics, and made available in the Deck.

3Non-negotiable promises

  • Privacy is visible. Audio stays on the device unless the user explicitly chooses Cloud transcription. Text leaves the device only through a clearly selected cloud feature and the user's own provider key.
  • Claims match reality. Never document, market, or display a feature that the current runtime does not implement.
  • The product remains focused. Voice-to-text is the centre; the Deck, meetings, Reader, and search support that workflow rather than replace it.
  • One shared product contract. Platform-specific code belongs in the platform seam. The Windows runtime is the reference implementation.
  • The four Core records stay current. Current truth belongs in README, STATUS, HANDBOOK, and LOGS rather than scattered dated project files.

5How development works

  1. Read this README and STATUS; read the relevant code and tests before editing.
  2. Make the smallest coherent change and keep runtime, UI, tests, and platform seams aligned.
  3. Verify the changed path, then run the isolated application suite when runtime code changes.
  4. Update the relevant Core record before sign-off. Unresolved work goes in STATUS; completed work goes in LOGS.
  5. Do not treat a local green test run as proof of clean installation, physical microphone/paste behaviour, signing, or public release readiness.
Owner boundary: secrets, spending, account changes, public releases, and destructive irreversible actions require the owner's explicit decision.
